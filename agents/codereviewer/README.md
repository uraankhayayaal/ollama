# Код-ревью агент

Агент `codereviewer` проводит автоматическое код-ревью Merge/Pull Request
и оставляет замечания прямо на строках кода. Поддерживает GitHub и GitLab
(в т.ч. self-hosted). Запуск:

```bash
go run . review <URL> [фокус_ревью]
# пример
go run . review https://github.com/user/repo/pull/10 "безопасность"
```

Всё настраиваемое поведение задаётся переменными окружения
(см. `.env.example`).

---

## Реализованные фичи

### 1. Мультихостинговая абстракция `Forge`
Единый интерфейс для систем хостинга кода. Добавление нового провайдера =
реализация интерфейса `forges.Forge` и регистрация в фабрике
(`forges.New`), тип распознаётся автоматически по URL.

- **GitHub** — REST API `https://api.<host>`, inline-комментарии с привязкой
  к `commit_id`, при невозможности привязать строку — fallback в общий тред.
- **GitLab** — включая self-hosted (домен содержит `gitlab`).
- Токены: `GITHUB_TOKEN` (scope `repo`/`public_repo`), `GITLAB_TOKEN`.

### 2. Проверка замечаний по диффу (защита от галлюцинаций)
Перед публикацией каждое замечание сверяется с актуальным диффом:

- Если файла нет в диффе или номера строки в новой версии не существует —
  комментарий отбрасывается (GitHub всё равно бы вернул 422).
- Отсечённые замечания не блокируют апрув и не считаются ошибками,
  но сообщаются модели в ответе и учитываются в сводке.
- Дубликаты замечаний к одной и той же строке публикуются один раз.

### 3. Ревью по частям (чаркинг большого диффа)
Большой дифф не переполняет контекст модели и меньше провоцирует
«провал внимания» и галлюцинации.

- Дифф режется по границам файлов (целый файл всегда в одном чанке).
- Модель обрабатывает по одному чанку через инструмент `NextChunk`.
- Порог разбиения — `REVIEW_CHUNK_SIZE` (по умолчанию 14000; 0 — выкл).

### 4. Восстановление ревью из текстового ответа
Модели (особенно YandexGPT) иногда пишут ревью текстом вместо вызова
инструментов. Такой структурированный ответ автоматически парсится
(файл / номер строки / текст) и публикуется тем же путём `ReviewMr`
с сохранением фильтра по диффу и дедупликации.

### 5. Критичность замечаний и блокировка апрува
- Замечание считается критичным, если текст начинается с `критично:`
  (регистронезависимо, с учётом пробелов).
- При наличии критичных замечаний `ApproveMr` блокирует одобрение.
- Здравый смысл зашит в промпт: критично = нарушение работы или безопасности.

### 6. Управление циклом ревью
- Лимит замечаний за ревью — `REVIEW_MAX_COMMENTS` (по умолчанию 10).
- Лимит раундов «модель → инструмент» — `REVIEW_MAX_ROUNDS` (по умолчанию 12).
- Таймаут всего цикла — `REVIEW_TIMEOUT` (по умолчанию 5m).

### 7. Отсечение сгенерированных и бинарных файлов
`dist/`, `vendor/`, `node_modules/`, `package-lock.json`, `*.min.js`,
`*.pb.go`, изображения, бинарники и т.п. исключаются из анализа
(`REVIEW_SKIP_GENERATED`, по умолчанию true), чтобы не тратить контекст
и не комментировать артефакты.

### 8. Фокус ревью
Цель ревью передаётся аргументом CLI (например «безопасность»,
«производительность», «миграции») и смещает внимание модели.

### 9. Детекция языка и языковые промпты
- Язык определяется по расширениям файлов в диффе (20+ языков).
- Для известных стеков подставляются специфичные правила (PHP/Laravel:
  PSR-12, Swoole/Octane, репозитории, DTO и т.п.).

### 10. Итоговая сводка в тред MR/PR
После цикла публикуется отчёт: число замечаний, критичных замечаний,
ошибок публикации, отсечённых галлюцинаций и фокус ревью.

### 11. Апрув с легендой
`ApproveMr` прикладывает к одобрению краткую легенду (сколько замечаний
опубликовано), чтобы в истории было видно, что именно проверялось.

### 12. Обработка ошибок публикации
Если комментарий не удалось опубликовать, ошибка фиксируется и апрув
блокируется — изменения не одобряются «вслепую» при частичном результате.

## Настройки (переменные окружения)

| Переменная                 | По умолчанию | Назначение                                   |
|----------------------------|--------------|----------------------------------------------|
| `GITHUB_TOKEN`             | —            | Токен GitHub (scope `repo`/`public_repo`)    |
| `GITLAB_TOKEN`             | —            | Токен GitLab (scope `api`)                   |
| `REVIEW_TIMEOUT`           | `5m`         | Таймаут всего цикла агента                  |
| `REVIEW_MAX_COMMENTS`      | `10`         | Лимит замечаний за ревью                    |
| `REVIEW_MAX_ROUNDS`        | `12`         | Лимит раундов «модель → инструмент»          |
| `REVIEW_BLOCK_ON_CRITICAL` | `true`       | Блокировать апрув при критичных замечаниях  |
| `REVIEW_SKIP_GENERATED`    | `true`       | Отсекать сгенерированные/бинарные файлы     |
| `REVIEW_CHUNK_SIZE`        | `14000`      | Порог (симв.) разбиения диффа на части; `0` — выкл |

## Идеи на будущее

### Приоритетные

- **Дедупликация однотипных замечаний между разными файлами** — одна и та
  же ошибка (например, пропущенная проверка `nil`) в нескольких местах.
  Сейчас каждая локация получает своё замечание (так и должно быть для
  автора), но можно добавить опцию «сгруппировать повторы в одну сводную
  заметку».
- **Автодетект «критично:» по паттернам, а не только по префиксу** —
  дополнительно распознавать SQL-инъекции, `eval` с user-вводом, ключи
  доступа и секреты в коде. Надёжнее блокировка апрува.
- **Детерминированный детектор секретов** — успешно публиковать замечания
  о найденных API-ключах, паролях, SSH-ключах отдельно и жёстко (не полагаясь
  только на модель).
- **Учёт локальных конфигов стиля** — читать `.editorconfig`, конфиг
  линтера (eslint/prettier/phpcs) и проверять соответствие стилю проекта,
  а не только общим рекомендациям.
- **Прогресс-комментарий** — для длинных ревью постить промежуточный
  «ревьюируется…», чтобы автор видел, что агент работает.

### Средние

- **Режим «только критика»** — не спамить замечаниями о стиле, вернуть
  только реальные баги и критические проблемы.
- **Таймаут/лимит токенов на модель** — суммарный бюджет токенов на всё
  ревью, чтобы зациклившаяся модель не расходовала контекст без пользы.
- **Мета-статистика по файлам** — в сводку добавлять плотность замечаний
  по файлам (где «горячее»), чтобы автор знал, что чинить первым.
- **Привязка комментариев к коммиту/ханку** — чтобы после правок и force-push
  контекст замечания не терялся.
- **Повторные раунды «проверка исправлений»** — агент сам перечитывает diff
  после внесённых правок и подтверждает закрытие замечаний.

### Для удобства

- **Подтверждение перед апрувом** — интерактивный запрос перед одобрением
  или переключатель «апрув только при нуле критичных».
- **Белый/чёрный список путей** — ревьюить только выбранные директории
  или исключать `docs/`, `i18n/` и т.п. через конфиг.
- **Экспорт отчёта** — сохранять сводку ещё и в файл (Markdown/JSON) для
  интеграций/CI.
- **HTTP Webhook/уведомления** — слать результат ревью в чат/сообщения.
