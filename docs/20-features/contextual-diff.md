# Контекстные диффы

Просмотр изменений **ветки задачи или эпика** относительно основной ветки
проекта, а не рабочей копии общего клона.

## Зачем контекстные

С появлением git-workflow реальная работа идёт не в основном клоне
`temp/<проект>`:

- специалисты задач в `in_progress` пишут в постоянные worktree веток
  `ai/task/<id>` (`.wt-task-<проект>-<taskID>`), `OutputDir` специалиста =
  worktree задачи;
- изменения попадают в релизные ветки эпиков `ai/epic/<id>` через
  авто-мёрдж `done → релиз`;
- основной клон остаётся чистым на `ai/<проект>`.

**Следствие:** проектный дифф показывал пустой результат либо только
legacy-правки общего клона. Кнопка «Дифф» была удалена как устаревшая;
`Diffboard` открывается из модалки задачи или эпика.

## Как открыть

| Откуда | Что показывает |
|---|---|
| `GitBlock` модалки **эпика** | Изменения ветки эпика `ai/epic/<id>` |
| `GitBlock` модалки **задачи** | Изменения ветки задачи `ai/task/<id>` |

Кнопка не показывается, если ветка ещё не создана или проект не
git-типа.

## Эндпоинт

```http
GET /api/projects/{id}/diff?ref=<ветка>&vs=<base>
GET /api/projects/{id}/diff?ref=<ветка>&vs=<base>&file=<путь>
```

| Параметр | Обяз. | Значение |
|---|---|---|
| `ref` | нет | Зарегистрированная ветка (в т.ч. worktree задачи) |
| `vs` | нет | Точка отхода; пусто = `git_base` проекта |
| `file` | нет | Патч одного файла (ленивая загрузка) |

Валидация (`server/git.go:219-241`):

- `vs` **обязан** совпадать с `git_base` проекта, иначе `400`.
- `ref` **обязан** быть зарегистрирован в проекте, иначе `400`.

Ответ без `file`:

```json
{"kind":"git","branch":"ai/task/42","base":"main","remote":"...",
 "files":[{"path":"...","status":"modified","added":12,"deleted":3}]}
```

Ответ с `file` — `{kind, path, status, patch}`.

### Статусы файлов

`server/diff.go:23-29`: `added`, `modified`, `removed`, `renamed`,
`submodule`.

## Как считается дифф

`server/diff.go:51-89`, две ветки:

### Ветка с worktree (задача)

```
1. root = worktree ветки
2. проверка: git rev-parse --git-dir  (worktree мог быть уже снят)
3. mergeBase = git merge-base <base> <branch>   ← в ОСНОВНОМ клоне
4. git add -N -A                             ← новые файлы в индекс
5. git -c diff.submodule=log diff <mergeBase>
```

> **Почему merge-base, а не трёхточечная форма:** трёхточечный diff
> сравнивает **коммиты** напрямую, а для worktree нужно включить рабочее
> дерево. Поэтому merge-base используется как обычная точка сравнения.
> Untracked-файлы включаются через `add -N`, сохраняя их содержимое.

`diff.submodule=log` показывает изменения сабмодулей как список коммитов
вместо смены SHA.

### Ветка без worktree (эпик)

```
git -c diff.submodule=log diff <base>...<branch>
```

Трёхточечная форма — только коммиты, рабочее дерево не трогается.

### Не-git проект

Baseline-снимок каталога (`snapDiff`), снимается при первом запросе.
Возвращаются списки `added` / `modified` / `removed` и per-file
unified-патчи для line-level отображения.

## Кэш

`cachedDiff` с ключом `project|ref|base` (`diff.go:107`), хранение под
`diffMu` (`server.go:78-82`).

- Список файлов (`file == ""`) **пересоздаётся** на каждый запрос — свежесть
  важнее экономии.
- Ленивые патчи берутся из последнего результата с тем же ключом.
- `invalidateDiffs(project)` (`:93`) сбрасывает все ветки и проект.

> **Бывший баг:** `gitProjectDiff` мог вернуть закешированные данные без
> пересоздания на новый запрос списка. Исправлено.

## Интерфейс

`web/src/Components/Diffboard/` — общая панель:

- список файлов с фильтрами;
- ленивая загрузка side-by-side патча (`sidebyside.ts`);
- **проектных действий accept/reject нет** — это дифф конкретной ветки.

Тип события `diff` объявлен во фронтовом union (`web/src/live.ts:36-40`),
но бэкенд его **не публикует**: диффы доступны только через REST. Не
рассчитывайте на push-обновление панели — перезапрашивайте по действию.

## Сабмодули

В диффе родителя сабмодуль отдаётся со статусом `submodule` — это смена
SHA. Содержимое правок смотрите в диффе самого сабмодуля (он зарегистрирован
как отдельный проект).

Подробнее — [Сабмодули](submodules-multirepo.md).

## Проверить

```bash
# Вручную
cd temp/<проект>
git diff main...ai/task/42 --stat
git -C .wt-task-<проект>-42 diff $(git merge-base main ai/task/42) --stat
```
