# Песочница выполнения

Команды инструмента `Run` приходят от модели. По умолчанию они выполняются
**на хосте** — это осознанное решение. Песочница включается явно.

## Почему по умолчанию хост

Пробный запуск с режимом `auto` показал, почему (`tools/sandbox.go:112-129`):
«docker доступен» не значит «в контейнере всё работает». В песочницу уезжал
LSP-чекер (он вызывает тот же `runCommand`) и падал на проектах без
распознанного стека, потому что образ выбирался по манифесту, которого у
чекера нет.

Молчаливый перенос **всего** исполнения (сборка, тесты, LSP) в контейнер —
поведенческое изменение, ломающее проекты по неочевидной причине.

## Настройка

```bash
CODEGEN_SANDBOX=             # пусто (по умолчанию) = хост
CODEGEN_SANDBOX_IMAGE=       # пусто = выбор по стеку проекта
CODEGEN_IMAGE=               # legacy-алиас для CODEGEN_SANDBOX_IMAGE
CODEGEN_SANDBOX_NETWORK=default    # default | none | bridge | whitelist
CODEGEN_SANDBOX_ALLOW_DOMAINS=     # белый список исходящего (см. «Сеть»)
CODEGEN_SANDBOX_MEMORY=2g
CODEGEN_SANDBOX_CPUS=2
CODEGEN_SANDBOX_RO=false     # read-only корень контейнера
CODEGEN_SANDBOX_ALLOW_WRITE=true    # монтировать проект на запись
CODEGEN_SANDBOX_DOCKER=      # путь к docker; читается ДО поиска в PATH
CODEGEN_SANDBOX_BIN=         # docker, который песочница подставит дочернему compose
CODEGEN_SANDBOX_USER=        # UID хоста для сборки образа
CODEGEN_DOCKER_HOST=         # альтернативный сокет демона
CODEGEN_DOCKER_TLS=
CODEGEN_DOCKER_CERT=
```

### Режимы

| Значение | Поведение |
|---|---|
| пусто / `0` / `off` / `false` / `no` / `local` / `host` | **Хост** (по умолчанию) |
| `container` / `1` / `on` / `true` / `yes` / `docker` | Всегда контейнер; нет Docker → **ошибка конфигурации**, не тихий возврат на хост |
| `auto` | Контейнер при доступном Docker, иначе хост с пометкой `sandbox_note` в ответе |
| `session` | **Контейнер на сессию оркестрации** (см. ниже); контейнера нет → строгая ошибка, не хост |

> `CODEGEN_DOCKER_*` существуют потому, что переменные `DOCKER_*` в окружении
> агента могут быть заняты чем-то ещё.

## Сессионный контейнер (`CODEGEN_SANDBOX=session`)

**Этап 1** изоляции рабочих пространств (план
`docs/plans/PLAN-2026-10-02-wip-enterprise.md`). Отличие от эфемерного
режима (`container`): эфемерный поднимает `docker run` **на каждую команду**
и убивает её после, сессионный держит **один контейнер на запуск
оркестрации** — от старта раннера до его завершения.

### Жизненный цикл

1. Сервер при старте оркестрации (`Session.start`) вызывает
   `server/sandbox.go:startProjectSandbox`: Docker ping → удаление остатков
   прошлой сессии (`ai-sandbox-<проект>`) → сеть → образ → контейнер.
   Ошибка старта = **отказ запуска оркестрации**: `session` объявляет
   изоляцию, тихий переход на хост запрещён.
2. Контейнер регистрируется в реестре (`sandbox/registry.go`); команды
   `FileOps.Run` и приёмки находят его по имени проекта или пути каталога.
3. По завершении (и по отмене стопом) контейнер снимается: stop → rm →
   удаление прокси (`defer` в горутине-раннера, п. 1.7).

### Что выполняется внутри, а что нет

Внутри контейнера: команды `Run` разработчика, приёмки (build/run/test) и
LSP-чекера — всё, что приходит через `runCommand` с покрытым каталогом.

Остаётся на хосте (сознательно, Этап 5): файловые операции (чтение/запись —
каталоги смонтированы по **тем же путям**, файлы видны обеим сторонам),
git-операции, RAG-индексация, логи. См. ограничения в плане.

### Монтирование

В контейнер идёт **родительский** каталог корня проекта: worktree'и задач
(`.wt-task-<имя>-…`, `.resolve-…`, `.conflict-…`) создаются соседями клона,
и корень один их не покрыл бы. Для temp-проектов родитель — общий `temp/`:
смешивания с чужими проектами нет, потому что матчинг внутри сессии идёт по
реестру — каталог проекта или его dot-сосед с именем проекта
(`sandbox/registry.go:coverLen`). Чужая команда в чужую сессию не попадает.

Пути **не переписываются**: workdir команды = хостовому пути, поэтому скрипты,
make-цели и агенты не замечают подмены.

### Изоляция (п. 1.4)

- non-root: uid/gid хоста (`HostUser`) — файлы проекта остаются владельцем;
- `cap-drop ALL`, `no-new-privileges`;
- лимиты CPU/RAM (`CODEGEN_SANDBOX_MEMORY/CPUS`), `/tmp` — tmpfs;
- отбраковка разрушительных команд до exec (общий гейт);
- сеть — изолирована по умолчанию (см. «Сеть»).

### Таймауты

Команда оборачивается в `timeout -s KILL <сек>` (бинарь есть в образах
debian/busybox; факт проверяется пробой при старте) плюс клиентский дедлайн
`CODEGEN_RUN_TIMEOUT`. Если бинаря `timeout` нет — только клиентский
дедлайн, а осиротевшие процессы живут до конца сессии и умирают вместе с
контейнером.

## Выбор образа

`CODEGEN_SANDBOX_IMAGE` → по стеку проекта → dev-образ `ai-sandbox:latest`.

| Маркер | Образ |
|---|---|
| `go.mod` | `golang:1.24` |
| `package.json` | `node:22` |
| `requirements.txt` / `pyproject.toml` | `python:3.12` |
| `composer.json` | `php:8.3-cli` |
| не распознан | `ai-sandbox:latest` |

Dev-образ нужен для монорепо и make-целей вида `make build`. Собирается
один раз (или средствами кода):

```bash
SANDBOX_UID=$(id -u) SANDBOX_GID=$(id -g) docker compose -f sandbox/compose.yaml build
```

Если образа нет в кэше демона, песочница собирает его **сама**: `ai-sandbox:latest`
в реестре не существует, поэтому неявный pull при `docker run`/`create` дал бы
«pull access denied» (даже если в логике Pull). Автосборка (`sandbox/ensureimage.go`)
использует тот же `sandbox/Dockerfile` (запечён в бинарь через `go:embed`) и
тот же Engine API, что и compose: реестровые образы она не трогает — их docker
тянет неявным pull. Сериализована мьютексом, чтобы параллельные команды/сессии
не гоняли один и тот же `docker build`.

Последний шаг обязателен: у ЛСП-чекера манифеста проекта нет, и без dev-образа
контейнерный режим был бы недостижим вовсе (`tools/sandbox.go:301-310`).

## Монтирование

| Что | Куда | Режим |
|---|---|---|
| Рабочий каталог | `/workspace` (`sandboxWorkspace:47`) | `:rw` по умолчанию |
| tmpfs | `/tmp` (`sandboxTmp:53`) | кэши и HOME |

`CODEGEN_SANDBOX_ALLOW_WRITE=false` монтирует проект `:ro` — команда,
которая пишет в проект, упадёт с ошибкой, а не «успешно» не сделает работу.

`CODEGEN_SANDBOX_RO=true` делает корень контейнера read-only; кэши и HOME в
tmpfs, поэтому тулчейн продолжает работать. Рекомендуется для приёмки и
режима «только посмотреть».

## Сеть

`CODEGEN_SANDBOX_NETWORK=default` (мост docker) — по умолчанию сеть **есть**:
без неё `go mod download` и `npm ci` не работают.

`none` отключает сеть полностью. Тогда модели нужны локальные кэши
(`vendor/`, `GOMODCACHE`, `node_modules`, `.venv`), а в ответе появляется
подсказка `sandboxNetworkHelp` (`tools/sandbox.go:453`).

### Изоляция сессии (п. 1.10, 1.11)

У сессионного контейнера сеть **по умолчанию отключена** (п. 1.10): ни
явного флага — нет интернета. Исключение — `CODEGEN_SANDBOX_ALLOW_DOMAINS`:
задан список → сессия получает сеть `whitelist` (п. 1.11).

`whitelist` устроен так: контейнер сидит во **внутренней** docker-сети без
маршрута наружу (обход прокси сырым сокетом невозможен), единственный выход —
прокси с белым списком (`sandbox/egress.go`): точное имя или `*.example.com`,
всё прочее — 403 с записью в лог.

Где живёт прокси — зависит от платформы:

- **Нативный Linux** — шлюз внутренней сети принадлежит хосту, поэтому
  прокси поднимает сам процесс сервера на адресе шлюза (`startEgressProxy`):
  LAN до него не достучится.
- **Docker Desktop (macOS/Windows)** — шлюз принадлежит гостевой VM, хост на
  нём слушать не может, а маршрута из внутренней сети до хоста не существует.
  Поэтому прокси — **gateway-контейнер** (`sandbox/proxycontainer.go`):
  одновременно подключён к внутренней сети сессий (session → прокси on-link,
  без default route) и к обычной `bridge` (выход в интернет через штатный NAT
  демона). Внутри контейнера исполняется наш статик-бинарь
  `cmd/sandbox-proxy` — он собирается кросс-компиляцией из исходников репо
  (`CGO_ENABLED=0 GOOS=linux`, один раз за жизнь процесса) и запекается в
  scratch-образ `ai-sandbox-proxy:latest` через Engine API (`POST /build`,
  без docker CLI и без pull). Сессия получает `HTTP(S)_PROXY` с адресом
  этого контейнера. Для сборки на Desktop нужны **исходники репозитория и go
  toolchain** — иначе старт падает с понятной ошибкой.

```bash
CODEGEN_SANDBOX=session
CODEGEN_SANDBOX_ALLOW_DOMAINS=proxy.golang.org, registry.npmjs.org, *.github.com
```

Явный `CODEGEN_SANDBOX_NETWORK` отменяет изоляцию по умолчанию (opt-out).
`whitelist` в эфемерном режиме (`container`) не поддерживается — прокси
живёт вместе с долгоживущим контейнером, значение откатывается в `default`.

**Что это даёт и чего не даёт:** нет прямого интернета и загрузка только с
разрешённых доменов; изоляции от хоста по-прежнему нет — контейнер видит
служебные порты хоста по адресу шлюза (уровень прежней песочницы; закрытие —
сетевые политики Этапа 5). На Desktop хост из internal-сети недостижим
вообще — это строгое «не даёт», чем на Linux.

## Отбраковка разрушительных команд

Песочница **не спасает** от `rm -rf` внутри рабочего каталога: каталог
проекта смонтирован на файловую систему хоста. Поэтому есть предварительный
фильтр: `sandbox/destructive.go` (общий для всех режимов, п. 1.4), обёртка
`tools/destructive.go` сохранена для эфемерного пути.

Песочница спасает от `rm -rf /` **внутри контейнера**. То есть опасность
зависит от того, где выполняется команда, а не от самой команды.

### Правила

| Категория | Примеры |
|---|---|
| Корень ФС | `rm -rf /`, `rm -fr /`, `rm -r -f /`, `rm --recursive --force /` |
| Домашний каталог | `rm -rf ~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg`, `~/` |
| Разметка разделов | `mkfs`, `fdisk`, `parted`, `diskutil erase` |
| Блочные устройства | `dd of=/dev/`, `>/dev/sd`, `of=/dev/disk` |
| Стирание данных | `shred`, `wipefs`, `srm` |
| Системные каталоги | `rm -rf /etc`, `/usr`, `/var`, `/bin`, `/lib`, `/boot`, `/opt`, `/sys`, `/proc` |
| Права и владелец | `chmod -R 777 /`, `chown -R root`, `chmod 777 /etc` |
| Запись в системные файлы | `>/etc/`, `tee /etc/`, `>/usr/`, `>/boot/` |
| Остановка хоста | `shutdown`, `reboot`, `poweroff`, `init 0`, `systemctl poweroff` |

> **Что НЕ блокируется сознательно:** `curl \| sh`, `sudo`, `dd`,
> `git push --force`. Ложное срабатывание хуже пропуска: агент отказался
> выполнить `rm -rf node_modules` перед сборкой и застрял (`destructive.go:8-15`).

Сравнение — по нижнему регистру с нормализацией пробелов: `rm  -rf  /tmp` и
`RM -RF /` отсекаются одинаково (`destructive.go:87-104`).

Ошибка возвращается модели с объяснением, **что делать вместо**.

## Ошибки конфигурации

`sandboxSpecFor` (`tools/sandbox.go:281-310`) — чистая функция без запуска;
тесты проверяют именно её. Отказ до старта контейнера:

- Команда разрушительна → причина запрета.
- Рабочий каталог не найден → явная ошибка.
- **Путь содержит `:` или `,`** → эти символы ломают `--volume`
  (`src:dst:opts`): контейнер стартовал и не видел проекта. Лучше явная
  ошибка конфигурации — перенесите проект в каталог без этих символов.

## Проверить

```bash
CODEGEN_SANDBOX=container go run . plan <проект> "..."
```

В ответе `Run` появляются sandbox-поля (`sandbox_note` при `auto`-деградации).
Проверить изоляцию:

```bash
CODEGEN_SANDBOX=container CODEGEN_SANDBOX_ALLOW_WRITE=false go run . plan <проект> "..."
```

Запись в проект должна упасть с ошибкой монтирования.

Сессионный режим (нужен запущенный Docker):

```bash
CODEGEN_SANDBOX=session go run . serve
```

В логе проекта — `[sandbox] контейнер сессии ai-sandbox-<проект> запущен …`;
при недоступном Docker запуск оркестрации откажется с явной ошибкой.

Живая проверка сессии и whitelist на настоящем Docker-демоне (вне рабочего
набора, по образцу `E2E_LIVE`; нужен доступный образ `redis:7-alpine` —
busybox sh/timeout/wget, без пулла тулчейнов):

```bash
SANDBOX_LIVE=1 go test ./sandbox/ -run TestLiveSession -v
```

Покрывает: замену сессии, пути/mount, отбраковку, сеть `none`, таймаут,
уничтожение контейнеров, whitelist (deny 403 + проход разрешённого домена
через прокси) — на Docker Desktop вместе с gateway-контейнером прокси.
