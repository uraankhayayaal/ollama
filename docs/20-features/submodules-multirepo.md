# Сабмодули и мульти-репозитории

Сабмодуль — самостоятельный git-репозиторий, «приклеенный» к родителю
gitlink-записью в index (mode 160000 + SHA). В диффе родителя он выглядит
как смена одного SHA, поэтому правки агента нужно смотреть в самом сабмодуле.

Система даёт сабмодулям такую же изоляцию, как основному клону.

## Настройка

```bash
GITOPS_SUBMODULES=1            # включено по умолчанию; "0" выключает
GITOPS_SUBMODULE_DEPTH=        # пусто = полная история; число = shallow
```

> `GITOPS_SUBMODULES` считается включённым при **любом** значении, кроме
> `"0"` (`gitops/gitops.go:251,271`). Пустое значение = включено.

`GITOPS_SUBMODULE_DEPTH` должен быть **положительным целым**, иначе —
ошибка конфигурации, а не молчаливый fallback на полную историю
(`gitops/submodule.go:168-174`).

## Тип сабмодуля

`gitops/submodule.go:31-43`:

| Поле | Смысл |
|---|---|
| `Path` | Путь относительно `Root` родителя (из `.gitmodules`) |
| `URL` | Remote сабмодуля (из `.gitmodules`) |
| `Root` | Абсолютный путь; пуст = не инициализирован |
| `Remote` | Вычисленный remote: `git remote get-url origin`, иначе `URL` из `.gitmodules` |
| `Base` | Коммит-база (`rev-parse HEAD`) |
| `Branch` | Изолированная feature-ветка |
| `DefaultBranch` | Ветка из `.gitmodules` или `origin/HEAD` |

## Жизненный цикл

```
git clone <remote> temp/<проект>
      │
      ▼
ListSubmodules — парсинг .gitmodules
   (нет файла → пустой список, НЕ ошибка)
      │
      ▼
EnsureSubmodules — git submodule update --init [--depth N]
      │
      ├── читается remote каждого сабмодуля
      └── Root = Root родителя + Path
      │
      ▼
PrepareSubmodules — изолированные feature-ветки
   ветка = <prefix>/submodule/<путь>  (SanitizeBranchName)
      │
      ├── git checkout -B <branch>
      └── git checkout --detach <branch>   ← detach!
      │
      ▼
Регистрация в реестре workspace как отдельные проекты
   имя = <родитель>--<путь>
      │
      ▼
Работа агентов: свои worktree, свои ветки ai/task/<id>
```

> **Важно:** после создания ветки сабмодуль **отсоединяется** (`--detach`) от
> неё. Это стандартная практика git для сабмодулей: без detach коммит в
> сабмодуле изменил бы состояние родителя.

## Порядок пуша

**Сабмодули пушатся ДО родителя.** Родительский gitlink поднимается только
после того, как на remote сабмодуля лёг новый SHA — иначе remote родителя
ссылался бы на несуществующий gitlink (`gitops/submodule.go:9-14`).

Это самый частый источник «сломанных» MR в мульти-репозиторных проектах.

## Реестр workspace

Каждый сабмодуль регистрируется как **отдельный git-проект** с именем
`<родитель>--<путь>`. Поэтому он виден в Web UI как самостоятельный проект
со своей доской, ветками и диффами.

## Диффы

`gitops.Repo.Diff` и `SubmoduleCommit` фиксируют и показывают изменения
сабмодуля. В `server/diff.go` сабмодуль отдаётся со статусом `submodule`
(`server/diff.go:23-29`) — панель диффов показывает смену SHA, а содержимое
правок доступно через дифф самого сабмодуля.

## Мульти-репозитории (не сабмодули)

Система не поддерживает несколько независимых репозиториев в одном проекте:
один проект = один `.git`. Для мульти-репо используйте один из вариантов:

1. **Сабмодули** — если зависимости версионируются вместе.
2. **Отдельные проекты** — каждый репозиторий регистрируется в реестре
   отдельно, а координация описывается в задачах.
3. **Монорепо** — чаще всего правильный выбор для нового проекта.

## Проверить

```bash
cd temp/<проект>
cat .gitmodules
git submodule status
git -C <путь-сабмодуля> branch -a
git -C <путь-сабмодуля> log --oneline -5
```

## Типичные проблемы

| Симптом | Причина |
|---|---|
| MR родителя падает на CI | Не запушен сабмодуль — родитель ссылается на несуществующий SHA |
| `git submodule update` не тянет | Выставлен `GITOPS_SUBMODULES=0` |
| Полная история сабмодуля | `GITOPS_SUBMODULE_DEPTH` пуст |
| Ошибка «must be a positive integer» | `GITOPS_SUBMODULE_DEPTH` задан не числом или ≤ 0 |
