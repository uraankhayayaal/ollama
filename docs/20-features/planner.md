# Планировщик

Команда `plan` разбивает задачу на шаги и выполняет их отдельными агентами с
чистым контекстом. Альтернатива доске (`kanban`) — здесь без Redis-доски,
всё в одном процессе.

```bash
go run . plan <имя_проекта> "<промпт>"
go run . plan <имя_проекта> "<промпт>" --resume
```

## Настройка

```bash
# Параллельность
CODEGEN_PARALLEL=1              # вкл по умолчанию; 0/false/off/no — выкл

# Откат
CODEGEN_ROLLBACK_ON_FAIL=1     # вкл по умолчанию

# Контракты
CODEGEN_CONTRACT_ENFORCE=1     # вкл по умолчанию (мягкий, Warn-уровень)

# Чекпоинты (Redis)
REDIS_ADDR=localhost:56379
REDIS_PASSWORD=
REDIS_DB=0
PLAN_CHECKPOINT=               # 1 — принудительно включить
PLAN_CHECKPOINT_TTL=0          # 0 = без истечения
PLAN_RESUME=                   # 1 — эквивалент --resume

# Кодогенерация
CODEGEN_LANG=Go
CODEGEN_MODULE=
CODEGEN_MAX_FILES=0
CODEGEN_NO_OVERWRITE=false
CODEGEN_SUMMARY_FILE=SUMMARY.md
CODEGEN_RUN_TIMEOUT=60s
CODEGEN_RUN_MAX_OUTPUT=20000
```

> `CODEGEN_PARALLEL`, `CODEGEN_ROLLBACK_ON_FAIL`, `CODEGEN_CONTRACT_ENFORCE`
> **не описаны в `.env.example`**, но активны по умолчанию. Чтобы выключить —
> нужно задать `0`/`false`/`off` явно.

## Цикл исполнения

`agents/planner/executor.go`:

```
1. ComputeWaves()               — нарезка шагов на волны независимости
   ошибка порядка шагов → фатальна
2. initCheckpoint()             — Redis-чекпоинт (если доступен)
   запись PLAN.md
3. Для каждой волны (строго последовательно):
   └─ runWave()                 — шаги внутри волны ПАРАЛЛЕЛЬНО
      └─ runAcceptanceLoop()    — цикл приёмки, бюджет ACCEPT_MAX_ROUNDS
4. Финальная перезапись PLAN.md
```

Первая ошибка в волне отменяет соседей через общий `context.WithCancel`
(`executor.go:207-234`).

Ограничения: `maxKanbanRounds = 100` (`kanban.go:29`), опрос в режиме
ожидания `standbyPoll = 5s` (`kanban.go:87`).

## Шаги плана

Планировщик возвращает план в JSON: шаги с типом агента, зависимостями и
**scope** — областью работы (конкретные файлы/каталоги).

- Агенты работают только в своём scope.
- Шаги разработки идут агентам `backend` (`server/`) / `frontend`
  (`frontend/`) — не пересекаются.
- Финальным шагом добавляется `qa` — единая приёмка. При провале отчёт
  возвращается планировщику, тот строит шаги исправления, приёмка
  повторяется (цикл `ACCEPT_MAX_ROUNDS`).

### Последовательность делегации

Все шаги разработки → агенты-разработчики → затем финальный шаг `qa`.
Это гарантирует, что приёмка увидит цельный проект, а не набор
недоделанных частей.

## Ключевые механизмы

### Скоупы и откат

Перед каждым шагом снимается **scoped-снимок** (только затронутые каталоги).
Если шаг упал с реальной ошибкой, директория возвращается к состоянию
снимка: файлы, созданные упавшим субагентом, удаляются; изменённые и
удалённые — восстанавливаются.

Откат **не выполняется** при исчерпании лимита раундов — иначе сломался бы
resume.

Файловые мутации сериализуются пер-проектной блокировкой
(`tools/filelock.go`): `Write`, `AppendTo`, `Remove`, `SearchReplace`,
`PatchGoFunction` и `snapshot.Restore` под блокировкой каталога проекта.
Параллельные шаги одной волны не рвут общие файлы. Разные проекты и тесты
не блокируют друг друга.

### Сжатие истории

Файлы читаются не целиком: `ReadFiles` поддерживает «хирургическое окно»
по строкам (`tools/fileops.go:627-723`) и лимиты
`CODEGEN_READ_MAX_FILE` / `CODEGEN_READ_MAX_TOTAL`. Дифф ревью ограничен
`REVIEW_MAX_DIFF_SIZE`. Подробнее — [Сжатие контекста](context-compression.md).

### Карта проекта

Перед планированием строится компактная карта проекта (структура, размеры
файлов, языки — без содержимого), которая подсказывает планировщику разбиение
(`agents/planner/project_map.go`). Крупная работа разбивается на шаги по
5–10 файлов, чтобы каждый помещался в контекст модели.

### Аудит контрактов

`tools/contract.go` снимает снимок публичного API Go-пакета между шагами и
сравнивает. Изменения видны как `+` (добавлено), `-` (удалено), `~`
(изменено подпись). `CODEGEN_CONTRACT_ENFORCE` включает строгий режим.
Реализовано только для Go.

### Аудит изменений

`Snap.Diff()` даёт дайджест (создано/изменено/удалено) с учётом scope и
exclude — попадает в чекпоинт и отчёт.

## Чекпоинты и resume

Чекпоинты включаются **автоматически**, если задан `REDIS_ADDR` (или явно
`PLAN_CHECKPOINT=1`), а также при запросе resume.

Статусы шагов: `pending`, `running`, `done`, `failed`, `skipped`
(`checkpoint/checkpoint.go:22-28`).

```bash
# Прогон прервался — продолжаем с места остановки
go run . plan storageService "Создай микросервис и автотесты" --resume
# или
PLAN_RESUME=1 go run . plan storageService "..."

# При resume планировщик НЕ вызывается — выполненные шаги не переделываются
```

Пакет `checkpoint` намеренно не зависит от типов planner: снимок хранит
план как непрозрачные байты (`PlanJSON`). Это позволяет менять структуру
плана, не ломая старые чекпоинты.

## Честность при сбоях

Если модель не создала код (пустой ответ с `finish_reason=length`), шаг
считается `failed`, и план останавливается с ошибкой — а не «успешно
выполняется без кода».

Исправление — увеличить лимит выходных токенов (`YANDEX_MAX_TOKENS`,
`OLLAMA_OUTPUT_TOKENS`) и повторить через `--resume`.

## Монорепозитории

Когда запрос затрагивает клиент и/или сервер, планировщик строит монорепозиторий
с подкаталогами `frontend/` и `server/`. Шаги назначаются отдельным агентам
и работают только внутри своей директории.

Приёмка монорепо выполняется по подпроектам: отдельная сборка/запуск
фронтенда и бэкенда, отчёт содержит блоки по каждому подпроекту, имена
файлов замечаний с префиксами `frontend/…`, `server/…`.

Статический фронтенд (Vite/React без точки входа для запуска) принимается
по сборке.

## Известные нюансы

- **Устаревший докомментарий:** в комментарии `Executor` сказано, что шаги
  волны выполняются по одному. Фактически `runWave` запускает горутины —
  параллельность включена по умолчанию (`executor.go:36-38` vs `:197-236`).
- **`Run` не сериализован** относительно правок соседнего шага волны.
  Осознанный компромисс (сборка дольше правок). Строгий режим —
  `CODEGEN_PARALLEL=0`.
