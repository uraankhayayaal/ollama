# Агенты и роли

Каждый агент — это системный промпт + набор инструментов + цикл
`runner.Runner`. Различие между агентами в основном в **правах на доске** и в
**том, что им разрешено делать с кодом**.

## Реестр ролей

| Роль | Пакет | CLI-команда | Назначение |
|---|---|---|---|
| Системный архитектор | `agents/architect/` | только через `kanban` / `serve` | Публикует эпики, ревизии, вердикты по багам |
| Backend Lead | `agents/backendlead/` | `backendlead` | Декомпозиция бэкенда |
| Frontend Lead | `agents/frontendlead/` | `frontendlead` | Декомпозиция UI, стейта, API-контрактов |
| DevOps Lead | `agents/devopslead/` | `devopslead` | Декомпозиция инфраструктуры |
| QA Lead | `agents/qalead/` | `qalead` | Тест-план, триаж багов |
| Разработчик | `agents/developer/` | `backend`, `frontend` | Генерация и правка кода |
| DevOps-инженер | `agents/devops/` | `devops` | Docker Compose, K8s, CI/CD |
| QA-инженер | `agents/qaengineer/` | `qa` | Автотесты, баг-репорты |

> `projectFromArgs` они тоже не перечислены (`main.go:391-402`).

## Права на доске

Инструменты `Board*` выдаются **только при подключённом `board.Store`**
(`tools/registry.go:34-36`). Без доски агент автоматически деградирует до
файловых инструментов, а модель не жжёт раунды на заведомо мёртвые вызовы.

| Агент | Эпики | Задачи | Баги |
|---|---|---|---|
| Архитектор | Create / Update / Delete / SetStatus | — | Review |
| Лиды направлений | — | Create / Update / Delete / SetStatus | — (QA Lead: List/Get/SetStatus) |
| Специалисты | — | Get / SetStatus | Create (QA) |
| Чат-ассистент | Create / Update / Delete / SetStatus | SetStatus **только** | Create / SetStatus / Review |
| Ревьюер | — | — | — |

Инструментов правки задач у чат-ассистента нет намеренно (закреплено тестом
`agents/chatassist/agent_test.go:99`): создавать задачи должен лид, иначе
декомпозиция не согласована с архитектурой.

## Обязательные первые раунды

Агенты могут не вызывать инструмент в первом раунде — сначала изучить
структуру (`List` → `ReadFiles`). Но у лидов задан **групп** обязательных
инструментов (`RequiredToolGroups`), а не один:

```go
// agents/backendlead/agent.go:114-124
[]tools.RequiredToolGroup{
    {Tools: []string{"List", "ReadFiles"}},
    {Tools: []string{"ReadMap"}},
}
```

Предварительные чтения и `AskUser` при этом разрешены — трактовка «группы»
меняет только требование к финальному набору, а не запрещает предварительные
чтения.

У архитектора и ассистента первый раунд не ограничен (`{"", false}`).

## Разрыв петли

Раньше зацикливание лечилось только подсказками в промпте (`loopMessage`,
`toolFailMessage`) — модель их часто игнорировала и продолжала повторять один и
тот же вызов до конца лимита раундов. Теперь это жёсткий механизм в
`runner/loop.go` (триггер в `runner.generate`).

Сигналы петли (`LOOP_SIG_REPEATS`, `LOOP_FAIL_STREAK`, `LOOP_NO_WRITE` —
см. [переменные окружения](../30-reference/environment-variables.md)):

| Сигнал | Что означает |
|---|---|
| Повтор сигнатуры | Один и тот же вызов (имя **и** аргументы) 3 раунда подряд |
| Серия неудач | 5 раундов подряд без единого успешного вызова |
| Только чтение | 16 раундов подряд агент изучает проект, но ничего не меняет |
| Неизменное состояние | 3 раунда подряд **одинаковый** вывод падающей проверки, а проект не менялся |

Последний сигнал закрывает дыру сигнатур: агент может каждый раунд делать
формально новый вызов — сдвинуть строки в `ReadFiles`, поменять ключи поиска,
дописать `| tail` к команде. Сравнивать надо не текст вызова, а **саму
проверку**: отпечаток состояния — нормализованная команда проверки
(`runner/loopstate.go:verifyIdentity`), из которой выкинуты конвейер после
первого `|` вместе с флагами (`grep -A5` против `grep -B3 -A20` — та же
проверка), перенаправления потоков и каталог в `cd <dir> &&`. Отпечаток по
выводу проверки не годится: grep показывает разные куски одного и того же
падения, поэтому вывод меняется каждый раунд и маскирует петлю (в этом
убедилась живая петля, где агент раунд за раундом менял только флаги grep).
Нормализованный вывод при этом идёт в **текст вмешательства** как диагноз —
выкинуты ANSI-цвета, абсолютные пути и префиксы временных каталогов, метки
времени, тайминги, номера строк/столбцов и счётчики в скобках
(`runner/loopstate.go:normalizeVerifyOutput`). Успешная правка сбрасывает
отсчёт: падающая проверка после реального изменения — это работа, а не петля.

### Verify guard: принудительное вмешательство

Когда **одна и та же** проверка падает второй раз подряд при неизменном проекте
(`LOOP_STATE_WARN`), харнес вмешивается сам, не дожидаясь разрыва петли
(`LOOP_STATE_REPEATS`). Вмешательство уходит в **следующий** запрос к модели:
после разрыва история схлопывается, и предупреждение, показанное с задержкой,
пропало бы вместе с ней. Отдельно ловится случай «агент правит файлы, а падает
ровно так же» — это порог `LOOP_VERIFY_FAILS` (5 раундов).

- модель получает диагноз — нормализованный текст ошибки и требование сменить
  стратегию: проверить саму проверку (ожидания, асинхронные ожидания, моки,
  снапшоты, окружение, порядок вызовов), а не повторять запуск;
- повторный запуск **этой** проверки блокируется на `LOOP_VERIFY_BLOCK_ROUNDS`
  раундов — раунд не сгорает впустую; блокировка возвращает модели явный отказ
  с объяснением. Блокировка навешена на нормализованную проверку, поэтому смена
  аргументов (`| grep -A5` → `| grep -B3 -A20`) её не обходит;
- блокировка проверки **не обнуляет** отсчёт петли: это решение самого харнеса,
  а не «агент перестал проверять», иначе блокировка вечно обнуляла бы счётчик и
  разрыв петли не наступал бы никогда.

Вмешательство не тратит бюджет разрывов петли: это более мягкий уровень, и оно
может повторяться.

### Санитайз вывода команд

`stdout`/`stderr` нормализуются **до** упаковки в JSON
(`tools/sanitize.go:SanitizeToolOutput`): ANSI-последовательности (цвета,
OSC-гиперссылки), управляющие байты и NUL вычищаются, CRLF приводится к LF.
Без этого escape-последовательности терминала попадали в JSON-пакет, и
разбор аргументов следующих вызовов падал с
`invalid character ']' looking for beginning of value` — то есть харнес ломался
из-за вывода команды.

Разбор аргументов, пришедших от модели, тоже толерантный
(`tools/ParseArguments.go`): висячие запятые, одинарные и «умные» кавычки,
неээкранированные переводы строк внутри строк, ```-обёртки и текст после JSON
чинятся автоматически. Если чинить нечего — вызов не выполняется, а модель
получает требование повторить его с валидным JSON; запуск при этом **не**
падает.

Что происходит при сигнале:

1. **Разрыв петли** — зацикленный хвост истории выбрасывается, а вместо него
   кладётся дайджест: последние вызовы, их аргументы и результат (ошибка или
   усечение до N символов). Системный промпт и исходная постановка задачи
   сохраняются, поэтому модель по-прежнему понимает, что делать.
2. **Перезапуск с чистого листа** — следом в то же сообщение добавляется:
   - **постановка задачи целиком**, напечатанная заново (последним сообщением
     истории, а не в начале — так модель читает её как актуальную);
   - **список уже тронутых файлов** (`path`/`paths`/`files[].filename` из
     аргументов вызовов) с требованием **перечитать их**;
   - прямое требование: первый вызов раунда — чтение этих файлов
     (`ReadFiles`/`ReadMap`, `List` — если не знаешь структуру), и только потом
     работа — но **другим** способом, чем запрещённый вызов.

   Одного запрета мало: модель продолжала «по памяти», не сверяясь ни с
   заданием, ни с реальным содержимым файлов (которое после её же правок уже
   не то, что она видела в начале).
3. **Запрет** — сигнатура повторяющегося вызова (а если перебирались аргументы,
   то весь инструмент — при 100% неудачных вызовах с его стороны) попадает в
   бан-лист, счётчики обнуляются, в промпт уходит императивное указание взять
   задачу с другой стороны, а не «улучшить тот же вызов».
4. **Ставка** (`LOOP_MAX_STRIKES`) — модель может один раз проигнорировать
   запрет. Второй такой вызов завершает запуск досрочно: история не
   сохраняется в checkpoint.
5. **Исчерпаны разрывы** (`LOOP_MAX_BREAKS`) — запуск падает сразу.

Дальше по цепочке:

- `runner.AgentResponse.Looped` / `LoopReason` — отдельный вердикт, не путается
  ни с `Truncated` (контекст закончился), ни с `StopReason`.
- `models/layered.go` — зациклившийся ответ уводит задачу на **большую**
  модель, и resume-состояние сбрасывается: продолжать застрявший диалог
  бессмысленно, крупная модель начинает с чистой истории и того же задания.
- `agents/planner` — если зациклилась и большая модель, запускается
  **эскалация** вместо провала (см. «Эскалация зациклившейся задачи»): задача
  **не** переводится в «выполнена» (раньше неуспешный шаг мог тихо считаться
  выполненным), а код **не** откатывается сам — за него это делает человек.

## Эскалация зациклившейся задачи

Зациклившийся специалист раньше просто ронял запуск. Теперь это
управляемое решение оркестратора (`agents/planner/kanban.go`):

1. Первая петля — задача переключается на **большую модель**
   (`board.ModelTierLarge` в записи задачи; требование переживает следующие
   прогоны, а не живёт один вызов), получает **разбор петли** инъекцией в
   конец блока сообщений и возвращается в очередь.
2. Каждая следующая петля — то же самое, пока не исчерпан бюджет
   `KANBAN_MAX_ESCALATIONS` (по умолчанию 3).
3. Исчерпан бюджет — работа задачи останавливается на паузе («нужен
   человек»), счётчик эскалаций фиксируется, а запуск падает с **этой**
   причиной, а не с «нет прогресса»: иначе человек видел бы сбой системы там,
   где на самом деле нужно его решение.
4. Решения (эскалации, возврат зависших задач) уходят в чат проекта
   статусными сообщениями — их видит человек, а не только доска.
5. Инъекция нормализуется и валидируется перед сохранением: запись без
   `name`/`content` тихо уехала бы в доску и не показалась бы модели.
6. Тот же бюджет считает **«пустую» работу**: гард «phantom done» отклонил
   `done` (нет коммитов и правок) — оркестратор не закрывает задачу и не
   возвращает её в очередь бесплатно, а эскалирует с причиной гарда
   (иначе QAL-01/FEL-04 — бесконечные прогоны без результата, см.
   [troubleshooting](../40-operations/troubleshooting.md#задача-без-результата-крутится-заново-fallback-в-done-отклонён-гардом)).
7. Специалист может остановить задачу сам: `BoardSetTaskStatus` со
   `status=human_help` и обязательным `reason` (задача невыполнима: кода или
   зависимостей нет, внешний блокер). Причина лежит в `pause_reason` задачи
   (карточка UI), а оркестратор **уважает** остановку и отмену от агента
   вместо fallback'а в `done` и вместо эскалации.

Откат кода — ручное действие человека
([откат задачи](gitops-workflow.md#откат-кода-задачи)), а не реакция на петлю:
откатывать историю автоматически опасно — иногда «зациклившийся» агент как раз
тот, кто был близок к результату.

## Возврат зависших задач в очередь

Статус «в работе» ставит хук доски, а снимает его агент. Если сервер или
агент упал посреди прогона, задача остаётся «в работе» навсегда, и следующий
запуск её не видит.

Раз в раунд планировщик (`recoverStuckTasks`) возвращает в очередку задачи
«в работе», у которых heartbeat старше `KANBAN_STALE_TASK_MIN` (30 мин), нет
heartbeat вовсе или он нечитаем. Активные задачи ЭТОГО раннера (`markActive`)
не трогаются — они живы по определению, даже если heartbeat ещё не успел
обновиться. `KANBAN_STALE_TASK_MIN=0` отключает порог: любая задача «в
работе», которую не выполняет этот раннер, возвращается в очередь (разумно
для однопользовательской установки, где параллельных прогонов не бывает).

## Модель для роли

Двухуровневая маршрутизация (`models/layered.go`):

- **Тяжёлая модель** — лиды, архитектор, ревьюер, эксперт по багам, планировщик.
- **Лёгкая модель** — разработчики, DevOps, QA.
- `LLM_ALWAYS_HEAVY=1` — всё через тяжёлую.

## Настройка ролей

### Лиды направлений

```bash
BACKEND_MAX_FILES=0          # лимит файлов за запуск (0 = без)
BACKEND_NO_OVERWRITE=false   # запрет перезаписи существующих файлов
BACKEND_PLAN_FILE=BACKEND_PLAN.json   # куда дублировать JSON-декомпозицию

FRONTEND_MAX_FILES=0
FRONTEND_NO_OVERWRITE=false
FRONTEND_PLAN_FILE=FRONTEND_PLAN.json

DEVOPS_MAX_FILES=0
DEVOPS_NO_OVERWRITE=false

QA_MAX_FILES=0
QA_NO_OVERWRITE=false
QA_REPORT_FILE=TEST_REPORT.md
```

Файл плана (`*_PLAN_FILE`) — отладочный артефакт: та же JSON-декомпозиция,
что ушла в модель, но сохранённая на диск. Пустое значение отключает.

### Общие для кодогенерации

```bash
CODEGEN_LANG=Go              # целевой язык
CODEGEN_MODULE=              # имя модуля для go.mod (пусто — модель придумывает)
CODEGEN_MAX_FILES=0          # лимит файлов за запуск
CODEGEN_NO_OVERWRITE=false   # запрет перезаписи
CODEGEN_SUMMARY_FILE=SUMMARY.md  # отчёт после генерации (пусто — выкл)
```

### RAG-контекст по ролям

```bash
RAG_PLANNER_CONTEXT=1        # вкл по умолчанию
RAG_ARCHITECT_CONTEXT=1      # вкл по умолчанию (нет в .env.example!)
RAG_ASSISTANT_CONTEXT=1      # вкл по умолчанию (нет в .env.example!)
```

Выключаются значением `0` / `false` / `off` / `no`.

### Автопереиндексация

```bash
RAG_AUTO_REINDEX=0           # по умолчанию выключено
```

Когда включено, разработчик после мутаций вызывает `ReindexTouched` —
затронутые файлы переиндексируются в Qdrant, исчезнувшие удаляются
(`runner/reindex.go`). Индексация ветко-осознанная: через
`rag.DetectIndexOptions(OutputDir)`.

Без Qdrant переиндексация молча пропускается — генерация продолжается.

## Как разрабатывать нового агента

1. Создать пакет в `agents/<имя>/` с `agent.go` и `config.go`.
2. Реализовать конструктор, собирающий набор через `tools.Select`.
3. Написать системный промпт.
4. При необходимости — зарегистрировать роль в `main.go` и в
   `projectFromArgs`.
5. Покрыть тестом (паттерн `agent_test.go` у соседних агентов).
6. Обновить документацию по
   [чеклисту добавления фичи](../40-operations/adding-a-feature.md).
