# Чат-ассистент

Агент, обслуживающий чат Web UI: понимает намерения по смыслу, отвечает по
проекту, создаёт эпики, задаёт уточняющие вопросы, выполняет git-операции.

Работает **только** в Web UI (`serve`). Отдельной CLI-команды нет.

## Настройка

```bash
RAG_ASSISTANT_CONTEXT=1    # RAG-контекст ассистента (вкл по умолчанию)
```

> Флага нет в `.env.example`, но он активен по умолчанию
> (`agents/chatassist/ragcontext.go:84-91`). Выключается `0`/`false`/`off`/`no`.

## Поток обработки

`server/chatassist.go:32-94`:

```
Сообщение пользователя
      │
      ▼
runChatAssistant (отдельная горутина)
      │
      ├── Работает в Root зарегистрированного проекта
      ├── Ленивый RAG-клиент
      ├── История диалога: последние 12 реплик, до 400 символов
      ├── Мосты: serverActionTools
      └── Репортер через runevents + runctx.WithCompression
      │
      ▼
Модель решает: ответить / создать эпик / выполнить действие / спросить
      │

```

**Бинарный сплит по ключевым словам убран** — триггером служит вызов
инструмента моделью, а не разбор текста.

## Что попадает в промпт

`server/chatassist.go:287-414`:

- Вопрос пользователя.
- **«Якорь действия»** (`chatActionAnchor:196-251`) — защита от цикла

- Состояние оркестрации: `running` / `gating` / `idle`.
- **Ревизия доски: N** (счётчик `boardRev`) — чтобы ассистент понимал, что

- Исходное ТЗ из `Meta`.
- Эпики и сводка задач по статусам (включая `paused`).
- Список задач «в работе».
- **Блок конфликтов мёрджа** (`:372-395`).
- Баги по статусам.

## Правила поведения

`agents/chatassist/agent.go`:

| Подтверждение | Создание записи — **без** подтверждения (`:59`) |

## Вопросы пользователю (`AskUser`)

`server/ask.go`. Агент может задать пачку структурированных вопросов с
вариантами — UI показывает карточку `AskCard`.

Схема вопроса:

```json
{
  "id": "storage",
  "text": "Какое хранилище использовать?",
  "kind": "single",
  "allow_custom": true,
  "options": [
    {"id": "postgres", "label": "PostgreSQL", "recommended": true},
    {"id": "sqlite", "label": "SQLite"}
  ]
}
```

| Поле | По умолчанию |
|---|---|
| `kind` | `single` (или `multi`) |
| `allow_custom` | `true` |
| `options[].recommended` | — |

Поведение:

- Таймаут ожидания — **15 минут** (`ask.go:115`), затем `context.DeadlineExceeded`.
- Один активный вопрос на сессию; повторный вызов — ошибка (`:213-217`).
- Вопрос публикуется в чат как `role=ask` (`:229`).
- Ответы возвращаются в порядке вопросов (`:279-286`).
- Статус-строка суммирует ответы (`summarizeAsk:315`).

Ответ через REST:

```http
POST /api/projects/{id}/ask/{askID}/answer
```

Клиент: `answerAsk` (`web/src/Api/Api.ts:276`), UI:
`Components/Chatboard/AskCard`.

## Конфликты мёрджа в чате

Если `merge_conflict_files` не пусто, блок конфликтов попадает в промпт
ассистента. Дальше:

- **Конфликт задачи:** `TaskMerge` возвращает детерминированную строку со
  списком файлов и точкой резолва; состояние **не меняется**
  (`server/actions.go:288-299`). Ассистент сообщает пользователю и
  предлагает путь.
- **Конфликт эпика:** ассистент ведёт через `ResolveGitConflicts`
  (status → start → apply), затем `EpicResolve` снимает признак конфликта.

## Разбор логов (`log_analysis`)

Ход, порождённый кнопкой «Разобрать» в панели логов. Пользователь ничего не
писал, поэтому в историю **не добавляется выдуманная реплика** — только
служебная строка статуса «Разбор логов: <файл>».

`server/loganalysis.go` собирает разбор детерминированно: читает те же
файлы, что показывает Logboard (`collectProjectLogs`), применяет фильтры
поиска и минимальной тяжести к строкам **до** группировки, после чего
`buildLogDigest` (`server/logdigest.go`) сворачивает повторы в находки.
В промпт уходит дайджест (`=== РАЗБОР ЛОГА ПРОЕКТА ===`) с явным контрактом
ответа и указанием условий выборки — иначе модель делает выводы по
подмножеству как по всему логу.

Особенности, которые неочевидны:

- **Уровень берётся из собственного тега строки**, а не поиском слова:
  `DETAIL`-строки с `{"level":"ERROR"}` внутри аргументов инструментов иначе
  дали бы массу ложных находок. Эвристика уровня применяется только к
  нетегированным строкам (логи самого приложения пишутся его логгером).
- **Шаблонизация** (`<path>`, `<file>`, `<n>`, `<uuid>`, `<str>`) обязательна:
  без неё один и тот же сбой на тысяче строк даёт тысячу находок.
- **Кадры стека** приклеиваются к находке и переживают фильтр по уровню:
  иначе доказательство ошибки вырезается.
- **Пустой разбор** отвечает детерминированно, без вызова модели.
- **Cooldown 90 с** на неизменившийся лог: два клика подряд не зовут модель
  дважды.

Докапывание — инструментом `ReadProjectLogs` (`server/actions_logs.go`):
логи лежат в `logs/<проект>.log`, то есть **вне** корня рабочей папки,
куда файловые инструменты ассистента (`tools/fileops.go:ResolvePath`) не
пускают, — поэтому нужен серверный мост. Он отдаёт хвост файла (200 строк
по умолчанию, потолок 1000) с необязательным `grep`, и ровно те же файлы,
что видит Logboard: чужие логи проектов и `server.log` не утекают.

## Промпт-инъекции (injections)

Промпт-инъекции — структурированные фрагменты, которые подмешиваются в
запрос к модели в момент его отправки. Ключевое свойство: инъекция применяется
к **следующему** обращению к модели, а не «когда-нибудь потом» и не только к
следующему ходу. Правка инъекций видна и в середине уже идущего цикла
агента, и на resume-сегменте после перезапуска.

### Область действия: конкретная задача

Инъекция задачи принадлежит ровно одной задаче доски и попадает в промпт
ровно её исполнителя. Никакого «глобального» текста, который ушёл бы в чужие
задачи, здесь нет (см. «Источники»).

Два способа задать инъекцию задачи:

```http
POST /api/projects/mytrip/tasks/FEL-02/injections
Content-Type: application/json

{"name": "testify", "target": "system", "content": "ПИШИ ТЕСТЫ НА TESTIFY"}
```

Ответ `201` содержит выданный `id` и полный список инъекций задачи. Дальше —
точечная правка `DELETE .../tasks/FEL-02/injections/{injID}` или полная
замена списка через `PUT /api/projects/mytrip/tasks/FEL-02` с полем
`injections` (полный список ЗАМЕНЯЕТ прежний). Из чата то же делает инструмент
доски `BoardUpdateTask` — то есть фраза «добавь задаче FEL-02 указание
пиши тесты на testify» работает без ручного вызова REST.

### Источники (scope)

Инъекции собираются из источников и применяются в порядке
`global → assistant → session → runtime`; внутри scope — по убыванию
`priority`, при равенстве порядок объявления. Сборка — `injectionSet.collect`
(`runner/injections.go`), применение — `injections.ApplyInjections`.

| Scope | Источник | К кому применяется |
|---|---|---|
| `global` | Зарезервирован в порядке и валидации; **конфига приложения с этим scope пока нет** | — |
| `assistant` | `chatassist.Assistant.Injections` (снапшот на старте хода) | Чат-ассистент |
| `session` | `Session.sessionInjections` + REST API | Текущая сессия проекта |
| `runtime` | `board.Task.Injections` — запись задачи + живое перечитывание | Исполнитель этой задачи |

Два замечания к областям, которые чаще всего понимают неправильно:

- **Сессионные инъекции обслуживают только чат-ассистента.** Агентские прогоны
  (канонический цикл задачи) управляются инъекциями задачи. Сессионная
  инъекция не попадёт в промпт backend-разработчика — и это осознанно:
  «применить к следующему ходу в чате» и «применить к текущей задаче на доске»
  разные области.
- **Сессионные инъекции живут в памяти процесса**, а не в Redis: они видны в
  `wg`/`stop`, но переживают только перезапуск сестри-процесса сервера.
  Инъекции задачи, наоборот, лежат в доске (Redis) вместе с записью задачи и
  переживают всё.

### Когда применяется

Один раз на каждый запрос к модели (`runner/runner.go`, `applyInjections`):

```go
request := applyInjections(messages, round)  // messages — «чистая» история
```

- История `messages` остаётся чистой: применённый текст не «впечатывается» в
  неё, поэтому инъекция не накапливается и не дублируется в следующих раундах.
- Источники читаются **один раз** на запрос. Живой источник ходит в доску, и
  двойное чтение давало бы два разных снимка инъекций в одном промпте.
- **Удаление действует сразу же**, в том числе частичное. Живой источник
  авторитетен: он читает ту же запись, что и стартовый снимок, поэтому
  полностью заменяет снимок, а не дополняет его. Иначе удалённые инъекции
  воскресали бы из снимка и жили до конца прогона. Откат на снимок происходит
  только при ошибке чтения (доска недоступна) — тогда лучше применить прежний
  текст, чем молча выключить инструкцию.
- Fast-path: инъекций нет — промпт собирается как раньше (стоимость для
  существующих агентов нулевая).
- Ошибка пайплайна не роняет цикл: модель получает промпт без инъекций,
  причина уходит в debug-лог.

Инъекции задачи видны модели через **живой источник**
(`board.WithInjectionSource`): агентский цикл перечитывает задачу перед каждым
запросом, а не один раз на старте прогона. Поэтому инъекция, добавленная
через REST или инструмент доски посреди работы агента, применяется к его
следующему запросу.

### Структура инъекции

```json
{
  "id": "chat-rag-disable",
  "name": "disable-chat-rag",
  "scope": "session",
  "target": "system",
  "position": "prepend",
  "content": "RAG-поиск отключён. Не вызывай CodeSearch.",
  "when": "model == \"qwen3:30b\"",
  "enabled": true,
  "priority": 10
}
```

| Поле | Описание | Значения |
|---|---|---|
| `id` | Идентификатор для точечных правок и дедупликации; выдаётся автоматически | строка (32 hex) |
| `name` | Имя (обязательно) | — |
| `scope` | Источник | `global`, `assistant`, `session`, `runtime` (пусто → `runtime`) |
| `target` | Куда вставить | `system`, `messages`, `user_last`, `assistant_last` |
| `position` | Как вставить | `prepend`, `append`, `replace`, `inject_at_index` (пусто → `append`) |
| `index` | Индекс (только для `inject_at_index`) | int ≥ 0 |
| `content` | Тело инъекции (шаблон) | строка, до 10 KB |
| `when` | Условие применения | булево выражение, см. ниже |
| `enabled` | Активна | `true`/`false`; **не указан — активна** (трёхзначно: `nil` = включена) |
| `priority` | Приоритет внутри scope | int (по умолчанию 0, больше — раньше) |
| `vars` | Переменные шаблона | map |
| `tags` | Метки | []string |

Значения `before_tools`/`after_tools` в `target` **не поддерживаются**: принять
их нельзя, иначе запись выглядела бы как применённая, а текст не дошёл бы до
модели. Инъекции с `target: messages` добавляются в историю с ролью `user` —
роль `system` в середине диалога ломает часть провайдеров.

### Валидация

Инъекция проверяется дважды, и оба раза до того, как текст может уйти в
модель:

- **На записи** (REST, инструмент доски, `board.Store`): строгий JSON-декод
  (неизвестное поле — `400`, а не «успех с молча потерянным параметром»),
  затем `Normalize` (дефолты, выдача `id`) и `Validate`. Ошибка — `400`,
  доска не меняется.
- **На применении**: инъекция, не прошедшая валидацию, не роняет цикл, а
  попадает в `MergeResult.Skipped` с причиной и пишется в debug-лог.

Дубли `id` в одном списке — ошибка (`400`). Пустые `scope`/`position` законны и
трактуются как дефолты: минимальная запись `{"name","target","content"}`
валидна.

### API

Сессионные (чат-ассистент):

| Эндпоинт | Что делает |
|---|---|
| `POST /api/projects/{id}/injections` | Добавить (или перезаписать по `id`) — `201` с реальным `id` |
| `DELETE /api/projects/{id}/injections/{injID}` | Удалить по id; чужой id — `404` |
| `GET /api/projects/{id}/injections` | Список (пустой список отдаётся как `[]`, не `null`) |

Инъекции задачи:

| Эндпоинт | Что делает |
|---|---|
| `POST /api/projects/{id}/tasks/{tid}/injections` | Добавить инъекцию к задаче — `201` |
| `DELETE /api/projects/{id}/tasks/{tid}/injections/{injID}` | Удалить; чужой id — `404` |
| `PUT /api/projects/{id}/tasks/{tid}` с `injections` | Полная замена списка |
| `BoardUpdateTask` (инструмент доски) | То же из чата |

Пример:

```http
POST /api/projects/mytrip/injections
Content-Type: application/json

{
  "name": "жёстче-тесты",
  "target": "system",
  "position": "prepend",
  "content": "Покрывай каждое изменение тестом; тест должен падать до фикса."
}
```

`scope` по умолчанию `session`. Повторный POST с тем же `id` правит запись, а
не плодит дубли, — `id` адресует ровно одну запись.

### Условия `when`

Булево выражение без исполнения кода: `==`, `!=`, `<`, `<=`, `>`, `>=`
(последние четыре — только для чисел, то есть практично для `turn`), `&&`,
`||`, `!` и скобки.

Переменные условия заполняются реальными данными прогона: `model`,
`provider`, `role`, `project`, `task_id`, `turn`, `user`, `tools`,
`has_files`. Пустое условие = применять всегда. Неразобранное условие считается
ложным (инъекция пропускается) и попадает в `Skipped` с причиной.

```json
{"when": "role == \"backend\" && turn > \"2\""}
```

### Шаблоны и окружение

`content` поддерживает подстановки: `{{vars.*}}`, `{{env.*}}`,
`{{session.*}}`, `{{assistant.*}}`.

Доступ к окружению закрыт **allowlist'ом**: читаются только переменные с
префиксами `AI_`, `CODEGEN_`, `OLLAMA_`, `KANBAN_` плюс префиксы из
`AI_INJECTION_ENV_ALLOW` (через запятую). Всё остальное окружение шаблону
недоступно: инъекция — это содержимое промпта, и подстановка произвольной
переменной утекала бы секреты в модель и в лог запроса.

- Чувствительное имя (`*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`,
  `*_CREDENTIAL`) запрещено всегда, даже если попало в allowlist по имени, и
  подставляет `[REDACTED]`.
- Переменная вне allowlist подстановку не получает, и плейсхолдер
  `{{env.PATH}}` остаётся в тексте как есть: молча превращать его в пустую
  строку значит незаметно испортить фразу инструкции.

### Ограничения и наблюдаемость

- `MaxContentSize` = 10 KB на инъекцию: обрезка с маркером `[truncated]`.
- `MaxTotalSize` = 50 KB суммарно: при превышении остальные пропускаются, в
  лог уходит предупреждение.
- Debug-лог фиксирует только метаданные — id, имя, scope, target, position и
  причину пропуска (`DescribeApplied`/`DescribeSkipped`). Текст инъекции в лог
  не пишется: в нём могут быть чувствительные строки.
- Действия пользователя (добавление/удаление/замена) пишутся в лог проекта и в
  шину доски: «применится со следующего запроса к модели».

### Пайплайн

```
Assistant.Injections (снапшот хода)  ─┐
Session.sessionInjections (живой)     ─┤
Task.Injections (снапшот + живой)     ─┼→ collect (дедуп по id, last-wins)
                                        │
                                        └→ sort (scope, priority) → validate
                                           → when → render → merge в target
                                              → truncate/лимиты → request к модели
```
