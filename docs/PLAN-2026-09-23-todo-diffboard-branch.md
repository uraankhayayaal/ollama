> решения по ref/vs, worktree и кэшу из этого документа остаются справочными.

Решения: (1) задача по умолчанию `vs=main` + переключатель `vs=ветка-эпика`;

(3) режим «Все изменения» включается в план отдельным этапом (Ф-5).
Формат — как в `PLAN-2026-09-17-wip-webui.md` / `PLAN-2026-09-22-done-dashboard-gitflow-auto.md`.

Дополняет выполненный git-workflow (`PLAN-2026-09-20-done-dashboard-workflow.md`, `PLAN-2026-09-22-done-dashboard-gitflow-auto.md`):
ветки `ai/epic/<id>` / `ai/task/<id>`, worktree задач и авто-мёрджи уже есть, но
панель «Дифф» (Diffboard) о них не знает.

## Проблема (диагноз)

Для git-проектов дифф Diffboard строится как `git add -N -A && git diff <base>` в
**рабочем каталоге основного клона** `temp/<проект>` (ветка `ai/<проект>`),
где `<base>` = `git_base` (main) с момента открытия
(`server/diff.go:50-67`, `gitops/gitops.go:315-327`).

Но с введением git-workflow эпик/задача реальная работа идёт **не в этом клоне**:

- специалисты задач в `in_progress` пишут в **постоянные worktree** веток
  `ai/task/<id>` (`.wt-task-<проект>-<taskID>`, `server/gitflow_auto.go:24-79`);
  `OutputDir` специалиста = worktree задачи (`server/session.go:184-185`);
- изменения задач попадают в **релизные ветки эпиков** `ai/epic/<id>` через
  авто-мёрдж done→релиз (`mergeTaskBranch`, `server/gitflow.go:380`) и авто-коммит;
- основной клон остаётся чистым на `ai/<проект>`.

**Следствие.** Diffboard для проекта с эпиками/задачами показывает пустой дифф
(«Изменений от точки отхода нет») либо только legacy-правки общего клона —
реальные изменения веток эпиков/задач он не видит вовсе. То есть дифф
«не актуальный» именно потому, что работа разнесена по веткам/worktree, а дифф
считается от неподвижной проектной копии.

**Дополнительно найден латентный баг кэша.** `gitProjectDiff` возвращает
закешированный `cachedDiff` (`server/diff.go:53`) и пересоздаётся только при
reject (`server/git.go:396`, `server/actions.go:258-260`), а комментарий
(`server/diff.go:47-49`) обещает пересоздание на каждый запрос списка. Даже
правки агента в самом клоне могут не отражаться между открытиями диффа.

## Цель

Показывать в Diffboard дифф **выбранной ветки** (эпик / задача / проектная
рабочая копия) относительно **главной ветки** (`git_base` = main) с учётом
незакоммиченных правок worktree задачи. Diffboard «привязывается к ветке»: то,
что человек видит в диффе, — ровно то, что принесёт релиз этой ветки в main.

## Решения (предложения)

### Решение 1. Дифф выбранной ветки против main (рекомендуется)

`GET /api/projects/{id}/diff` дополняется параметрами `?ref=<ветка>` и
`?vs=<точка сравнения>`; без них поведение не меняется (проектная ветка
`ai/<проект>` против main — текущий контракт).

- Список доступных `ref`: проектная ветка `ai/<проект>` (по умолчанию) + каждая
  ветка эпика `ai/epic/<id>` + каждая ветка задачи `ai/task/<id>` (из side-реестра
  `workspace.GitBranches`, `workspace/branches.go:29-32`).
- Резолв ref → каталог и семантика:
  - ветка задачи **с зарегистрированным worktree** (`BranchRef.Worktree`): команды
    выполнять в worktree, включать незакоммиченные правки специалиста —
    `git add -N -A` + `git diff <MB>`, где `MB = merge-base(vs, HEAD)`. Это ровно
    то, что на done закоммитит `commitTaskWorktree` (`server/gitflow_auto.go:96`);
  - ветка **без worktree** (эпик, задачи done/не взятые в работу): только коммиты —
    `git diff <vs>...<ref>` (three-dot, вклад от merge-base) в основном клоне,
    рабочий каталог клона не участвует;
  - проектная ветка (ref пуст / не распознан): legacy-поведение (рабочий каталог
    клона), но с тем же улучшением через merge-base.
- `vs` по умолчанию = `git_base` (main): дифф показывает всё, что придет в main
  при «Залить в main»/MR эпика. Для задач — переключатель `vs=ветка-эпика`,
  чтобы видеть **только свою часть** без изменений эпика (т.к. ветка задачи
  отходит от релизной ветки, three-dot против main включит и изменения эпика).
  По умолчанию (решение принято) — `vs=main`, переключатель рядом в UI.
- Three-dot (`...`) выбран принципиально: показывается вклад ветки от общего
  предка, без «обратного» шума от движения main после точки отхода
  (см. `git diff A` — «рабочая копия vs A», которая ломается, если main ушёл
  вперёд).

### Решение 2. Починка кэша диффа

Ключ кэша расширяется до `(project, ref, vs)`; список файлов **пересоздаётся на
каждый запрос списка** (как задумано комментарием `server/diff.go:47-49`), патчи
конкретных файлов отдаются из последнего разбора (ленивая загрузка `?file=` не
меняется). Инвалидация при accept/reject/release/merge/создании ветки.

### Решение 3. Нет нового REST-маршрута

Список веток отдаётся внутри ответа диффа (`refs`): label «Проект ai/<имя>»,
«Эпик <заголовок> (ai/epic/<id>)», «Задача <заголовок> (ai/task/<id>)», признак
«идёт работа в worktree», точку сравнения `vs`. Фронт не ходит вторым запросом.

### Решение 4. Действия по выбранной ветке (отдельный этап, не первая волна)

Кнопки «Принять → MR» / «Отклонить ветку» сейчас привязаны к проектной ветке
(`server/git.go:297-406`). **Первая волна (решение принято)** — только просмотр
диффа выбранной ветки; accept/reject остаются у проектной ветки как сейчас.
Позже (опция): перенаправить на существующие действия «Создать MR эпика/задачи»
(`createEpicMR`/`createTaskMR`), «Залить в main» (`releaseEpic`) и аналог
«Отклонить ветку».

### Решение 5. Режим «Всё» (включён в план, этап Ф-5)

Агрегированный дифф «все ветки эпиков против main» одним списком — для общего
ревью без переключения. Дополняет Решение 1, а не заменяет. Реализация:
суммарный перечень изменённых файлов по всем релизным веткам эпиков относительно
main (патч каждого файла — от ветки, несущей изменения); при конфликте
нескольких веток на одном файле — перечислить оба варианта с меткой ветки.

## API (дополнения к существующему)

```
GET /api/projects/{id}/diff                            — legacy: проектная ветка ai/<проект> vs main
GET /api/projects/{id}/diff?ref=ai/epic/<eid>[&vs=main]
GET /api/projects/{id}/diff?ref=ai/task/<tid>[&vs=main|ai/epic/<eid>]

Ответ (git): { kind:"git", branch, vs, base(факт. точка сравнения), remote,
               refs:[{branch,label,kind,vs,worktree?}, ...], files:[...] }
```

## Этапы и чеклист

### Ф-1 — Сервер: примитивы gitops
- [ ] `gitops.DiffIn(ctx, dir, vs, ref)` — работа с явным каталогом (worktree/клон),
      merge-base + опционально незакоммиченные (`git add -N -A`)
- [ ] `gitops.DiffTree(ctx, vs, ref)` — three-dot по коммитам
- [ ] hermetic-тесты fake-исполнителя (merge-base / add -N / diff) + real-git E2E

### Ф-2 — Сервер: REST с ref/vs и починка кэша
- [ ] `handleGetDiff`: чтение `?ref`/`?vs`; дефолт = проектная ветка (контракт не ломается)
- [ ] резолв ref → (каталог, семантика) через `workspace.GitBranchMap` + `BranchRef.Worktree`
- [ ] ключ кэша `(project, ref, vs)`; список пересоздаётся на каждый запрос списка;
      патчи из последнего разбора; инвалидация accept/reject/release/merge/ветка
- [ ] `refs` в ответе (label из доски: заголовки эпика/задачи)
- [ ] hermetic-тесты: эпик vs main; задача+worktree (вкл. dirty); задача vs эпик;
      ветка без коммитов; несуществующая ref (400)

### Ф-3 — Web: селектор веток в Diffboard
- [ ] `Types.ts`: `DiffRef`, `DiffView.refs`
- [ ] `Api.ts`: `projectDiff(project, ref?, vs?)`
- [ ] `Diffboard.tsx`: селектор (проект / эпики / задачи), перезагрузка, шапка
      «branch → vs», пометка работы в worktree, empty-state («коммитов ещё нет»)
- [ ] `App.tsx`: опции из `board.git` + meta
- [ ] `npm run build`

### Ф-4 — Верификация
- [ ] `go build/vet/test` (перечень AGENTS.md) + `npm run build`
- [ ] ручной E2E на реальном git-проекте: специалист пишет в worktree →
      Diffboard показывает дифф задачи против main; у эпика — дифф против main;
      legacy-проект без эпиков — поведение не изменилось

### Ф-5 — Режим «Все изменения» (решение принято: включён)
- [ ] `GET /diff?ref=all` (или переключатель «Всё» в селекторе): суммарный перечень
      файлов по релизным веткам эпиков против main
- [ ] патч файла от ветки-владельца; файл из нескольких веток — обе опции с меткой
- [ ] UI: режим «Всё» рядом с per-веткой; `npm run build`
- [ ] hermetic-тесты агрегации (два эпика, пересечение файлов)
