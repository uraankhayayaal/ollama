Вот подробный план внедрения Qdrant в проект uraankhayayaal/ollama для создания контекстной памяти (RAG) ИИ-агентов, оформленный в удобном для интеграции Markdown-формате.
------------------------------
## План внедрения Qdrant (Архитектура RAG для ИИ-агентов)## 🏗️ Этап 1: Инфраструктура и окружение
Цель: Подготовить базу данных и среду для работы с векторами.

* Настройка Docker Compose
* В существующем файле compose.yaml убедиться в наличии и активности сервиса qdrant.
   * Зафиксировать gRPC-порт 6334 (он работает в разы быстрее, чем HTTP 6333).
* Конфигурация переменных среды (.env)
* Добавить новые параметры для связи с БД и моделью эмбеддингов:
   
   QDRANT_ADDR=localhost:6334
   EMBEDDING_MODEL=nomic-embed-text # или qwen3-coder с поддержкой эмбеддингов
   QDRANT_COLLECTION_NAME=project_code_base
   
   * Инициализация коллекции при старте
* Написать функцию инициализации в main.go или отдельном пакете checkpoint/qdrant.go.
   * При запуске проверять наличие коллекции project_code_base. Если её нет — создавать программно через client.CreateCollection с метрикой косинусного сходства (Distance_Cosine).

------------------------------
## ✂️ Этап 2: Конвейер индексации (Chunking & Embedding)
Цель: Научить систему разбивать исходный код на смысловые части, переводить их в векторы и сохранять.

* Создание модуля разделения кода (Chunking)
* Создать инструмент в tools/ для нарезки файлов на чанки.
   * Стратегия нарезки: Не просто резать по количеству символов, а учитывать структуру кода. Один чанк должен содержать законченную функцию, метод или структуру со всеми сопутствующими комментариями (go/ast для Go или построчный парсинг для других языков с лимитом ~50-100 строк на чанк).
* Генерация эмбеддингов через Ollama
* Написать хелпер, отправляющий POST-запрос на /api/embeddings локальной Ollama.
   * Функция принимает текст чанка, а возвращает массив []float32 (размерность зависит от модели, обычно 768 или 1024).
* Проектирование Payload (Метаданных)
* Для каждой точки (Point) в Qdrant сформировать структуру метаданных для последующей фильтрации:
   
   {
     "file_path": "server/internal/storage/service.go",
     "start_line": 45,
     "end_line": 90,
     "code_content": "func (s *Service) SaveFile(...) { ... }",
     "scope": "server"
   }
   
   
------------------------------
## ⌨️ Этап 3: Команда индексации (go run . index)
Цель: Создать CLI-инструмент для первичного «обучения» агента на существующей кодовой базе.

* Реализация CLI-команды index
* Добавить обработку нового аргумента командной строки по аналогии с backend/frontend/plan.
* Логика работы воркера индексации:
1. Рекурсивно сканировать дерево файлов проекта (используя существующую логику List).
   2. Игнорировать бинарные файлы, .git, node_modules и файлы, указанные в .gitignore.
   3. Передавать валидные текстовые файлы в модуль Chunking, генерировать векторы и загружать пакетно (Upper/Upsert) в Qdrant.
* Авто-обновление при изменении кода
* Внедрить триггер в цикл авто-самоисправления (Ф-2). Как только агент-разработчик успешно применил WriteFiles или SearchReplace, запускать частичную переиндексацию — удалять старые векторы измененного файла и записывать новые.

------------------------------
## 🤖 Этап 4: Интеграция в инструменты ИИ-агентов (Retrieval)
Цель: Предоставить агентам возможность семантического поиска по коду вместо чтения всех файлов подряд.

* Создание инструмента CodeSearch для субагентов
* Добавить новый инструмент в пул разработчиков (Бэкендера и Фронтендера).
   * Входной параметр: query (строка, например: "где валидируется токен сессии").
   * Логика работы: Инструмент векторизует запрос пользователя -> отправляет в Qdrant через семантический поиск -> возвращает топ-3 релевантных кусков кода с указанием файлов и строк.
* Интеграция в Агента-Планировщика (plan)
* Перед тем как планировщик построит JSON-карту этапов, расширить его системный промпт. В дополнение к компактной «карте проекта» (дереву файлов) делать быстрый поиск в Qdrant по тексту глобальной задачи пользователя и подмешивать точные куски релевантного кода прямо в контекст планирования.
* Настройка жестких фильтров по Scope
* При вызове CodeSearch бэкенд-агентом автоматически подставлять фильтр Qdrant Filter{ Must: []Condition{...} }, ограничивающий поиск только файлами из папки server/. Для фронтенд-агента — только из frontend/. Это исключит «галлюцинации» и подмешивание чужого кода.

------------------------------
## ⚙️ Этап 5: Оптимизация и защита контекста
Цель: Предотвратить падения из-за переполнения памяти и лимитов токенов.

* Контроль размера выдачи
* Ввести новые лимиты в конфигурацию по умолчанию:
   
   RAG_MAX_RESULTS=3 # сколько чанков возвращать за раз
   RAG_READ_MAX_TOTAL=150000 # символьный лимит текста из кэша Qdrant
   
   * Интеграция с KV-кэшем модели
* Использовать оптимизацию OLLAMA_KV_CACHE_TYPE=q8_0 для длинных сессий, так как RAG-поиск будет постоянно дописывать новые контекстные куски кода в историю диалога субагентов.
