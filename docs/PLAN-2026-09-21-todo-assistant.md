# План: «умный ассистент» — намерения по смыслу, RAG, действия на сайте

Статус: **ПЛАН (реализация позже)**. Формат — как остальные `PLAN-*.md`:
решения пользователя, решения архитектуры, привязка к текущему коду
(`file:line`), этапы с чекбоксами, верификация. Обновлять файл по мере
выполнения (чекбоксы `[x]`), статус менять на «реализовано» только после
зелёной верификации.

## Цель

Превратить текущий чат из двух режимов, включаемых по ключевым словам
(«создай эпик/задачу…» vs «всё остальное»), в **единого умного ассистента**,
который понимает намерение пользователя **по смыслу, а не по словам**:

1. Понимает, что нужно создать эпик/задачу/таску из любого осмысленного
   сообщения («заведи эпик "порт на Rust"», «хочу канбан на рефакторинг
   сервера», «надо бы завести баг с тормозами»).
2. Отвечает на любые вопросы — от состояния проекта (RAG + доска) до
   новостей и общих тем, уточняя живую информацию в интернете через
   `WebSearch` (+ знания модели), честно сообщая о живых/нежилых данных.
   Погода — лишь частный пример такого запроса: отдельный инструмент для
   неё не нужен, достаточно общего поиска в сети.
3. Хорошо знает текущий проект: семантический поиск по коду (RAG-контекст
   в промпте + инструмент `CodeSearch`), LSP, карта файлов; подсказывает
   лучшее решение и **задаёт уточняющие вопросы** при неоднозначности.
4. **Совершает действия вместо пользователя**: создаёт эпик/задачу, двигает
   статусы, заводит баги, запускает канбан, удаляет задачу, откатывает
   изменения (reject-branch), мёрджит задачу, релизит эпик в main.
5. Деструктивные операции выполняет **только после явного подтверждения**
   пользователем в чате; об этой границе ассистент рассказывает сам.

## Решения пользователя (зафиксировано)

1. Подтверждение деструктивных действий — **всегда спрашивать в чате**:
   ассистент предлагает действие и ждёт явного «да/подтверждаю» из чата,
   потом выполняет через инструмент.
2. Живая информация из интернета — **опциональный `WebSearch`** (DuckDuckGo,
   без API-ключа) для любых запросов на уточнение (новости, факты, справка;
   погода — лишь частный пример, отдельный инструмент не нужен). Если
   сеть/инструмент недоступны — ассистент отвечает из знаний модели и
   честно говорит, что данные не живые.
3. Набор действий — **максимум**: всё, что уже умеют REST/канбан
   (создание/удаление/статусы эпиков, задач, багов; запуск канбана;
   reject-branch; release в main; merge задачи). Файлы проекта руками
   ассистент **не правит** — этим занимаются агенты через Kanban.

## Архитектурные решения

### Р-1: один ассистент вместо бинарного сплита
Убираем `isChatTaskRequest`/`taskRequestPhrases`. Любое сообщение идёт в
`runChatAssist` (название → `runChatAssistant`), где единый агент **сам по
смыслу** решает: создать эпик/задачу (инструменты Board*), завести баг,
просто ответить, спросить уточнение. Решение принимает модель, а не
регэкспеп. Триггер «класть эпик на доску» больше не эвристика — это вызов
инструмента `BoardCreateEpic` моделью.

Примечание: сообщения вида «задача: …» продолжают работать (модель поймёт
приказной тон), но это лишь следствие семантики, а не маркер-сплит.

### Р-2: ассистент получает write-инструменты + RAG + WebSearch
- `assistantToolNames` расширяется: Board-записи (Create/Update/Delete/Status
  эпиков, задач, багов) + `CodeSearch` (RAG) + `ResolveGitConflicts`
  (для git-проектов, требует `GitExec`) + `WebSearch` + новый
  server-мост `*Action` (ниже).
- `assistantSystemPrompt` переписывается: read-only-ограничение уходит,
  добавляются правила подтверждения деструктивных действий (удаление,
  reject-branch, release, merge) и правило «задавай уточняющие вопросы при
  неоднозначности» (спрашивай, а не угадывай).
- В промпт ассистента добавляется RAG-блок по вопросу (`ragProjectBlock`-стиль
  из `agents/planner/ragcontext.go:54`), чтобы он «знал» релевантный код не
  только через инструменты, но и из контекста первого ответа.

### Р-3: безопасность деструктивных действий
Двухступенчатая схема **без новых инфраструктурных гейтов**:
1. Промпт: перед удалением/reject/release/merge ассистент спрашивает в чате
   «Подтвердите: ...? (да/нет)» — это обычное текстовое сообщение.
2. Получив «да/подтверждаю/ок/делай» → ассистент вызывает инструмент.
   Псевдо-инструмент `ConfirmAction` НЕ нужен: подтверждение живёт в тексте
   чата, а серверный мост `*Action` выполняет действие после вызова моделью.
   (Опционально, Ф-6: жёсткая CLI-кнопка «разрешить ассистенту деструктив» —
   но не обязательно.)

### Р-4: мост к серверным git/канбан-действиям
Инструменты вида `server/*.go` (пакет `tools`), которые через
расширенные `Deps` получают серверные примитивы:
- `KanbanStart` → `POST /api/projects/{id}/continue` (`sess.continue`,
  `server/server.go:600`) — запустить канбан по эпику/задаче.
- `TaskMerge` → `.../tasks/{tid}/merge` (`gitflow.go:198`) — влить задачу в релиз.
- `EpicRelease` → `.../epics/{eid}/release` (`gitflow.go`) — «Залить в main».
- `BranchReject` → `POST .../reject-branch` (`server/git.go:382`) — откат
  фича-ветки.
Каждый требует явного подтверждения из Р-3.

Инжей посредники: `server/chatassist.go` строит ассистента с
`tools.Deps{FileOps, Board, RAG, GitExec}` + серверные actions. Сервер владеет
`*rag.ClientSafe` (как планировщик, `agents/planner/planner.go:38`) и
`gitops.Executor` — передаёт их в набор ассистента.

## Интеграции с существующим кодом

- **`tools.Deps`** (`tools/tool.go:33-38`) уже имеет `RAG *rag.Client` и
  `GitExec` — заполняем их в `server/chatassist.go:67`. Интерфейс
  `tools.Tool`/`Set.Execute` (`tools/registry.go:50-65`) переиспользуется
  без изменения.
- **`agents/chatassist`** — расширяем список инструментов и промпт, интерфейс
  агента (GetTools/CallFunction) не меняется; runner (`runner/runner.go:444`)
  уже умеет цикл инструментов — ассистент станет «исполнителем» через тот же
  цикл, что и остальные агенты (сейчас `runChatAssist` делает один проход —
  переводим на `runner.Generate`-подобный цикл с инструментами, см. Ф-2).
- **`board/store.go`** — уже готово, правок не нужно.
- **REST** — новые маршруты не нужны (release/merge/reject/continue уже есть);
  единственный недочёт — **нет REST для удаления отдельной задачи**
  (`board.DeleteTask` `:417` есть, маршрута нет): добавим
  `DELETE /api/projects/{id}/tasks/{tid}` под `authHandler` (мутация → CSRF,
  `server/server.go:150`), чтобы инструмент `BoardDeleteTask` мог выполниться
  по-человечески и через REST (для веб-кнопок/тестов).
- **WS** — не требуется; действия через уже существующие `sess.kickBoard`/
  WS-board события (`server/session.go:394`, `boardFlusher`).

## API (изменения)

```
DELETE /api/projects/{id}/tasks/{tid}   — удалить задачу (обращение к board.DeleteTask)
```

вызывает через runner, сервер выполняет существующие хендлеры.
