# Анализ: как работает доска с эпиками, задачами, ролями и gitflow

**Тип:** анализ + рекомендации (без пунктов для выполнения).

## Текущая архитектура доски

Доска хранится в Redis (`board/store.go`), привязана к проекту. Ключевые
сущности:

| Сущность | Описание |
|---|---|
| `board.Meta` | метаданные проекта: `Task` (текст задачи), `Status` (in_progress / done) |
| `board.Epic` | эпик: `TaskID`, `Title`, `Description`, `AssignedRole` (к какому лиду), `Tasks []string` (список задач), `Status`, `Revision` / `LeadSyncedRev` (ревизия vs синхронизация лида), `ArchitectureSummary`, `SequenceOrder`, `CanRunParallel`, `Dependencies` |
| `board.Task` | задача: `TaskID`, `Title`, `Description`, `AssignedRole` → `Assignee`, `EpicID`, `Status`, `SequenceOrder`, `CanRunParallel`, `Dependencies`, `GitBranch` |
| `board.BugReport` | баг-репорт: `BugID`, `Title`, `Description`, `TaskID`, `EpicID`, `Status`, `ReporterRole`, `Verdict`, `FixEpicID` |

Статусы (единые для эпика/задачи, `board/entity.go`):
`new → analysis → ready → in_progress → done | cancelled`
(переходы валидирует `ValidateTransition`).

## Кто создаёт и управляет

| Роль | Где создаёт | Что делает |
|---|---|---|
| **Системный архитектор** | оркестратор (`agents/planner/kanban.go` → `phaseArchitect`) | создаёт эпики; по умолчанию — только при запуске из чата (не board-only) |
| **Лид направления** (backendlead/frontendlead/devopslead/qalead) | оркестратор → `phaseLeads` | декомпозирует/обновляет задачи в эпике; ревизует при `Revision > LeadSyncedRev` |
| **Специалист** (developer/devops/qaengineer) | оркестратор → `phaseExecute` | выполняет задачу (пишет код); ставит `done` |
| **Ассистент** (чат) | `server/chatassist.go` | по смыслу сообщения пользователя: создаёт эпики/задачи/баги или отвечает; работает в board-only при нажатии «Продолжить» |

> **Примечание об «аналитиках»**: в коде отдельной роли «аналитик» нет.
> Статус `analysis` у задач — это этап в конечном автомате (задача «в анализе»,
> готовится к работе). Анализом занимаются архитектор (при создании эпика)
> и лид (при разбиении эпика на задачи). Если под «аналитиком» подразумевается
> отдельный процесс/роль, его нужно спроектировать.

## Git-flow (текущее)

Реализовано в `PLAN-dashboard-workflow.md` (Ф-1..Ф-5, все выполнено) и
дополняется `PLAN-dashboard-gitflow-auto.md`.

- **Эпик** = релизная ветка `ai/epic/<epic_id>` (база = `main`).
- **Задача** = фича-ветка `ai/task/<task_id>` (база = релизная ветка эпика).
- Создание веток: **ручное** через кнопку в модалке эпика/задачи
  (`POST .../branch`, `server/gitflow.go:47,111`). Авто-создания пока нет.
- **Выполнение задачи** — специалист работает в рабочей копии клона
  (`temp/<имя>`, текущая ветка = проектная feature-ветка `ai/<имя>`),
  **не** в ветке задачи. Коммит на ветке задачи не создаётся автоматически.
- **done → авто-мёрдж** ветки задачи в релизную ветку эпика
  (`board.Store.TaskDoneHook`, `server/gitflow.go:442`). При конфликте —
  лог-предупреждение, ручной резолв через `tools/gitresolve.go`.
- **«Залить в main»**: кнопка у эпика со статусом `done`
  (`handleReleaseEpic`, `server/gitflow.go:254`); если конфликт с main —
  `releaseEpic` → 409, ручной резолв через `.../rebase` → авто-инструмент
  `ResolveGitConflicts` → обязательная приёмка → финальный merge.
- **MR/PR**: кнопка «Создать MR» в модалках (MR задачи → ветка эпика,
  MR эпика → main). Ссылки в side-реестре `workspace.Info.GitBranches`;
  сверка с форджем в фоне (гидридный опрос, `server/gitflow_mr.go:350`).

## Текущие болевые точки

1. **Ручное создание веток** — задержка между эпиком/задачей и возможностью
   коммитить (кнопка «Создать ветку»). Нет автоматизации «ветка создалась
   при создании записи на доске».
2. **Коммиты попадают не в ветку задачи** — специалист пишет в общий клон
   (`ai/<имя>`), а не в `ai/task/<id>`. Результат: авто-мёрдж
   (done→merge)ливает пустую или неактуальную ветку задачи.
3. **Кнопка «Создать MR»** показывается всегда при наличии ветки,
   даже если коммитов нет — бесполезный серверный запрос.
4. **Релизная ветка может отклоняться от main** — если main двигалась после
   создания ветки эпика, клик «Залить в main» упирается в 409; резолв
   ручной (через инструмент, но пользователь не знает, что конфликт «на подходе»).
5. **Механизм «kickBoard»** — рассылка снимков доски分散о в ~10+ местах кода,
   каждый вызывает `sess.kickBoard()` напрямую; связь «доска↔чат» реализована
   через публикации в шину, но без явного контракта на события.

## Рекомендации

### Сохранить эпики как единицу

Эпик в текущей системе — это **релизная ветка + контейнер задач**. Отказываться
от эпика не стоит, потому что:
- Git-flow жёстко привязан к понятию «релизная ветка» → эпик — естественный
  агрегатор;
- Модель «архитектор → лид → специалист» масштабируется именно через
  эпики (направления: инфраструктура / приложение / тестирование).

### Что можно улучшить

| Рекомендация | Причина |
|---|---|
| **Авто-создание веток** (хуки в `board.Store`) | снять ручную задержку; кнопки оставить как страховку |
| **Worktree-изоляция специалиста** (git worktree на ветке задачи) | коммиты попадают куда нужно; авто-мёрдж becomes нативным |
| **«Единый тикер» для сессии** (event/listener шина) | заменить разрозненные `kickBoard` на централизованную событийную модель |
| **Периодический синхрон релизной ветки с main** | кнопка «Залить в main» всегда без конфликтов |
| **Признак `has_commits` в git-статусе доски** | MR-кнопка не дёргает сервер без нужды |
| **Отдельная роль/процесс «аналитик»** (если нужен) | статус `analysis` существует, но отдельной роли в агентах нет; при необходимости — добавить агента-аналитика между архитектором и лидом, который структурирует вход перед декомпозицией |
| **Вынести обязательные параметры эпика/задачи из промпта в схему** | текущий ассистент чата заполняет поля по своему усмотрению; жёсткая схема с валидацией снижает мусор |

### Отдельное замечание по «отменённым» записям

В доске статус `cancelled` не удаляет запись физически — это правильное решение
(сохраняет хронологию). Однако «новая» (board-only, без архитектора)
задача без эпика создаётся ассистентом через `BoardCreateTask` с обязательным
`epic_id` — без эпика задачу создать нельзя. Если нужно «быстрое поручение
без эпика», стоит рассмотреть флаг `epic_id = ""` или отдельный тип сущности.

## Итого

Код доски, эпиков/задач, лидов/специалистов и git-flow тесно связан, но
масштабируем. Ключевые узкие места (ветки-вручную, коммиты не в ветке задачи,
kickBoard-рассылка) решаемы, и рекомендации выше описывают, как это сделать
без слома существующего флоу.
