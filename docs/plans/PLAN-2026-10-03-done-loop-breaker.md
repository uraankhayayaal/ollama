# PLAN-2026-10-03 — Разрыв петли агента (loop breaker)

**Статус:** выполнено.

## Проблема

Агент не понял свою ошибку и зациклился: повторял один и тот же вызов, пока не
выбрался лимит раундов. Помощь выглядела как тихий перебор бюджета — работа не
делалась, но запуск формально шёл.

Причина в коде: единственная защита от повторов — мягкие подсказки в промпт
(`loopMessage`, `toolFailMessage`). Дальше по цепочке любой неуспешный ответ
шага считался «шаг завершён» либо тихо проглатывался, а `LayeredProvider`
поднимал на большую модель только ошибку и `Truncated`, но не петлю.

## Решение (выбрано пользователем)

1. Детектор петли с **разрывом** вместо очередной подсказки.
2. **Эскалация** на большую модель, когда маленькая зациклилась.
3. **Честный фейл**, если зациклилась и большая: задача не помечается
   выполненной, запуск падает.
4. Лимит раундов (`REVIEW_MAX_ROUNDS` и прочие) не трогаем — петля рвётся
   независимо от него.

## Что сделано

### `runner/loop.go` (новый файл)

- `loopConfig` — пороги из окружения с дефолтами.
- `loopDetector`:
  - сигнатуры вызовов (`callSignature(name, args)`) и серии раундов;
  - `sigRound` — повтор одной сигнатуры (`LOOP_SIG_REPEATS`);
  - `failStreak` — раунды без успешного вызова (`LOOP_FAIL_STREAK`);
  - `noWrite` — раунды без мутации, где нужен write (`LOOP_NO_WRITE`),
    чтение определяется через `tools.IsParallelSafe`;
  - `ban` (сигнатуры и инструменты) и `strikes` (`LOOP_MAX_STRIKES`);
  - `progressIdx` — точка последнего реального продвижения, до которой
    схлопывается история.
- `breakLoop` — схлопывает хвост, сохраняя system/user, добавляет дайджест
  последних вызовов (`LOOP_DIGEST_MAX`) и императивное указание сменить подход.
- `loopBreakMessage` — дайджест + запрет + требование нужного действия.
- `loopRestartMessage`, `loopTaskStatement`, `loopCallPaths`, `touchedFiles` —
  перезапуск с чистого листа: постановка задачи печатается заново последним
  сообщением, а уже тронутые файлы (пути из аргументов вызовов) предлагается
  перечитать; первый вызов раунда обязан быть чтением.

### `runner/runner.go`

- `AgentResponse.Looped`, `AgentResponse.LoopReason`;
  `StopReason()` и `LoopError(prefix)`.
- `WithoutResumeState(ctx)` — снять resume-историю (нужно эскалации).
- Учёт вызовов раунда, `progressPoint`, `markLoopCall`, бан листа и ставочный
  подсчёт; при нарушении запрета — немедленный `Looped`.
- Разрыв петли срабатывает **до** мягких подсказок: если история уже
  схлопнута, повторный сигнал не тратит бюджет раундов.
- После разрыва модель не просто «не повторяет запрещённое», а начинает задачу
  заново: постановка печатается заново (последним сообщением — иначе она
  далеко в начале длинной истории), файлы, которые агент уже менял,
  перечисляются для перечитывания, и первым действием требуется чтение.

### `models/layered.go`

- `Looped` поднимает задачу на большую модель (как ошибка и `Truncated`),
  причём `runner.WithoutResumeState(ctx)`: продолжать застрявший диалог нельзя.
- Если зациклилась большая модель, её вердикт уходит наружу как `Looped`.

### `agents/planner`

- `kanban.go`: архитектор, ревью эпика, лид, специалист, триаж, эксперт по
  багам — зацикливание = ошибка запуска, а не «шаг сделан».
- `executor.go`: для looped-шагов не сохраняется round-состояние (resume),
  `truncatedStepError` вынесен в общий хелпер.

### `tools` (новое поведение для всех агентов)

- `tools/sanitize.go` (новый файл) — санитайз вывода команд; вызывается из
  `fileops.go` (`runCommandSandbox`), потому что `runner` импортирует `tools`,
  а наоборот — нет.
- `ParseArguments.go` — толерантный разбор аргументов от модели; нечинимый
  вызов больше не роняет запуск, а возвращается модели требованием повторить
  его с валидным JSON.

## Дополнение: петля по состоянию, verify guard, санитайз

Первая версия фиксировала петлю по сигнатурам вызовов. На живой жалобе этого
оказалось мало: агент каждый раунд делал **формально новый** вызов — сдвигал
строки в `ReadFiles`, менял ключи поиска, дописывал `| tail` к команде, — и
сигнатуры не повторялись.

### 1. Отпечаток состояния: проверка, а не её вывод (`runner/loopstate.go`)

Петля — это не повтор вызова, а отсутствие изменений. Ключ отпечатка — сама
проверка: `cd <каталог> && npm test src/pages/Login.test.tsx` с отброшенным
конвейером после первого `|` (grep/tail/head вместе с флагами),
перенаправлениями потоков и каталогом. Отпечаток накапливается ПО ПРОВЕРКЕ, а не
по «последней проверке раунда»: чередование двух падающих проверок не должно
обнулять отсчёт каждой.

Почему не вывод (это выяснила живая петля, а не рассуждение): агент раунд за
раундом гонял одну и ту же падающую проверку, меняя только фильтр вывода —

```
npm test src/pages/Login.test.tsx 2>&1 | grep -B5 -A30 "FAIL|Error"
npm test src/pages/Login.test.tsx 2>&1 | grep -A5 "stderr"
npm test src/pages/Login.test.tsx 2>&1 | grep -i "console|warn"
npm test src/pages/Login.test.tsx 2>&1 | grep -B3 -A20 "stderr"
```

— и отпечаток по нормализованному выводу менялся каждый раунд, потому что grep
печатает РАЗНЫЕ куски одного и того же падения. Такой отпечаток обходится за
секунду. Нормализованный вывод остался, но в другом месте: это ДИАГНОЗ в тексте
вмешательства (умеет ли проверка вообще, асинхронные ожидания, JSDOM вместо
`window.location`).

Тот же отпечаток `LOOP_STATE_REPEATS` раундов подряд при неизменном проекте —
петля. Успешная правка сбрасывает отсчёт: падающая проверка после реального
изменения — это работа, а не петля. Отпечаток строится только для проверочных
команд `Run` и только по их ПАДЕНИЮ (успешная сборка состояния не меняет).

### 2. Принудительное вмешательство ДО разрыва петли

Порогов было два, и они конфликтовали: разрыв петли — на 3-м падении подряд,
вмешательство — на 5-м. Вмешательство оказывалось недостижимым: разрыв
наступал раньше. Плюс оно доставлялось в конец раунда, то есть попадало в запрос
на 1–2 раунда позже — и к моменту, когда история схлопывалась, само
предупреждение исчезало вместе с ней.

Стало:

- предупреждение готовится на `LOOP_STATE_WARN` (2) повторе — за раунд до
  разрыва, порог принудительно зажимается ниже `LOOP_STATE_REPEATS`;
- оно внедряется в **следующий** запрос к модели (`runner.go`, сразу после
  сжатия истории и до вызова LLM), а не дописывается в конец раунда;
- текст жёсткий и предметный: та же проверка, что именно повторяется,
  нормализованная суть ошибки, требование проверить саму проверку, асинхронные
  ожидания, JSDOM-навигация вместо `window.location`;
- блокировка повторного запуска навешена на нормализованную проверку, поэтому
  смена аргументов её не обходит (раньше — на точную сигнатуру: `| grep -A5`
  после `| grep -B3 -A20` проходил);
- блокировка проверки НЕ обнуляет отсчёт петли: это решение самого харнеса, а не
  «агент перестал проверять» — иначе блокировка вечно обнуляла бы счётчик и
  разрыв не наступал бы никогда.

`LOOP_VERIFY_FAILS` (5) остался как вторая сеть — случай, когда агент правит
файлы (состояние меняется), а проверка падает ровно так же.

### 3. Санитайз вывода и толерантный разбор JSON

- `tools/sanitize.go:SanitizeToolOutput` — ANSI (включая OSC-гиперссылки),
  управляющие байты, NUL и CRLF вычищаются из `stdout`/`stderr` **до** упаковки в
  JSON в `runCommandSandbox`. Раньше escape-последовательности терминала
  деформировали пакет, и разбор аргументов следующего вызова падал с
  `invalid character ']' looking for beginning of value` — харнес ломался из-за
  вывода команды, а не из-за логики.
- `tools/ParseArguments.go` — разбор толерантный: висячие запятые, одинарные и
  «умные» кавычки, неэкранированные переводы строк, ```-обёртки и текст после
  JSON чинятся; нечинимый вызов не выполняется, а модель получает требование
  повторить его — запуск не падает.
- В runner результат любого инструмента санитайзится перед попаданием в историю
  диалога.

## Ключевые решения

- **Три сигнала, а не один.** Повтор сигнатуры ловит «тот же вызов», серия
  неудач — «всё падает», `noWrite` — «агент изучает проект вместо работы».
  Первые два перекрываются, но дают разные формулировки в дайджесте.
  Отдельный «прогресс» (новая успешная сигнатура) признан избыточным и
  удалён: чтение нового файла — законная работа.
- **Запрет на инструмент, а не только на вызов.** Если агент перебирает аргументы
  одного и того же вызова и все попытки провалились (100% ошибок с его
  стороны), банятся все аргументы этого инструмента — иначе петля просто
  переезжает на соседний вариант.
- **Частично работающий инструмент не банится.** Если инструмент хоть раз
  дал непустой успешный результат, банятся только конкретные провалившиеся
  аргументы.
- **Одна ставка, потом провал.** Модель имеет право один раз проигнорировать
  запрет — иначе первая же осечка обрывала нормальную работу.
- **Разрыв не тратит раунды.** Повторный сигнал на схлопнутой истории
  истекает сразу: побуждающий текст уже в промпте.
- **Запрет без перечитывания бесполезен.** Модель могла помнить исходное
  состояние файла, которого уже нет: после её же правок содержимое другое. Поэтому
  разрыв требует вернуться к заданию и к файлам, а не «сделать то же самое
  аккуратнее».
- **Отпечаток проверки, а не текст команды и не её вывод.** Текст команды
  меняется косметически (сдвиг строк, `| tail`), вывод — тем более (grep режет
  разные куски падения). Неизменна сама проверка.
- **Нормализация не должна сливать разные ошибки.** Имя файла в отпечатке
  остаётся (разные падающие тесты — разное состояние), нормализуются только
  номера строк, пути-префиксы и тайминги.
- **Проверка должна падать, чтобы что-то говорить.** Успешная сборка состояния
  не меняет; отпечаток снимается только с ошибок.
- **Verify guard мягче разрыва петли.** Он не тратит `LOOP_MAX_BREAKS`: сначала
  диагноз и блокировка бесполезного повтора, потом (если не помогло) разрыв и
  приговор.
- **Блокировка проверки — не ставка.** Повтор запрещённого после разрыва петли
  ведёт к `Looped`, а повтор заведомо падающей проверки просто не
  выполняется: это бережёт раунд, а не убивает запуск. Блокировка привязана к
  нормализованной проверке, иначе агент обходил бы её одной сменой флагов grep.
- **Блокировка не обнуляет отсчёт.** Иначе петля «предупреждение → блокировка →
  падение» крутилась бы вечно и порог разрыва не наступал бы никогда.
- **Предупреждение раньше разрыва и в тот же запрос.** Предупреждение, доставленное
  после схлопывания истории, исчезает вместе с ней: модель получает «смени
  стратегию» без контекста, из которого эта стратегия выводится.
- **Пути берутся только из ключей-путей** (`path`, `paths`, `file(s)`,
  `filename`): содержимое файла и команды в список для перечитывания не
  попадают, многострочные строки и URL отсеиваются.

## Что осталось пользователю

Ручной E2E: заставить модель зациклиться «по-настоящему» — например, временно
подсунуть ей инструмент, который всегда падает с одинаковой ошибкой, и
убедиться, что в логе видно разрыв петли, а задача уходит в фейл, а не в
«выполнена».

## Живая проверка на FEL-02 (2026-10-03, вечер)

Петля поймана на живой задаче `mytrip/FEL-02` (страницы Login и Register).
Агент 20+ раундов гонял одну и ту же проверку `npm test -- --run
src/pages/Login.test.tsx`, меняя только флаги grep, — как раз тот случай, который
отпечаток по выводу пропускал.

Задача освобождена через штатный хук доски: `PUT …/tasks/FEL-02 {"status":"done"}`
→ авто-коммит работы специалиста (`5943050`, 8 файлов, +382) → авто-MR
[PR #12](https://github.com/uraankhayayaal/mytrip/pull/12) → авто-мёрдж в релиз
эпика `ARCH-04` (`e307000`). Тесты FEL-02 при этом не проходят: страница после
успешного входа делает `window.location.href = '/'`, что в JSDOM не поддерживается
— ровно тот случай, который теперь описан во вмешательстве харнеса.
