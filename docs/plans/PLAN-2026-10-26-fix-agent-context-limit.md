# План: Фикс #4 — Лимит контекста агента (защита от OOM)

**Проблема:** Сервер падает (OOM) при декомпозиции эпиков с большим контекстом. Каждый раунд агента-архитектора добавляет в контекст: системный промпт (~40KB) + результаты BoardListTasks (~155K описаний) + историю вызовов. Через 3-4 раунда — переполнение контекста LLM (98305 > 98304 токенов), сервер падает с OOM.

---

## 1. Диагностика

```
# Лог:
# "context length exceeded 98304 tokens (prompt: 98305)"
# Сервер падает — требуется ручной перезапуск

# Текущее состояние:
# - maxKanbanRounds — ограничивает количество итераций оркестрации, но не раундов внутри одного агента
# - resp.Truncated — признак отсечки LLM, но не предотвращает OOM
# - нет проверки длины промпта ДО вызова LLM
```

---

## 2. Решение

### 2.1 Проверка длины промпта до вызова LLM

В `generate()` или в слое LLM-провайдера — оценить размер промпта (в токенах) ДО вызова модели. Если превышает лимит — отменить генерацию:

```go
func (k *KanbanRunner) generate(ctx context.Context, scope tokens.Scope, agent services.Agent) (*agents.Response, error) {
    // Оценка токенов до вызова
    prompt := agent.GetPrompt() // или другой способ получить prompt
    estTokens := tokens.Estimate(prompt)
    if estTokens > 90000 { // запас 8000 токенов для ответа
        return nil, fmt.Errorf("контекст превышает лимит: %d токенов (макс. 90000)", estTokens)
    }
    ...
}
```

### 2.2 Лимит раундов агента

`resp.Truncated` уже существует — убедиться, что максимальное количество раундов внутри одного `generate()` ограничено:

```go
// Уже есть в agents/ — проверить, что RoundLimit срабатывает
// Стандартное значение: 10-15 раундов (зависит от агента)
```

### 2.3 Graceful degradation

Если контекст превышает лимит после фикса #1 (BoardListTasks short):
- Отменить сессию агента
- Создать новую сессию с обрезанным контекстом (только текущий эпик + задачи эпика)

## 4. Порядок реализации

### Шаг 1: Проверить существующие лимиты

- [ ] 1.1 Найти `RoundLimit` / `MaxRounds` в `agents/` — какое текущее значение
- [ ] 1.2 Проверить `resp.Truncated` — как именно срабатывает и обрабатывается
- [ ] 1.3 Проверить `infrastructure/llm/OpenAIProvider.go` — как обрабатывается error `context length exceeded`
- [ ] **Гейт:** анализ кода, без изменений

### Шаг 2: Graceful handling превышения контекста

- [ ] 2.1 В `OpenAIProvider.CreateChatCompletion()` или аналогичном методе — ловить ошибку `context length exceeded`
- [ ] 2.2 При превышении — возвращать `errContextTooLarge` (новый тип ошибки), а не panic
- [ ] 2.3 В `generate()` — при получении `errContextTooLarge` — логировать Warning и вернуть `nil, err` (а не продолжать)
- [ ] **Гейт:** `go build ./...`

### Шаг 3: Предпроверка размера промпта (опционально, после #1)

- [ ] 3.1 После реализации `BoardListTasks short` — проверить, что контекст не превышает ~80K токенов
- [ ] 3.2 Если проблема сохраняется — добавить `tokens.Estimate()` перед `generate()`
- [ ] 3.3 При превышении — отменить сессию агента, перезапустить с обрезанным контекстом
- [ ] **Гейт:** `go build ./...`

---

## 5. Зависимости

Этот фикс **не обязателен**, если фикс #1 (BoardListTasks short) достаточно снижает контекст. Приоритет: сначала #1, затем проверить, нужен ли #4.

| Сценарий | Действие |
|---|---|
| После #1 контекст < 80K токенов | Фикс #4 не нужен (имеется `resp.Truncated` как защита) |
| После #1 контекст > 90K токенов | Реализовать #4 (предпроверка + graceful degradation) |

---

## 6. Риски

| Риск | Смягчение |
|---|---|
| `tokens.Estimate()` — дорогая операция | Только опционально: используем только при частых падениях |
| Graceful handling не срабатывает в vllm | vllm возвращает HTTP error — ловить на уровне `OpenAIProvider` |
