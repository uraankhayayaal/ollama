# PLAN-2026-10-05-todo-kanban-rollback

Промежуточные коммиты как единица отката, State Tracking задачи в доске
и **ручной** откат из UI. Автоматика тупиков — только продолжение
(инъекция / смена модели), без отката. Цель: автономность харнеса,
минимизация участия человека.

---

## Ключевые решения

| # | Решение | Обоснование |
|---|---|---|
| Р-1 | Единица отката — **git-коммит**, снимаемый по ходу работы над задачей | Правки агента не коммитятся до `done` (`gitflow_auto.go:298-330`), поэтому рабочее дерево внутри прогона грязное целиком. `git stash` прячет изменения и не трогает untracked (новые файлы агента) — как единица отката не годится |
| Р-2 | Откат — **только ручной**, из UI доски. Автоматически при тупике — только **продолжение** | Откат уничтожает прогресс, а петля чинится инъекцией или сменой модели. Авто-откат + авто-retry замыкает петлю, которую уже пришлось разрывать детектором петель |
| Р-3 | **Git-история worktree задачи и есть журнал State Tracking** | Отдельный подписчик `runevents → Redis` не нужен: коммит содержит раунд, агента, фазу и затронутые файлы. Плюс доска обновляется существующим `publishBoard`, а не новым каналом |
| Р-4 | Откат — рекурсивный, включая вложенные worktree сабмодулей | У каждой задачи с сабмодулями вложенный worktree (`gitflow_auto.go:113-149`); `git reset --hard` содержимое сабмодуля не откатывает |
| Р-5 | Цель — автономность 99.999%: watchdog по heartbeat, авто-возобновление после рестарта сервера, персистентная смена модели на уровне задачи | Сейчас «живость» сессии живёт в памяти процесса (`Session.running`), а `resetStaleInProgress` (`kanban.go:958-976`) **угадывает** вместо того, чтобы знать |

## Находки разведки (проверено в коде)

- **Н-1. Откатывать контекст LLM нечего.** В kanban-режиме диалог агента **не сохраняется
  вообще**: `runner.ResumeState` пишет только консольный планировщик
  (`executor.go:1016-1037` → `checkpoint.Conversations[stepID]`), в `kanban*.go` — ноль
  совпадений по `ResumeState|checkpoint|Conversations`. Диалог умирает вместе с прогоном,
  поэтому перезапуск задачи **сам по себе** даёт чистый контекст. Пункт «удалить последние
  реплики агента» из исходной постановки снимается.
- **Н-2. `chat:<project>` — транскрипт для человека, а не диалог агента.** Обрезать его
  = удалить то, что видит пользователь; поля `task_id` в записи нет
  (`chat/store.go:220-241`), так что обрезка даже не привязывается к задаче. Откат истории
  к снапшоту уже ломал систему — удалённые записи воскресали, `DELETE` отвечал `200`, а
  текст продолжал уходить в модель (А-11, `PLAN-2026-10-04:328-345`). **Не делаем.**
- **Н-3. Приёмка не гоняет тесты.** Стадии acceptor'а: `build`, `run`, `format`,
  `analyze`, `install`, `config` (`report.go:24-31`). Падение `go test` ловится только
  verify-guard'ом ранера. Триггер отката «упали тесты» к приёмке отношения не имеет.
- **Н-4. Лимита «3 попытки» в системе нет.** Бюджет слоёный: `REVIEW_MAX_ROUNDS=120`
  (живой `.env`), реальные гейты — `LOOP_VERIFY_FAILS=5`, `LOOP_STATE_REPEATS=3`,
  `LOOP_STATE_WARN=2`, `LOOP_MAX_BREAKS=2`, `ACCEPT_MAX_ROUNDS=3`. Откат привязываем к
  ручному действию, поэтому лимиты не блокируются.
- **Н-5. Доска — JSON-строки, а не хэши.** Ключи `board:<project>:task:<id>` пишутся
  через `Set` (`store.go:450`), множества — `SAdd`. Новые поля добавляются **JSON-тегами
  в `board.Task`**; запись в хэш создала бы второй источник истины, невидимый для кода.
  Подписчик событий → Redis для доски отсутствует **осознанно** (`board/tokens.go:14-16`);
  из потока событий в Redis пишутся только токены.
- **Н-6. FSM запрещает `in_progress→ready`** (`entity.go:87-118`) — «переместить карточку
  назад» в существующем автомате невозможно, нужен новый статус или новый переход.
- **Н-7. Статуса «провалено» нет.** Терминальны только `done|cancelled`
  (`entity.go:63-74`), поэтому при провале `kanban.go:1273-1288` вынужденно ставит `done`.
- **Н-8. Приёмка фиксирует, что автокоммит делается один раз на `done`.** Промежуточные
  коммиты меняют этот инвариант: на `done` дерево уже будет чистым.
- **Н-9. Расхождение комментария с кодом.** `runner/loop.go:21` утверждает
  «`REVIEW_MAX_ROUNDS` в живом `.env` = 500» (фактически `120`), а `:20-23` описывает
  «resume с той же историей», тогда как `executor.go:731-733` историю как раз сохраняет
  ради продолжения. Поправить попутно.
- **Н-10. `Repo.ex` не экспортируется** — агент не может собрать `&gitops.Repo{Root: ...}`
  для локальных операций: `nil` исполнителя даёт панику на первом же вызове.
  Единственный путь — `RepoFromState(&gitops.CLIExecutor{}, root, "", "", "")`.
  Промежуточный коммит — локальная операция, remote и точка отхода ему не нужны,
  поэтому это ограничение здесь безвредно, но для будущих вызовов из агентов стоит
  завести явный `gitops.NewLocalRepo(root)`.

## Этап 1: Промежуточные коммиты (фундамент отката)

- [x] 1.1. `gitops.CommitIfDirty(ctx, root, msg)` — обёртка над существующим
      `Repo.Commit` (`gitops.go:121-147`): он уже коммитит грязные сабмодули перед
      `add -A`, повторять эту логику нельзя. Тело Commit вынесено в
      `commitTracked` (поведение существующих вызовов не изменилось),
      добавлены `HeadSHA` и `InTaskBranch`
- [x] 1.2. Хук в блоке пост-раундовых обработчиков `runner/runner.go:1094-1120`
      (единый дренаж `TakeTouched`), а **не** после `observeRound` — так коммит
      получает ровно те файлы, которые агент изменил в раунде, и не конкурирует
      за очередь с авто-лечением LSP и реиндексацией RAG. Коммит идёт ПЕРВЫМ
      среди хуков
- [x] 1.3. Формат сообщения: `wip: раунд <n> (файлов: <k>)` + перечень путей в
      теле с усечением хвоста (`KANBAN_WIP_COMMIT_FILES`, по умолчанию 12).
      Обогащение агентом/фазой/ошибкой проверки — этап 2 (поля State Tracking):
      репортёр раннера не отдаёт scope на чтение
- [x] 1.4. Гард области: `gitops.InTaskBranch` — проверка **ветки** `ai/task/<id>`,
      а не имени каталога (имя worktree — конвенция сервера, ветка задаёт
      принадлежность кода задаче и переживает перенос каталога). Префикс вынесен
      в `gitops.TaskBranchPrefix` — единый источник для сервера и гарда
      (`server/gitflow.go:29` теперь ссылается на него). В plan-режиме агент
      пишет в общий клон `temp/<project>` на ветке `ai/<project>` — коммиты там
      не создаются
- [x] 1.5. Ключ выключения `KANBAN_WIP_COMMIT=0` (по умолчанию включено)
- [x] 1.6. `.gitignore`-bootstrap при создании worktree (`gitflow_auto.go:23-56`) —
      **только если файла нет**: `node_modules/`, `dist/`, `build/`, `__pycache__/`,
      `.venv/`, `target/`. Без этого `git add -A` на каждом раунде затащит артефакты
      сборки в историю задачи. `vendor/` в список **не** включаем — для Go его коммитят
      осознанно. `bootstrapTaskGitignore` вызывается и для worktree задачи, и для
      вложенного worktree сабмодуля (агент собирает и там)
- [x] 1.7. Автокоммит на `done` пересмотрен: пустой коммит не создаём (`Commit`,
      без `CommitAllowEmpty`) — с 1.1 дерево обычно чистое. **Но** чистое дерево
      сабмодуля больше не пропускает публикацию его ветки: `merge` в базовую ветку
      сабмодуля + `push` + `reset --hard` (обновление gitlink) выполняются ВСЕГДА,
      иначе gitlink родителя указал бы на коммит, которого нет в origin сабмодуля
- [x] 1.8. **Решено: squash НЕ делаем.** Причины: (1) идемпотентность
      `MergeFeature` держится на `MergedInto` (ancestry) — squash ломает проверку
      «уже влита» и плодит повторные merge-коммиты; (2) WIP-коммиты — журнал
      отката этапа 3, squash их бы стёр; (3) дифф MR и ревью считают net-изменения,
      число промежуточных коммитов на них не влияет
- [x] 1.9. Тесты: `gitops/wipcommit_test.go` (коммит только при грязном дереве,
      чистое дерево → без коммита, сабмодуль фиксируется до родителя, HeadSHA,
      InTaskBranch — таблица + ошибка), `runner/wipcommit_test.go` (env-флаг,
      сообщение, усечение списка), `agents/developer/wipcommit_test.go` (гард:
      общий клон не коммитится, ветка задачи коммитится, чистое дерево после
      коммита не даёт второго). Прогон с `-race` зелёный

## Этап 2: State Tracking задачи

- [x] 2.1. Поля в `board.Task` (`entity.go:261-289`), JSON-теги, не новый хэш:
      `agent_state` (`writing_code`/`running_tests`/`fixing_errors`/`idle`),
      `active_agent`, `checkpoint` (`base_sha`/`last_sha`/`last_good_sha`),
      `attempts`, `last_error` (стадия + усечённый нормализованный вывод),
      `heartbeat_at`
- [x] 2.2. `base_sha` — HEAD в момент создания worktree (`gitflow_auto.go:23-56`)
- [x] 2.3. `last_good_sha` — коммит, после которого проверка прошла; источник сигнала
      уже есть, это классификация verify-вызовов в `loopstate.go:95-141`, её же
      переиспользуем для `agent_state=running_tests`
- [x] 2.4. `heartbeat_at` обновляется каждый раунд (там же, где коммит) — это делает
      состояние переживающим рестарт сервера
- [x] 2.5. Показ в UI: карточка/лог агента. Данные поедут существующим путём —
      `publishBoard` (`session.go:661-668`) → WS `board` → `App.tsx:250-328`
- [x] 2.6. Тесты: запись/чтение полей, `last_good_sha` двигается только на успешной
      проверке, heartbeat обновляется

**Реализовано (этап 2).** Поля `board.Task` (+`TaskCheckpoint`, константы
`AgentState*`); запись — `Store.PatchTask` с хуком `TaskStateHook`, который
сервер подписывает на `srvEmitBoard` (правка состояния сама по себе обновляет
карточку). Классификация раунда вынесена в `runner/taskstate.go`:
`agentStateFor(ran, failedVerify, touched)` — любая упавшая verify-команда в
раунде даёт `fixing_errors` и **не** двигает `last_good_sha` (иначе зелёная
проверка следом «забыла» бы сломанный раунд), иначе при наличии проверки
`running_tests`, иначе `writing_code`/`idle`. `last_good_sha` двигается только
если в раунде был WIP-коммит И проверка прошла (точка отката должна указывать на
коммит, а не на «грязное» состояние). `last_error` усекается до 600 символов.
`attempts` инкрементится в `SetTaskStatus` при входе в `in_progress`.

## Этап 3: Ручной откат из доски

- [x] 3.1. Эндпоинт `POST /api/projects/{id}/tasks/{tid}/rollback` по образцу
      `reject-branch` (`server/git.go:382`)
- [x] 3.2. Цель отката: `last_good_sha` по умолчанию, `base_sha` — вариант «снести всё»,
      произвольный SHA — для power-user
- [x] 3.3. `gitops.RollbackWorktree(ctx, path, sha, recursive)`:
      `git reset --hard <sha>` + `git checkout -- .` + `git clean -fdq`.
      **`-x` не использовать** — иначе снесёт игнорируемые `node_modules`/`.venv`
- [x] 3.4. `clean -fdq` **без** `-x`, рекурсивный проход по вложенным worktree сабмодулей
- [x] 3.5. FSM: завести `failed_review` (терминальный? нет — из него должен быть повтор)
      и переходы `in_progress→failed_review→ready`. Либо явно разрешить `in_progress→ready`
      только для отката. `entity.go:26-37`, `:87-118`
- [x] 3.6. Кнопка «Откатить к последней рабочей версии» в UI задачи + подтверждение
      (операция необратима: WIP-коммиты уходят в reflog)
- [x] 3.7. Status-сообщение в чат по образцу `gitflow_auto.go:383-394`; `emitBoard`
      обновляет карточку
- [x] 3.8. Тесты: откат к `last_good_sha` возвращает дерево; `clean` не трогает
      игнорируемые файлы; сабмодуль откатывается рекурсивно; неизвестный SHA → 400;
      повторный откат идемпотентен

**Реализовано (этапы 3 и 5.1–5.2).** `gitops.RollbackWorktree` (+`RollbackResult`,
`ErrNoSuchCommit`): гард `InTaskBranch` (общий клон откатывать нельзя — его делят
шаги плана), проверка существования коммита, `reset --hard` + `checkout -- .` +
`clean -fdq` **без `-x`**. Рекурсия по сабмодулям: цель — не «последний SHA
сабмодуля», а gitlink **целевого коммита родителя** (`rev-parse <sha>:<path>`),
иначе откат родителя оставил бы сабмодуль на отменённом коде (gitlink в индексе
при этом остаётся новым — именно поэтому рекурсия обязательна); после прохода
`git add -- <пути>` ставит обновлённые gitlink'ы в индекс родителя. Эндпоинт
`POST /api/projects/{id}/tasks/{tid}/rollback`: сначала проверка worktree
(откатывать нечего → 404/400), потом разбор цели (`last_good`/`base`/SHA),
затем сам откат; неизвестный коммит — 400 (вина запроса), сбой git — 502.
Чекпойнт и `last_error` переезжают на точку отката, `in_progress → ready`
(возврат в очередь; разрешён в FSM как «откат», терминальные статусы не трогаются).
UI: две кнопки («К последней рабочей» / «Снести всё») с двухшаговым
подтверждением (не `window.confirm` — решение должен принимать человек, глядя на
задачу), кнопки заблокированы, если точки отката нет. Тесты: `gitops/rollback_test.go`
(8, реальный git с сабмодулем) и `server/taskrollback_test.go` (5, HTTP-роутинг).

## Риски

| Риск | Смягчение |
|---|---|
| `git add -A` на каждом раунде закоммитит артефакты сборки | 1.6 (`.gitignore`-bootstrap), 1.5 (выключатель) |
| Коммит при каждом раунде → шумная история MR | 1.8 — squash отклонён (ломает `MergedInto` и журнал отката), net-дифф MR не меняется |
| Параллельные задачи одного проекта делят один `.git` | У связанных worktree **свой** индекс (`.git/worktrees/<имя>/index`), конфликта `index.lock` нет; общий риск — gitlink сабмодуля, закрывается глубокой рекурсией (этап 5) |
| Откат уничтожает WIP-коммиты | Ожидаемо, коммиты остаются в reflog; подтверждение в UI (3.6) |
| Бесконечная автономия при тупике | 4.5 — конечный бюджет с эскалацией человеку |
| Промежуточные коммиты ломают существующий авто-мёрдж | Этап 1 идёт первым, за ним 3 — до этапа 4; тесты git-flow обязательны |

## Инцидент mytrip (FEL-04/FEL-05) и закрытие причин

Живой прогон на проекте mytrip вскрыл три системные причины, каждая закрыта
кодом (не только документацией):

1. **Мусор в коммите задачи.** Образ песочницы для монорепозитория (Go + Node)
   собирался по корневому `go.mod` → `golang` без npm. Агент скачал Node в корень
   проекта, и `git add -A` закоммитил `node.tar.gz` (46 МБ) и 4287 файлов
   распакованного тулчейна под заголовком «wip: раунд 14 (файлов: 4)».

   - `server/gitflow_auto.go:ensureTaskGitignore` — дописывает недостающие
     паттерны (`node_modules/`, `node-v*/`, `*.tar.gz`, `*.tsbuildinfo`, …) в
     существующий `.gitignore`, ничего не удаляя. `vendor/` не трогаем.
   - `gitops/gitops.go:checkStagedVolume` — гард объёма промежуточного
     коммита: один файл > `KANBAN_WIP_COMMIT_MAX_FILE_BYTES` (8 МБ) или набор
     > `KANBAN_WIP_COMMIT_MAX_BYTES` (32 МБ) → коммит не создаётся, индекс

     Служебный `.gitignore` оркестратора доказательством не считается.

## Что осталось пользователю (ручной E2E)

1. Прогнать задачу с 3+ раундами правок, убедиться в WIP-коммитах:
   `git -C temp/.wt-task-<проект>-<id> log --oneline`
2. Сломать проект так, чтобы проверка падала, дождаться тупика — убедиться, что
   происходит **продолжение** (инъекция/смена модели), а **не** откат
3. Нажать «Откатить к последней рабочей версии» — дерево должно вернуться к
   `last_good_sha`, WIP-коммиты уйти в reflog
4. Проверить то же самое на задаче с сабмодулями
5. Перезапустить сервер во время работы задачи — убедиться, что `in_progress`
   восстанавливается по heartbeat, а не по угадыванию
