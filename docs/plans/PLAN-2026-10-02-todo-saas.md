# PLAN-2026-10-02-todo-saas

Пошаговый план трансформации проекта в многопользовательское облачное SaaS-решение.

---

## Этап 1: Изоляция рабочих пространств (Sandbox)

- [ ] 1.1. Абстрагировать слой работы с файлами: выделить интерфейс `Workspace` вместо прямой работы с `temp/`
- [ ] 1.2. Реализовать `LocalWorkspace` (текущее поведение) как реализацию интерфейса
- [ ] 1.3. Реализовать `DockerWorkspace`: запуск команд через Docker API в изолированном контейнере
- [ ] 1.4. Добавить конфигурацию песочницы: лимиты CPU/RAM, таймауты, запрещённые команды
- [ ] 1.5. Интегрировать оркестратор агентов с Docker API (под каждую сессию — контейнер)
- [ ] 1.6. Реализовать монтирование кода пользователя в контейнер (volume mount)
- [ ] 1.7. Добавить очистку/уничтожение контейнеров после завершения сессии
- [ ] 1.8. (Опционально) Поддержка Kubernetes Pods как альтернативного бэкенда песочницы
- [ ] 1.9. (Опционально) Оценить Firecracker/vHive для микровиртуалок

## Этап 2: Многопользовательская архитектура (Multi-tenancy)

- [ ] 2.1. Спроектировать схему PostgreSQL: таблицы users, projects, sessions, prompts, agent_logs, kanban_boards
- [ ] 2.2. Добавить миграции БД (golang-migrate или goose)
- [ ] 2.3. Добавить поле `user_id`/`tenant_id` во все таблицы
- [ ] 2.4. Реализовать слой репозиториев с фильтрацией по user_id
- [ ] 2.5. Настроить логическое разделение Redis (префиксы ключей или отдельные DB)
- [ ] 2.6. Настроить логическое разделение Qdrant (отдельные коллекции на пользователя/проект)
- [ ] 2.7. Реализовать динамическое создание индексов Qdrant под пользователя
- [ ] 2.8. Интегрировать OAuth2 (GitHub/GitLab) для аутентификации
- [ ] 2.9. Реализовать JWT-сессии с refresh-токенами
- [ ] 2.10. Добавить middleware авторизации на все API-эндпоинты
- [ ] 2.11. Реализовать проверку прав доступа к проектам (owner/member)

## Этап 3: Масштабирование LLM-слоя

- [ ] 3.1. Определить стратегию: собственный инференс (vLLM/TGI) или облачные API (OpenAI/Anthropic/DeepSeek)
- [ ] 3.2. (Если собственный) Развернуть кластер vLLM/TGI с балансировщиком
- [ ] 3.3. (Если собственный) Реализовать очередь запросов к LLM с приоритетами
- [ ] 3.4. (Если API) Абстрагировать провайдеров моделей через единый интерфейс `LLMProvider`
- [ ] 3.5. (Если API) Реалиовать провайдеры: OpenAI, Anthropic, DeepSeek, Groq
- [ ] 3.6. Добавить circuit breaker и retry для внешних API
- [ ] 3.7. Реализовать учёт токенов и затрат на пользователя
- [ ] 3.8. Добавить кэширование повторяющихся запросов к LLM

## Этап 4: Очереди задач и асинхронность

- [ ] 4.1. Выбрать стек очередей (Asynq/machinery на Redis или RabbitMQ/Kafka)
- [ ] 4.2. Реализовать постановку задач агентов в очередь вместо синхронного выполнения
- [ ] 4.3. Реализовать background worker: забор задачи → песочница → агенты → результат
- [ ] 4.4. Добавить статусы задач: queued, running, completed, failed
- [ ] 4.5. Реализовать WebSocket или SSE для real-time логов агентов на фронтенд
- [ ] 4.6. Добавить отмену задач (graceful shutdown контейнера)
- [ ] 4.7. Реализовать повторные попытки (retry) при  transient-ошибках
- [ ] 4.8. Добавить приоритеты задач (платные пользователи — выше)

## Этап 5: Сетевой контур и безопасность

- [ ] 5.1. Реализовать безопасное хранение Git-токенов пользователей (шифрование)
- [ ] 5.2. (Опционально) Интегрировать HashiCorp Vault для секретов
- [ ] 5.3. Настроить reverse proxy / API Gateway (Nginx/Traefik/Kong)
- [ ] 5.4. Реализовать терминацию SSL/TLS
- [ ] 5.5. Добавить rate limiting на API (запросов/мин, токены/мин)
- [ ] 5.6. Добавить rate limiting на песочницы (не более N контейнеров на пользователя)
- [ ] 5.7. Реализовать CORS и security headers
- [ ] 5.8. Добавить аудит-логирование действий пользователей
- [ ] 5.9. Реализовать сканирование загружаемого кода на вредоносные паттерны

## Этап 6: Монетизация и метрики

- [ ] 6.1. Определить модель монетизации: подписка / pay-as-you-go / гибрид
- [ ] 6.2. Интегрировать Stripe (или CloudPayments) для платежей
- [ ] 6.3. Реализовать тарифные планы: лимиты проектов, вызовов агентов, токенов LLM
- [ ] 6.4. Добавить вебхуки Stripe для управления подписками
- [ ] 6.5. Реализовать дашборд использования (токены, проекты, затраты)
- [ ] 6.6. Добавить автоматические уведомления о приближении лимитов
- [ ] 6.7. Реализовать приостановку сервиса при превышении лимитов
- [ ] 6.8. Добавить метрики и мониторинг (Prometheus + Grafana)
- [ ] 6.9. Реализовать алертинг при аномалиях

## Порядок выполнения

1. Этап 1 (Sandbox) — фундамент безопасности
2. Этап 2 (Multi-tenancy) — данные и доступ
3. Этап 4 (Очереди) — асинхронность
4. Этап 3 (LLM) — масштабирование инференса
5. Этап 5 (Безопасность) — сетевой контур
6. Этап 6 (Монетизация) — обвязка

Этапы 2 и 4 можно параллелить. Этап 3 зависит от выбора стратегии (собственный vs API).
