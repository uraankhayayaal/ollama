# План: git submodule и мульти-репо задачи (одна задача → несколько проектов)

Статус: **РЕАЛИЗОВАНО (Ф-1—Ф-4).** Полный набор Go-тестов запускался;
два заранее известных flaky-теста ассистента падают и при изолированном запуске.
План
внедрения работы с git submodule и
мульти-репозиторными задачами: одна задача пользователя может затрагивать
несколько git-репозиториев одновременно (родитель + его submodule-пакеты),
каждый — со своими коммитами, ветками и MR. Отмечать чекбоксы `[x]` по мере
выполнения, как в `PLAN-2026-09-19-done-lsp.md`.

План сверен с кодовой базой 2026-09-24: ссылки на файлы и строки
актуализированы (см. «Сверка с кодом»).

## Проблема

До этой работы цикл был строго однопроектным. Сейчас прямые submodule
регистрируются как дочерние git-проекты, а их имена сохраняются на новых
эпиках/задачах в `Repositories`. Каноническим `OutputDir` остаётся worktree
родителя; worktree сабмодуля монтируется по пути из `.gitmodules` внутри него.
Операции git и MR при этом выполняются для каждого репозитория отдельно.

До внедрения git submodule не поддерживался:

- `gitops.Clone` без инициализации сабмодулей (`gitops/gitops.go`);
- в diff gitlink упадёт как смена одного SHA, содержимое не видно
  (`gitops/gitops.go:315-327` — `git diff <base>`, без `--submodule`);
- commit/push внутри сабмодуля не выполняются; push только родителя
  (`server/git.go:156-161`);
- реестр запрещает вложенность корней: `checkNesting`
  (`workspace/registry.go:255-275`, ошибки `ErrNested`/`ErrContains` `:80-81`);
- `grep -ri submodule` по Go-коду — 0 совпадений.

## Цель

1. Открытие git-проекта, содержащего прямые субмодули: clone, распознавание
   `.gitmodules`, регистрация сабмодулей как самостоятельных git-проектов
   (свой remote/base/branch), diff видит содержимое сабмодуля.
2. Одна задача может исполниться сразу в нескольких репозиториях; приёмка
   даёт N коммитов/N MR (сначала submodule, потом родительский gitlink).
3. Submodule-cовместимые reject (сброс дочерней ветки и gitlink) и merge.

## Ключевые решения

- **Модель регистрации.** Субмодуль из `.gitmodules` при открытии родителя
  регистрируется в реестре как отдельная запись `KindGit` с именем
  `<родитель>--<путь в родителе>` (например `app--packages/auth`) и полем
  `Parent` → имя родительского проекта. Корень — каталог сабмодуля (лежит
  внутри корня родителя). Блокер `checkNesting` ослабляется: вложенность
  разрешается, если вложенный проект — submodule зарегистрированного родителя.
- **Транзакционный порядок ≠ транзакция:** коммиты и MR строятся на каждом
  репозитории независимо, но с фиксированным порядком: внутренние (submodule)
  раньше внешних (родитель). gitlink родителя поднимается после коммита в
  сабмодуле. Полный атомарный мульти-коммит (одна транзакция) — вне рамок:
  разносится на N MR.
- **Мульти-задача использует один родительский OutputDir**: task worktree
  содержит submodule worktree по его относительному пути. FileOps и Run уже
  ограничены корнем родителя и работают с обычными путями вложенных файлов.
- **Дифф по умолчанию `--submodule=log`** — в диффе родителя gitlink показывается
  как заголовок коммита сабмодуля; полное содержимое — через diff самого сабмодуля.
- **Пуш с токеном на сабмодуль**: у сабмодуля свой remote; `tokenPushURL`
  (`server/git.go:140-148`) применяется к каждому репозиторию по его remote.
- **Гит-сабмодуль ≠ git-подпроект с `git subtree`**: не путать; субмодуль —
  это gitlink, неделимое pointer-состояние в родителе.
- Первая версия поддерживает прямые сабмодули родителя; сабмодули внутри
  сабмодулей не регистрируются и не принимаются пакетно.

## Точки изменений

### Ф-1: submodule-aware gitops (фундамент, самодостаточен)

- [x] `gitops/gitops.go` `Clone`: clone родителя, валидировать пути из
  `.gitmodules`, затем `git submodule update --init`; env
  `GITOPS_SUBMODULES=0` выключает инициализацию, `GITOPS_SUBMODULE_DEPTH`
  задаёт положительную глубину. Инициализация отдельной командой позволяет
  проверить пути из манифеста до их материализации.
- [x] `gitops/submodule.go`: `ListSubmodules`, `EnsureSubmodules` и
  `PrepareSubmodules` читают манифест, проверяют пути и готовят detached
  checkout feature-ветки (ветка хранится как ref, HEAD не занимает её).
  `Repo.Commit` коммитит изменения сабмодулей и затем gitlink родителя;
  `Repo.PushToWith` отправляет дочерние ветки первыми и позволяет серверу
  выбрать credentialed URL отдельно по remote каждого сабмодуля.
- [x] `gitops/gitops.go` `Diff` использует `diff.submodule=log`; подробный
  diff содержимого возвращается из отдельного проекта сабмодуля.
- [x] `gitops/gitops.go` `Push`/`PushTo`: push сабмодулей выполняется до push
  родителя, gitlink публикуется после доступности дочернего SHA.
- [x] `server/diff.go`: gitlink имеет статус `submodule`, а диффы дочерних
  репозиториев добавляются в общий список с путём относительно родителя.
  Кэш пересобирается по запросу и инвалидируется после accept/reject.
- [x] Реестр `workspace`: `Parent`, `GitTarget` и валидация вложенного корня;
  имя строится как `<parent>--<path>`, разделитель пути обратимо кодируется.
- [x] `server/git.go` `handleOpenGitProject`: после clone регистрирует прямые
  сабмодули с их remote, feature branch, base commit и MR target branch.
- [x] merge примитивы остаются на Git SHA gitlink; `Diff` показывает log для
  gitlink, а тесты подтверждают коммит и push дочернего репозитория до родителя.
- [x] Тесты: `.gitmodules` parser и реальный локальный clone/commit/push в
  `gitops`; вложенность реестра; submodule diff и path-prefix parsing в
  `server/diff_test.go`.

## Верификация

```
go build . ./agents/... ./tools/ ./board/ ./gitops/ ./workspace/ ./server/
go vet  . ./agents/... ./tools/ ./board/ ./gitops/ ./workspace/ ./server/
go test . ./agents/... ./tools/ ./board/ ./gitops/ ./workspace/ ./server/
npm run build  # web/
```

Ручной E2E (реальные gит-протокол, два репозитория): локальный родитель +
submodule → открыть по `git_url` → правка в сабмодуле + правка в родителе →
diff видит содержимое сабмодуля → accept → 2 коммита/2 MR (сабмодуль раньше) →
reject сбрасывает оба.

Автоматизированные локальные E2E для gitops commit/push, task worktree,
batch accept и reject добавлены и проходят. Внешний GitHub/GitLab MR-flow не
запускался: тестовые remotes и credentials в этой среде не задавались.

Последняя верификация:

- `go build . ./agents/... ./tools/ ./board/ ./gitops/ ./workspace/ ./server/` — прошло.
- `go vet . ./agents/... ./tools/ ./board/ ./gitops/ ./workspace/ ./server/` — прошло.
- `npm run build` в `web/` — прошло.
- Полный Go-набор падает на уже отмеченных flaky-тестах
  `TestChatAssistantDeleteTaskAfterConfirm` и
  `TestChatAssistantCreatesBugAndTask`; оба также воспроизводятся отдельно.

Известные нюансы (не убирать):
- `go build ./...` падает на `temp/moon-distance/...` — использовать перечень выше.
- Не форматировать `agents/acceptor/checks.go`, `agents/acceptor/run.go`.
- Комментарии/промпты/UI-тексты — на русском.
- Remote каждого сабмодуля может требовать свой токен; сервер отдельно
  выбирает `GITHUB_TOKEN`/`GITLAB_TOKEN` по host remote сабмодуля.
- `--depth=1` в сабмодулях экономит время, но ломает `git merge-tree`-проверки
  в `gitops/merge.go`: мини-клоны мержить нельзя — merge идёт в родителе по
  pointer'у (версия задачи Ф-1 фиксирует только push/diff/commit, не merge).
- Параллельные агенты одного проекта и worktree сабмодулей не должны
  пересекаться каталогами (`mergeLock` на проект уже есть).
- Реестр JSON обратной совместимости: `Parent`/`Repositories` — omitempty,
  старые файлы открываются без изменений.

| Ф-2 модель N-репозиториев | ~7 файлов (board, kanban, gitflow_auto, executor, developer) | высокая |

## Сверка с кодом (2026-09-24)

Проверены ссылки плана против текущей ветки; пункты отражают текущую
реализацию. Проверка локальным Git не требует внешнего remote; интеграция с
реальными GitHub/GitLab remotes зависит от доступных credentials.

- Текущий workflow ограничен прямыми сабмодулями: они регистрируются,
  получают project/task worktree, проходят commit/push/MR и попадают в общий
  Diffboard. Вложенные сабмодули внутри них не регистрируются отдельно.
- Кэш `gitProjectDiff` пересобирается при запросе списка, а после accept и
  reject инвалидируется; дифф дочерних проектов агрегируется в список файлов.
- `board/store.go`: Redis-ключи `board:<project>:*` — `key`/`epicsID`/`tasksID`/
  `bugsID`/`epicKey`/`taskKey` (`:85-102`), под репозитории сабмодуля своей
  шины доски не заводится.
- Добавлены `gitops/submodule_test.go`, `server/diff_test.go` и
  `server/gitflow_submodule_test.go` с parser, path safety, локальными clone,
  task worktree, batch accept/reject сценариями.
- Проверочные команды и «Известные нюансы» совпадают с `AGENTS.md`
  (рабочий перечень: `./agents/... ./tools/ ./board/ ./gitops/ ./workspace/
  ./server/`).
