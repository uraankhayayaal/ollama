# План: актуальность RAG при переходе между эпиками (индекс `main` + рабочая копия агентов)

Статус: **РЕАЛИЗОВАНО**, остался ручной E2E на живом Qdrant (инфраструктура и
модель эмбеддингов — у пользователя). Формат — как остальные `PLAN-*.md`.
Верификация 2026-09-28: `go build`/`go vet`/`go test` (`.`, `./agents/...`,
`./tools/`, `./board/`, `./rag/`, `./server/`, `./runner/`, `./gitops/`) —
зелёные.

## Цель

Убрать жалобу «переключаю эпик на следующий, а агент в статусе `analysis` не
видит изменений предыдущего эпика»: и в файлах рабочей копии, и в выдаче
`CodeSearch`.

## Проблема (три независимые причины)

1. **Индекс `main` не обновлялся после релиза эпика.** Branch-Aware RAG
   (PLAN-2026-09-27) ищет по связке «текущая ветка + `main`», но индекс `main`
   наполнялся только если кто-то явно нажал «Индекс RAG» или отработал
   `RAG_AUTO_REINDEX`. Для типового сценария «релиз эпика → новый эпик» точки
   `main` отсутствовали либо содержали код до релизов предыдущих эпиков.
2. **Рабочая копия агентов `temp/<имя>` не синхронизировалась с `main`.**
   Она живёт на ветке `ai/<имя>` (ветка задач — `ai/task/<id>`, релизная —
   `ai/epic/<id>`), и после merge эпика в `main` оставалась на старом коде.
   Аналитик и лиды работают именно в ней, а worktree задачи создаётся только на
   `in_progress` — то есть весь `analysis` шёл по коду до релизов.
3. **CodeSearch не находил проект из worktree задачи.** Имя проекта для RAG
   бралось как `basename(OutputDir)`, а агент задачи работает в
   `temp/<имя>/.wt-task-<имя>-<id>` → проект `<имя>-task-<id>`, которого нет.

Плюс: `RagIndexStatus` считает точки всех веток сразу, поэтому «индекс
построен» маскировало пустую ветку `main`.

## Решения пользователя

Все три причины исправляются (не только первая), с тестами.

## Архитектурные решения

- **Индекс ветки читается из git-объектов, а не из рабочей копии.** Иначе
  checkout, отставший от `main`, снова дал бы «индекс main со старым кодом» —
  ровно тот дефект, который чинится. Явный `branch` больше не переименовывает
  снимок checkout: `IndexBackground(branch)` = индекс содержимого ветки,
  `IndexBackground("")` = индекс рабочего каталога.
- **Ветка задачи индексируется по диффу, а не целиком.** `ai/task/<id>`
  отребейчена на релизную ветку эпика, поэтому «свои» файлы задачи и код уже
  слитых задач эпика — это `git diff main...ai/task/<id>`. Остальное покрывает
  индекс `main`, а выдача `rag.Search` объединяет ветку задачи с `main` и сам
  отбрасывает перекрытые `main`-чанки. Полная индексация worktree стоила бы
  эмбеддингов всего проекта на каждый старт задачи.
- **Хуки фоновые и деградирующие.** Ошибка индексации/синхронизации — только в
  лог (`Detailf`/`Warnf` + статус в чат), git-flow от неё не зависит.
- **Не теряем правки агентов.** Merge `main` в `ai/<имя>` выполняется только при
  чистом дереве; конфликтный merge откатывается (`git merge --abort`), грязное
  дерево пропускается. Если HEAD не сдвинулся (main уже внутри ветки проекта) —
  переиндексация не запускается.
- **Индексация без «пустых» прогонов.** `BranchIndexed` отсекает повторный
  полный прогон, а в статусе чата он отличается от реального обновления
  («актуален, повторная индексация не требовалась»), чтобы ноль файлов не
  выглядел как «обновилось».
- **Рабочая копия синхронизируется из `main`, а не наоборот.** Ветка проекта
  `ai/<имя>` — «рабочая линия» агентов; `main` не трогаем никогда.

## Известные ограничения

- Сбор ветки повторяет правила фильтрации обхода рабочей копии, но опирается на
  `git ls-tree` (только отслеживаемые файлы); принудительно добавленные в git
  игнорируемые файлы в индекс попадут.
- `git merge main` в `ai/<имя>` не делает `git fetch`: подтягивается локальный
  `main` (его двигают наши же релизы). Изменения `main` извне подхватываются
  при следующем клоне/fetch, а не этим хуком.
- Индексация `main` после релиза — полная (весь проект). Для крупных проектов
  она ощутимо дольше фоновой переиндексации задачи; выполняется в фоне и
  отсекается проверкой актуальности.

## Что осталось пользователю (ручной E2E)

1. Поднять инфраструктуру (Redis, Qdrant, модель эмбеддингов) и `go run . serve`.
2. Проект с ≥2 эпиками: слить эпик-1 в main, дождаться статуса
   «RAG-индекс проекта обновлён … (ветка main)».
3. Создать задачу эпика-2 на `analysis` и проверить в чате/логах:
   `CodeSearch` находит функцию, добавленную эпиком-1; `git log` в
   `temp/<имя>` содержит коммит синхронизации с main.
4. Проверить, что повторный релиз (`already=true`) не мутирует git.
