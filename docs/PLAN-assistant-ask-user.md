# План: «спроси пользователя при неоднозначности» — структурированные вопросы ассистента

Статус: **ПЛАН (реализация позже)**. Формат — как остальные `PLAN-*.md`:
решения пользователя, решения архитектуры, привязка к текущему коду
(`file:line`), этапы с чекбоксами, верификация. Обновлять файл по мере
выполнения (чекбоксы `[x]`), статус менять на «реализовано» только после
зелёной верификации.

## Цель

Когда ассистент видит неоднозначность (несколько равнозначных трактовок,
несколько кандидатов-объектов, не хватает реквизитов для действия: эпика,
исполнителя, приоритета, формата ответа), он **не угадывает**, а задаёт
**структурированный вопрос пользователю** прямо в чате:

- несколько **вариантов выбора** + один **кастомный вариант** с полем ввода;
- вопрос бывает двух видов:
  - **один вариант** (опции) — пользователь просто **нажимает на одну опцию**,
    это и есть ответ;
  - **несколько вариантов** (чекбоксы) — пользователь отмечает **несколько +
    кнопка «Подтвердить»**;
- ассистент может спросить **несколько вопросов за один раз** — они
  показываются **пошагово** (вардин-мастер: один вопрос на шаг, счётчик
  «Вопрос N из M», «Назад» для исправления);
- в каждом вопросе **отмечается предпочтительный вариант** (выделение +
  бейдж «рекомендую»), но решение всегда за пользователем.

Ответ пользователя возвращается модели как результат инструмента, и диалог
продолжается — ассистент отвечает уже с учётом выбора.

## Решения пользователя (зафиксировано)

1. **Не угадывать**: при неоднозначности ассистент обязан спросить, а не
   выбрать «наиболее вероятное» сам.
2. **Формат ответа**:
   - одиночный выбор — пользователь кликает **одну опцию** (это ответ,
     дополнительной кнопки нет);
   - множественный выбор — пользователь отмечает **несколько чекбоксов**
     и жмёт **«Подтвердить»**;
   - всегда есть **кастомный вариант** «Свой ответ» с полем ввода (в
     одиночном и множественном виде).
3. **Несколько вопросов за раз** — пошаговый вардин (один вопрос на экран,
   «Назад», счётчик шагов); ответ на каждом шаге отправляется сразу по мере
   прохождения, все ответы собираются и возвращаются модели одновременно.
4. **Предпочтительный вариант** — ассистент помечает опцию флагом
   `recommended`; в UI она выделена и подписана «рекомендую». Это подсказка,
   не принуждение: выбор всё равно делает пользователь.
5. Подтверждение деструктивных действий (Р-3 из `docs/PLAN-assistant.md`)
   остаётся текстовым («Подтвердите: ...? (да/нет)») — не в этой фиче.

## Архитектурные решения

### Р-1: инструмент `AskUser` как серверный мост
Новый инструмент `AskUser` реализует `tools.Tool` в `server/ask.go` (как
`actionTool` в `server/actions.go`) и добавляется ассистенту через уже
существующий `asst.AddTools(sess.serverActionTools()...)`
(`server/chatassist.go:49`), поэтому в `agents/chatassist/agent.go` менять
нечего — инструмент приходит с сервера.

Модель вызывает `AskUser` с массивом `questions`. Схема аргументов:

```json
{ "questions": [ {
    "id": "q1",
    "text": "Какой язык для порта?",
    "kind": "single",                 // single — опции; multi — чекбоксы
    "allow_custom": true,             // показать «Свой ответ» с полем ввода
    "options": [
      { "id": "go",   "label": "Go (фичи уже на Go)", "recommended": true },
      { "id": "rust", "label": "Rust" },
      { "id": "ts",   "label": "TypeScript" }
    ]
}, { "id": "q2", "kind": "multi", ... } ] }
```

Инструмент **блокирует** (как `waitGate`, `server/session.go:250`) до тех пор,
пока пользователь не ответит на все вопросы, после чего возвращает модели JSON:

```json
{ "status": "answered",
  "answers": [
    { "question_id": "q1", "selected": ["go"],          "custom": "" },
    { "question_id": "q2", "selected": ["a","b"],       "custom": "своё значение" }
  ] }
```

Модель видит ответы как результат инструмента в том же цикле генерации
(`runner/runner.go:444`) и продолжает отвечать с учётом выбора.

### Р-2: ожидание ответа через `Session` (паттерн gate, но для чата)
На `*Session` заводится реестр ожидающих вопросов (структура `pendingAsk`):
- `AskUser(...)` — публикует вопрос(ы) в чат (роль `ask`, payload `chat.Ask`),
  кладёт в реестр `ask_a` с каналом `ans chan askAnswers` (буфер 1) и блокает;
- `AnswerAsk(askID, choice)` — правалидирует активный `pendingAsk`, пишет ответ
  в канал; когда отвечены **все** вопросы пачки — разблокирует инструмент;
  каждый пришедший ответ также сохраняется в `pendingAsk.answers` для истории
  и повторного рендера;
- защита: только один активный неотвеченный `AskUser` на сессию; повторный
  вызов при неотвеченном — ошибка «предыдущий вопрос ещё не отвечен» (модель
  по промпту не должна спамить вопросами без ответов);
- отмена контекста (`sess.stopped`) разблокирует инструмент с ошибкой — как в
  `waitGate` (`server/session.go:281`).

### Р-3: роль `ask` в чате + структурированный payload
`chat.Message` расширяется полем `Ask *chat.Ask` (`json:"ask,omitempty"`), где
`chat.Ask` = `{ ID, Questions []Question, Answered bool }`. Роль сообщения —
новая `chat.RoleAsk = "ask"`. Разбор/сбор записи стрима дополняется в
`chat/store.go:161-217` (поле `ask` кодируется JSON-строкой внутри flat-record).
Live-доставка работает без изменений: `Append` уже публикует полное сообщение
в шину (`chat/store.go:119-125`).

### Р-4: фронт — карточка вопроса (вардин)
Новый компонент `AskCard` в Chatboard. Поведение:

- сообщение с ролью `ask` рендерится карточкой (не текстом);
- верх: текст вопроса + счётчик «Вопрос i из N»;
- опции:
  - `kind=single` — радио-кнопки; клик по опции **сразу отправляет ответ**
    (`POST .../ask/{askID}/answer`) и автоматически переводит на следующий шаг;
    при выборе «Свой ответ» открывается поле ввода, отправка по клику на
    опцию/Enter;
  - `kind=multi` — чекбоксы + кнопка **«Подтвердить»** (активна, когда
    отмечено ≥1 и заполнено кастомное поле, если оно отмечено);
- опция с `recommended: true` — выделена стилем и бейджем «рекомендую»;
- навигация вардина: «Назад» к предыдущему шагу (можно изменить ответ —
  повторный `POST` перезаписывает), прогресс «i из N»;
- когда отвечены все шаги — карточка сворачивается/помечается «ответы
  получены», а в истории чата появляется итоговое user-сообщение с ответами
  (для аудита и контекста).

### Р-5: ответ возвращается модели через инструмент, а не через контекст
Ответы пользователя попадают модели **результатом инструмента `AskUser`**
(в том же `Generate`-цикле), поэтому в историю сообщений модели не нужно
подмешивать синтетические user-строки. Пользовательское резюме в чате
(Р-4) — только для отображения/аудита.

## Интеграции с существующим кодом

- **Блокирующий инструмент** — тот же паттерн, что `waitGate`
  (`server/session.go:250-284`): канал + select на `ctx.Done()`. Раннер не
  меняется.
- **Добавление инструмента ассистенту** — `sess.serverActionTools()`
  (`server/actions.go:172`) уже инъектируется в набор ассистента
  (`server/chatassist.go:49`); `AskUser` добавляем в этот список.
- **Чат/шина** — `sess.append` (`server/session.go:385`) + hub-publish
  (`chat/store.go:119-125`) работают без изменений при расширенном `Message`.
- **REST** — новый маршрут копирует `handleGateDecide` (`server/server.go:686`,
  CSRF через `authHandler`, `server.go:150`).
- **WS** — новых типов событий не нужно: `ask`-пост приходит как обычный `chat`,
  frontend различает по роли.

## API (изменения)

```
POST /api/projects/{id}/ask/{askID}/answer
тело: { "question_id": "q1", "selected": ["go"], "custom": "" }
ответ: { "ok": true, "answered": 2, "total": 2 }
```
Ответ с `answered < total` — промежуточный (вардин); инструмент разблокируется,
когда `answered == total`. `custom` заполняется только при выборе кастомного
варианта.
