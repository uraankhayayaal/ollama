# Решение проблем

Симптом → причина → решение.

## Запуск

### `unknown provider`

**Причина:** не задан `LLM_PROVIDER`, либо значение не распознано
(`models/resolve.go:71`).

**Решение:**

```bash
LLM_PROVIDER=ollama   # или yandex / trim / reg
```

### Ollama недоступна

**Симптом:** таймаут HTTP-запроса к модели.

**Проверить:**

```bash
curl -s localhost:11434/api/tags | head
ollama list
```

**Решение:** `ollama serve` в отдельном терминале. Проверьте
`OLLAMA_HOST`, если Ollama не на дефолтном порту.

> Ollama **не входит в `compose.yaml`** — там только Qdrant и Redis.
> `docker compose exec -it ollama …` не сработает: сервиса нет.

### Модель не найдена

```bash
ollama pull qwen3-coder:30b
```

> Модель берётся из `providers.json` (`default_model`) или из `MODEL`.
> Пустое значение при отсутствии `default_model` — ошибка
> «у провайдера не задана модель», а не молчаливая подстановка.

## Выбор модели

### Какая модель работает?

Один источник правды — логи, а не догадки по переменным окружения:

```bash
grep "server: LLM" logs/server.log | tail -3
grep "\[llm\]" logs/<проект>.log | tail -3
```

Формат: `server: LLM <провайдер>/<модель> (large=<крупная модель>)`. Строка
`[llm] модель запуска: …` появляется на каждый старт оркестрации, `[llm] модель:
…` — на каждое сообщение в чат.

### Выбор модели в UI не применился

**Симптом:** переключатель в шапке показывает новую модель, а работа идёт на
старой.

**Причины и проверки:**

| Причина | Как проверить |
|---|---|
| Идёт оркестрация — она держит прежний провайдер до конца запуска | UI покажет предупреждение; в ответе REST `applies_to_running: true`. Дождитесь конца запуска или нажмите «Остановить» |
| Модели нет в `providers.json` для этого провайдера | Ответ `400`: перечисляет доступные модели. Дописать в `models` — конфиг перечитывается без перезапуска |
| Провайдер не собирается (битый `base_url`, пустая модель) | Ответ `400`/`502` с текстом; UI откатывает выбор и показывает ошибку |
| Обновили `providers.json`, но модель не появилась в списке | Файл перечитывается по mtime — проверьте, что редактировали тот файл, который нашёл процесс (`PROVIDERS_CONFIG` или поиск вверх от рабочего каталога сервера) |
| Ollama: модель не скачана | `ollama list`; конфиг не проверяет наличие модели — нужен `ollama pull` |

### После смены модели в UI всё равно старая

Перезапустите оркестрацию кнопкой «Остановить» → «Продолжить»: новый провайдер
создаётся на старте запуска. Кнопка «сброс» у переключателя возвращает выбор из
`LLM_PROVIDER`/`MODEL`/`MODEL_LARGE`.

### `providers.json не найден`

Файл ищется в рабочем каталоге сервера и выше до корня. Задать путь явно:

```bash
PROVIDERS_CONFIG=/etc/ai/providers.json go run . serve
```

### Значения `OLLAMA_MODEL`, `*_INPUT_TOKENS` игнорируются

После перехода на `providers.json` лимиты и модели читаются только из конфига.
Перенесите `OLLAMA_MODEL` → `MODEL` (+ `default_model`), `OLLAMA_NUM_CTX` /
`OLLAMA_OUTPUT_TOKENS` / `OLLAMA_THINK_TOKENS` → `settings` провайдера. Старые
имена молча ничего не делают.

## Инфраструктура

### Qdrant недоступен

**Симптом:** `CodeSearch` возвращает `skipped`.

```bash
docker compose ps
docker compose logs qdrant | tail -20
docker compose exec qdrant sh -c 'ls /qdrant/storage'
```

**Важно:** приложение ходит в Qdrant по **gRPC** (`56334`). `curl
localhost:56334` ничего не вернёт — это не ошибка. Проверяйте инструментом
`RagIndexStatus`.

### Redis недоступен

**Симптом:** нет чекпоинтов плана, доска не работает.

```bash
redis-cli -p 56379 ping
```

Агенты, RAG и ревью при этом работают — чекпоинты и доска просто
недоступны.

### `QDRANT_ADDR` недоступен после рестарта

Данные Qdrant в volume `qdrant`. `docker compose down` их сохраняет,
`docker compose down -v` — **удаляет**. После `-v` нужна полная
переиндексация.

## RAG

### Поиск ничего не возвращает

Возможные причины:

1. **Индекс не построен** — `go run . index <проект>`.
2. **Индекс пуст** — `RagIndexStatus` вернёт `chunks: 0`.
3. **Ветка не совпадает** — индекс версионирован по веткам. Индекс,
   построенный в `main`, не виден из `ai/task/42` для перекрытых чанков.
   Переиндексируйте в нужной ветке.
4. **Пустой коммит** — проект без Git индексируется с пустым
   `commit_sha`; при возврате к Git-версионированию точки не совпадут.

### Поиск находит старую версию файла

Индекс устарел. `RAG_AUTO_REINDEX=1` включает автопереиндексацию после
мутаций; вручную — `go run . index <проект>`.

### После релиза эпика новый эпик не видит его изменений

Проверьте в `logs/<проект>.log`:

- `rag: фоновая индексация <проект>: ветка main из git …` — индекс `main`
  пересобирается после реального merge эпика (фоновый хук, `server/ragref.go`).
- `rag: индекс ветки main (<коммит>) актуален — повторная индексация не нужна` —
  ветка не менялась с прошлого прогона, переиндексация закономерно
  пропущена.
- `gitflow: рабочая копия ai/<имя> синхронизирована с main` — рабочая копия
  агентов подтянута. Если вместо этого
  `rag: синхрон рабочей копии с main пропущен — есть незакоммиченные правки`,
  дождитесь коммита агентов (или перезапустите оркестрацию) и повторите.
- `rag: фоновая индексация … изменения ветки ai/task/<id> относительно main` —
  индекс изменений ветки задачи (код задачи и слитых задач эпика) создан.

`RagIndexStatus` считает точки **всех** веток сразу, поэтому «индекс построен»
не означает, что в `main` есть точки: смотрите лог индексации и `branch` в
ответе `CodeSearch`.

### `409` при `POST /api/projects/{id}/index`

Индексация этой ветки уже идёт (single-flight по ветке). Дождитесь статуса в
чате. Другие ветки при этом индексируются параллельно — 409 означает
конфликт только по той же ветке.

### Эмбеддинги не совпадают по размерности

Коллекция создана с другой моделью (`EMBEDDING_MODEL`). Сменили модель —
нужно пересоздать коллекцию.

## LSP

### `LspCheck` возвращает `skipped`

Сервер не найден или не установлен.

```bash
which gopls; which typescript-language-server; which pyright
LSP_BIN_PATH=/custom/path go run . ...
```

Установить: `go install golang.org/x/tools/gopls@latest`,
`npm i -g typescript-language-server typescript pyright`.

### `LSP_SERVER` не подхватывается

Значение разбирается через `strings.Fields` — полная команда с
аргументами, первый элемент ищется через `binpath.Look`.

### Диагностики не успевают

`LSP_DIAG_WAIT` — верхняя граница ожидания; фактическое ожидание
адаптивное (`4 ×` измеренной латентности, в границах
`[250ms, LSP_DIAG_WAIT]`). На первом запуске латентность неизвестна —
поднимите `LSP_DIAG_WAIT` до 5-10 с.

## Планировщик

### Resume не находит чекпоинт

Чекпоинты включаются, только если задан `REDIS_ADDR` явно, `PLAN_CHECKPOINT=1`
или передан `--resume` (`main.go:683-684`). Проверьте, что Redis доступен
**на момент первого запуска** — иначе чекпоинт не был записан.

### Шаг падает с ошибкой LSP

Это **предохранитель**, а не поломка: ошибка в изменённых файлах шага роняет
шаг и откатывает его scope (`agents/planner/lspgate.go:159-164`).
Посмотрите примеры `file:line:col` в сообщении.

Выключить: `LSP_STEP_GATE=0` (осторожно — теряется главный предохранитель
против «красивого, но не компилирующегося» кода).

### Откат мешает отладке

`CODEGEN_ROLLBACK_ON_FAIL=0` — scope останется как есть.

### Агент повторяет один и тот же вызов

Детектор петли (`runner/loop.go`) рвёт зацикленную историю, запрещает
повторяющийся вызов и даёт указание сменить подход, а при повторном нарушении
валит запуск с «зациклился» — задача при этом **не** помечается выполненной.
Это независимо от лимита раундов: даже `REVIEW_MAX_ROUNDS=500` не даст петле
выбраться.

Если пороги не подходят проекту — подкрутите `LOOP_SIG_REPEATS`,
`LOOP_FAIL_STREAK`, `LOOP_NO_WRITE` (см.
[справочник env](../30-reference/environment-variables.md)). Подробнее о
механизме — [разрыв петли](../20-features/agents-and-roles.md#разрыв-петли).

### Агент патенно правит один и тот же тест, но вызовы каждый раз разные

Это петля по **состоянию**, а не по сигнатуре: совпадает нормализованная сама
проверка, проект не меняется. Ловит сигнал «неизменное состояние»
(`LOOP_STATE_REPEATS`, по умолчанию 3). Отпечаток строится по проверке, а не по
её выводу: иначе `| grep -A5` и `| grep -B3 -A20` выглядели бы как разные
ошибки, хотя это один и тот же падающий тест — типичный способ агента
замаскировать петлю.

Порядок реакции харнеса: на втором падении подряд (`LOOP_STATE_WARN`) модель
получает сильное предупреждение с нормализованной сутью ошибки (умеет ли
проверка вообще, асинхронные ожидания, JSDOM-навигация вместо
`window.location`), а повторный запуск той же проверки блокируется на
`LOOP_VERIFY_BLOCK_ROUNDS` раундов; на третьем — разрыв петли (схлопывание
истории, запрет, требование начать заново), а после исчерпания разрывов —
честный провал задачи.

Если ваш стек гоняет одну и ту же проверку с РАЗНЫМИ аргументами по делу (и это
не петля), поднимите `LOOP_STATE_REPEATS`; если наоборот нужна более жёсткая
реакция — опустите `LOOP_STATE_WARN` до 1.

### В логе `invalid character ']' looking for beginning of value`, запуск падает

Разбор аргументов вызова от модели. Раньше это был фатальный error всего
запуска; сейчас аргументы чинятся толерантно (висячие запятые, кавычки,
переводы строк, ```-обёртки), а нечинимый вызов просто не выполняется, и модель
получает требование повторить его с валидным JSON. Если падает уже не разбор, а
что-то другое — включите детальный лог и посмотрите `Debugf` в `runner.go`.

### В JSON пакетах / логах видны цвета терминала и мусорные байты

Вывод команды нормализуется в `tools/fileops.go:runCommandSandbox` до упаковки
в JSON (`tools.SanitizeToolOutput`). Если мусор всё же доходит до модели —
значит, он приходит не из `Run` (например, из подмешиваемых логов приложения).

### Задача падает с «зациклился», хотя модель явно делала что-то полезное

Сработал бан на инструмент: если агент перебирал аргументы одного вызова и все
попытки падали, банятся все аргументы этого инструмента. Проверьте в дайджесте
(лог запуска), какие именно вызовы запрещены — скорее всего, ошибка была
неустранимой (нет доступа, битый путь), и осмысленного продолжения не было.

## Контекст

### `400 exceeded_context_size`

**Причина:** история агентского цикла разрослась.

**Решение — по возрастанию стоимости:**

```bash
# 1. Включить памятку модели о сжатии
CODEGEN_HISTORY_NOTICE=1

# 2. Задать явный бюджет
CODEGEN_HISTORY_BUDGET=200000

# 3. Вытеснение в RAG (требует Qdrant)
CODEGEN_HISTORY_EVICT=1

# 4. Оглавления убранных файлов (требует LSP)
CODEGEN_HISTORY_OUTLINE=1
```

> Страховка по окну модели (`CODEGEN_HISTORY_TOKENS` и адаптивный бюджет)
> работает **всегда**, даже при `CODEGEN_HISTORY_BUDGET=0`. Если ошибка
> сохраняется — увеличьте `settings.input_tokens` в `providers.json`.

## Git

### `ошибка клонирования: … ambiguous argument 'HEAD'`

Репозиторий **пуст** (0 коммитов): `git clone` проходит, но ветки нет —
HEAD нерождённый, `rev-parse --abbrev-ref HEAD` падает с 128.

```bash
git ls-remote --heads git@github.com:owner/repo.git   # пусто → репозиторий пуст
```

Исправлено: база определяется по имени unborn-ветки, создаётся первым коммитом
(`README.md`) и пушится в remote. Если ошибка осталась — нужен доступ на
**push**: `git push -u origin main` в `temp/<имя>` вручную покажет причину.

### `каталог … уже существует и не пуст`

В `temp/<имя>` лежит мусор от неудачного клона. Каталог от неудачного клона
**того же** репозитория (тот же origin, ни одного коммита, чистое состояние)
убирается автоматически при следующей попытке; чужое содержимое — никогда,
удалять нужно руками:

```bash
ls -a temp/<имя>            # убедиться, что там нет вашей работы
rm -rf temp/<имя>
```

### Плохой `origin` у проекта

Открыт не тот репозиторий (или тот же, но после смены адреса). Проект
переоткрыть нельзя — он в реестре. Удалите запись из
`<workspaces.json>` и каталог `temp/<имя>`, затем откройте заново.

### Конфликт мёрджа

| Что | Что происходит |
|---|---|
| Задача | `merge_conflict_files` заполняется, статус откатывается в `in_progress` |
| Эпик | `merge_conflict_files` заполняется, признак снимается `EpicResolve` или `EpicRelease` |
| `TaskMerge` из чата | Состояние **не меняется**, возвращается строка со списком файлов |

Разрешить: `ResolveGitConflicts` (`status` → `start` → `apply`) или
вручную в worktree.

### Авто-резолв не справился

Три попытки (`server/gitflow_ar.go:55`). Дальше — ручной разбор.

### Сабмодуль не запушился

Порядок важен: **сабмодули пушатся ДО родителя**, иначе gitlink родителя
ссылается на несуществующий SHA.

```bash
cd temp/<проект>
git submodule status
git -C <путь> log --oneline -3
```

## Приёмка

### Приёмка падает, хотя код работает

Проверьте, что команды приёмки совпадают с проектом:

```bash
ACCEPT_BUILD_CMD=... ACCEPT_TEST_CMD=... go run . accept <проект>
```

Приоритет: env → make-цель → автодетект по стеку.

### `ACCEPT_MAX_ROUNDS` не помогает

По умолчанию 3. Значение `≤ 0` — цикл отключён (только отчёт).

## Web UI

### Фронтенд показывает старую версию

```bash
npm --prefix web run build
go build .
```

`web/dist` встраивается в бинарь через `//go:embed` — без пересборки
фронтенда бинарь отдаёт старое.

### Не открывается WebSocket

Проверьте, что выбран существующий проект, и что соединение идёт по тому
же хосту. Клиент переподключается с растущей задержкой
(300/800/1500/3000/5000 мс) и перезапрашивает снапшоты.

### `429` при обновлении страницы

Rate-limit (константы в `server/server.go:116-118`, не настраиваются):

| Лимит | Значение |
|---|---|
| `/api/*` | 120 запросов в минуту на IP |
| Вход | 5 попыток в минуту |
| Отправка сообщения в чат (`/api/*/chat`) | 30 в минуту |

Лимит сбрасывается по окну, а не постепенно: после всплеска подождите минуту.
Лимит чата считает и пустые отправки — авто-пост на каждый ввод быстро его
исчерпывает.

### Плашмящийся diff пуст

Диффы теперь **контекстные** — открываются из модалки задачи или эпика.
Проектной кнопки «Дифф» больше нет: основной клон остаётся чистым, а
работа идёт в ветках и worktree.

## Песочница

### `Ошибка/Error 127` в приёмке

В контейнере нет `make` или другого инструмента хоста. Добавьте его в
`sandbox/Dockerfile` или используйте зеркальные `make infra.<цель>`.

### Путь проекта содержит `:` или `,`

Символы ломают `--volume` (`src:dst:opts`) — контейнер стартует и не видит
проекта (`tools/sandbox.go:294-300`). Ошибка конфигурации выдаётся явно.
**Перенесите проект** в каталог без этих символов.

### `go mod download` / `npm ci` не работают в контейнере

`CODEGEN_SANDBOX_NETWORK=none` отключает сеть. Верните `default` либо
запасите локальные кэши (`vendor/`, `GOMODCACHE`, `node_modules`, `.venv`).

### `rm -rf node_modules` отклонено

Так и задумано: ложное срабатывание хуже пропуска. Если команда
действительно нужна, убедитесь, что в строке нет запрещённых фрагментов
(`tools/destructive.go:33-86`).

### `pull access denied for ai-sandbox` — образ песочницы не собран

`ai-sandbox:latest` — **локальный** dev-образ, в реестре его нет, поэтому
pull всегда даёт `access denied` (проект-монорепо/без распознанного стека
выбирает именно его). Обычно песочница собирает его сама при старте
(`sandbox/ensureimage.go`); если этого не произошло — соберите вручную:

```bash
SANDBOX_UID=$(id -u) SANDBOX_GID=$(id -g) docker compose -f sandbox/compose.yaml build
```

## Сборка

### `go build ./...` падает

Ожидаемо: в `temp/` лежат сгенерированные проекты, которые не являются
исходным кодом. Используйте перечень без `./...`:

```bash
go build . ./agents/... ./tools/ ./board/
```

### `gofmt -l` показывает чужие файлы

Это **не гейт**: в репозитории 29 файлов с предсуществующими отклонениями
форматирования. Форматируйте только свои:

```bash
gofmt -l <файлы-которые-вы-трогали>
```

### `TestAcceptBuildFallsBackToInfraMirror` / `TestAcceptBuildToolMissingSkips` падают

Причина — окружение хоста, а не код: тесты ждут make-специфичный маркер
(`Ошибка` / `Error 127`), а системный `make` на этой машине выполняет
цель и возвращает `make: *** [build] Error 1` с
`No such file or directory` — без ожидаемого маркера.

Проверяется чистым HEAD: если падает и там — не регрессия. Логика зеркала
`make infra.<цель>` работает в контейнере приёмки.

### Инъекция добавилась, но модель её не применяет

Проверьте три вещи, в этом порядке — они отличаются симптомами:

1. **Область действия.** Инъекция сессии (`scope: session`) обслуживает только
   чат-ассистента. Если она добавлена во время агентского прогона задачи, в
   промпт исполнителя задачи она не попадёт — для этого есть инъекции задачи
   (`POST /api/projects/{id}/tasks/{tid}/injections` или `BoardUpdateTask`).
2. **Условие `when`.** При ложном условии инъекция не применяется, и это видно
   в debug-логе как `skipped` с причиной. Частая причина — переменная, которая
   в этом прогоне пустая (`model`, `project`, `task_id`).
3. **Выключена.** `enabled: false` сохраняет запись, но не применяет её; поле
   отсутствует — активна.

Текст инъекции в лог не пишется (в нём могут быть чувствительные строки), так
что смотреть нужно на метаданные: id, имя, scope, target и причину пропуска.

### `{{env.PATH}}` в инъекции остался плейсхолдером

Так и задумано: инъекция читает только переменные с префиксами `AI_`,
`CODEGEN_`, `OLLAMA_`, `KANBAN_` и разрешённые через `AI_INJECTION_ENV_ALLOW`.
Всё остальное окружение шаблону недоступно (иначе инъекция утекала бы секреты в
модель и в лог запроса). Если переменная нужна — добавь её префикс в
`AI_INJECTION_ENV_ALLOW`. Имена вида `*_API_KEY`, `*_TOKEN`, `*_SECRET`,
`*_PASSWORD` запрещены всегда: они подставляют `[REDACTED]`.

### `POST /injections` вернул `201`, а `DELETE` по этому id отвечает `404`

Обычно означает, что в запросе не совпадает `id` с тем, что лежит в записи.
Узнать фактические id: `GET /api/projects/{id}/injections`. Пустой список
означает, что запись не сохранилась (например, `500` на самом `POST` —
проверьте лог проекта).

## Задача навсегда осталась в статусе «в работе»

Обычно значит, что прогон упал: агент снял бы статус сам, но не успел
(сервер перезапустили, кончился контекст, убит процесс). Проверьте время
`heartbeat_at` задачи: пока оно моложе `KANBAN_STALE_TASK_MIN` (30 мин по
умолчанию), задача считается живой и в очередь не вернётся.

Что делать:

- подождать порог — следующий запуск вернёт задачу в очередь сама;
- если ждать нельзя, руками: `PUT /api/projects/{id}/tasks/{tid}` с
  `{"status":"ready"}` (то же делает кнопка «Вернуть в очередь»);
- `KANBAN_STALE_TASK_MIN=0` — вернуть всё, что не выполняет текущий запуск
  (осторожно с параллельными прогонами: watchdog ждёт только heartbeat).

## Задача зациклилась и остановилась «нужен человек»

Бюджет эскалаций исчерпан (`KANBAN_MAX_ESCALATIONS`): каждый раз, когда
специалист уходил в петлю, задача переключалась на большую модель, получала
разбор петли и возвращалась в очередь. Ничего не помогло — работа остановлена
на паузе, запуск упал с этой причиной.

Дальше — по существу, а не повтором запуска:

1. посмотрите `last_error`, `checkpoint.last_good_sha` и разбор петли в чате
   проекта;
2. откатите код к последней рабочей версии или снесите правки задачи
   ([откат](../20-features/gitops-workflow.md#откат-кода-задачи));
3. поставьте задачу в очередь вручную или перепишите её.

Больше попыток без изменений не будет: счётчик эскалаций сохранён в задаче.

## Промежуточный коммит задачи не создаётся: «коммит не создан: … больше лимита»

`git add -A` на раунде не фильтрует ничего, кроме `.gitignore`, поэтому в
коммит могло попасть всё, что агент положил в рабочее дерево. Живой случай:
в образе песочницы не было npm, агент скачал Node в корень проекта, и в коммит
ушли `node.tar.gz` (46 МБ) и 4287 файлов распакованного тулчейна. Теперь
`gitops.CommitIfDirty` меряет проиндексированные файлы и отказывает в коммите
(`gitops/gitops.go:checkStagedVolume`):

- один файл больше `KANBAN_WIP_COMMIT_MAX_FILE_BYTES` (по умолчанию 8 МБ);
- набор в сумме больше `KANBAN_WIP_COMMIT_MAX_BYTES` (по умолчанию 32 МБ).

Что делать:

1. убрать мусор из рабочего дерева задачи (или объяснить его в `.gitignore`);
2. если файл легальный (видео, датасет) — поднять порог осознанно, а не
   обходить проверку;
3. если мусор уже в истории ветки задачи — переписать её (см. ниже).

Индекс при отказе снимается (`git reset`), дерево не остаётся half-staged.

## Мусор в коммите задачи: node.tar.gz, node-v…, *.tsbuildinfo

Три причины, все закрыты в коде:

1. **Образ песочницы без нужного стека.** `tools/sandbox.go:detectSandboxStack`
   смотрит корень И первый уровень вглубь и, если найдено несколько стеков
   (монорепозиторий Go + Node), берёт dev-образ с go+node+python. Раньше
   монорепо попадало в `golang` без npm — агент и скачивал Node вручную.
2. **`.gitignore` проекта без стандартных артефактов.** `ensureTaskGitignore`
   дописывает недостающие паттерны (`node_modules/`, `node-v*/`,
   `*.tsbuildinfo`, `*.tar.*`, …) в существующий файл, ничего не удаляя.
   `vendor/` в список не входит.
3. **Объём коммита.** См. предыдущий раздел.

Переписать историю уже испорченной ветки: в worktree задачи уберите мусор,
затем пересоздайте коммит и запушьте с `--force-with-lease` в пределах своей
задачи. Коммит с чужими файлами можно вычистить из всех коммитов ветки через
`git filter-repo --path node-v20.18.0-linux-x64 --path node.tar.gz --invert-paths`.

## Задача не может стать выполненной: «в ветке … нет ни одного коммита»

Серверный гард «phantom done» (`server/gitflow_done_guard.go`) отказывает в
переходе в `done`, пока в ветке задачи нет своих коммитов относительно базы
эпика И worktree пуст. Именно так выглядела задача, которую никто не сделал, но
которая получила `done` от fallback'а оркестратора.

Дальше:

1. поставьте задачу в очередь — при следующем прогоне агент сделает работу;
2. если задача закрывается без кода (исследование, решение) — гард лишний,
   задайте `KANBAN_DONE_REQUIRES_COMMIT=0` для этого проекта;
3. если работа есть, но не в ветке задачи (например, агент правил основной
   клон) — перенесите изменения в ветку задачи, перезапустите прогон и только
   потом закрывайте.

## Кнопка отката у задачи не появляется

Откат работает по рабочей копии задачи (worktree). Она удаляется, когда задача
выполнена, — тогда в карточке вместо кнопок будет пояснение, что worktree
удалён. `git.tasks[tid].worktree` в снимке доски показывает, есть ли копия;
`git.tasks[tid].submodules` — какие вложенные сабмодули вернутся к состоянию
откатываемого коммита.

## Диагностика одним списком

```bash
docker compose ps                                    # инфраструктура
redis-cli -p 56379 ping                             # Redis
curl -s localhost:11434/api/tags | head              # Ollama
go run . index <проект>                              # RAG
which gopls                                          # LSP
go run . accept <проект>                             # приёмка
grep -n "skipped\|error" logs/<проект>.log | tail   # лог проекта
```
