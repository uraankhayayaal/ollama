# PLAN-2026-09-25 — Находки ручных E2E (2026-09-24)

Дефекты, найденные при выполнении пяти ручных E2E-пунктов из планов
`2026-09-22-done-assistant-ask-user`, `2026-09-24-done-architect-intelligence`,
`2026-09-24-done-contextual-diff`, `2026-09-24-done-makefile`,
`2026-09-24-done-merge-conflict-board`. Каждый пункт воспроизводится на тестовых
проектах в `temp/e2e-*` (git-демон `git://127.0.0.1:9418`), логи — в
`/tmp/opencode/e2e-logs/`.

## Ф-1 — Бинарный конфликт не распознаётся

- [ ] `gitops/merge.go:mergeTreeConflicts` учитывать бинарные конфликты
      (`git merge-tree` для бинарника отдаёт `warning: Cannot merge binary
      files: <path> (.our vs. .their)` + `changed in both`, без маркеров
      `<<<<<<< .our`), а не только текстовые.
- [ ] `POST /api/projects/{id}/epics/{eid}/release` при бинарном конфликте
      отдавать 409 со списком файлов, а не 502 «Конфликт слияния в …».
- [ ] `POST …/rebase` не должен отвечать «конфликтов не найдено», когда
      конфликт есть (сейчас бинарник молча резолвится, попадает в
      `resolved`, и в бейдж не попадает).
- [ ] Тест: бинарный конфликт эпика → 409/`files` → бейдж с путём бинарника.

## Ф-2 — Ручной релиз эпика не ставит признак конфликта

- [ ] `server/gitflow.go:handleReleaseEpic` при 409 записывать
      `epic.MergeConflictFiles = files` (как это делают
      `handleTaskMerge`, `autoResolveMainSync`, `handleEpicResolve`) и слать
      `RoleStatus`-уведомление.
- [ ] Тест REST: релиз эпика с конфликтом → 409 и
      `merge_conflict_files == ["app.py"]`; повторный `GET` доски показывает
      признак; успешный резолв снимает его.

## Ф-3 — Взаимная блокировка лидов при зависимости задачи от другого эпика

- [ ] `agents/planner/kanban.go:phaseLeads` не выдавать следующий эпик лиду,
      только пока `pipelineIdle`, если на доске есть задачи, заблокированные
      зависимостью от ещё не разобранного эпика. Сейчас: лид объявляет
      `dependencies:["ARCH-01"]` (эпик), `depsDone` требует `done` эпика,
      а разобрать эпик нельзя, пока задача не выполнена → `Kanban-цикл 2: нет
      прогресса`.
- [ ] Варианты: (а) приоритетно разбирать эпики-зависимости pending-задач;
      (б) разрешать зависимость «эпик» как «эпик декомпозирован и его задачи
      выполнены»; (в) валидация: не давать лиду ставить зависимость от эпика
      в очереди без предупреждения.
- [ ] Тест: доска с двумя эпиками, задача второго зависит от первого → цикл
      доходит до выполнения, а не падает «нет прогресса».

## Ф-4 — Web UI не доходит до main-фазы архитектора

- [ ] `server/session.go:247` (`SetBoardOnly(true)`) → `phaseArchitect`
      пропускается (`agents/planner/kanban.go:360`): из Web UI нельзя проверить
      обязательный эпик «Makefile проекта», предложение RAG-индекса и
      декомпозицию с учётом стека. Требуется решение: отдельный режим
      «новая задача» (не board-only) либо явная кнопка «Спланировать».
- [ ] Чат-ассистент не вызывает `ResolveGitConflicts` сам: на прямой просьбе
      («вызови инструмент ResolveGitConflicts») ограничивается `KanbanStart` и
      уточняющим вопросом — стоит усилить промпт `agents/chatassist/agent.go` /
      `server/chatassist.go`.

## Ф-5 — `GateBanner` не восстанавливается после перезагрузки страницы

- [ ] `web/src/App.tsx` инициализирует `gate` только из live WS-события:
      после F5 при `status=waiting` статус виден, затвор («утвердить
      эпики/задачи») не показывается. Проверено на `e2e-console-app`:
      подтверждение ушло через `POST /api/projects/{id}/{gate}/decide`.

## Не входит

- Правка `git daemon` в тестовом стенде (push через `git://` требует
  `--enable=receive-pack`; без него авто-синхрон падал на push) — это была
  проблема тестового окружения, не продукта.
- Модельные формулировки чат-ассистента (резолв) — ограничение поведения LLM,
  а не кода; кандидат на усиление промпта (Ф-4).
