# План: конфликты мёрджа на доске + без зацикливания ассистента

Статус: **DONE** (реализованы Ф-1..Ф-5; остался ручной E2E на живом проекте).

## Цель

Сделать конфликты git-мёрджа видимыми там, где они происходят — в задачах и
эпиках на доске, — и убрать порочный круг чат-ассистента, который при
конфликте `TaskMerge` раз за разом генерирует одно и то же сообщение.

Контекст из лога `2026-09-24_20-14-03_chat_.txt` (проект `my-rust-app`, эпик
GO-CLEANUP-01): мёрдж ветки GO-CLEANUP-01-T2 в релизную ветку эпика упирается в
конфликт бинарника `my-rust-app`, ассистент ~10 раз подряд выдаёт идентичный
ответ «Мерж не прошёл: конфликт в бинарнике…», нигде на доске конфликт не
отображается.

## Проблема (диагноз)

1. **«Фонового агента мёрджа» нет.** Мёрджи выполняют три независимые точки,
   и все они в фоне относительно цикла оркестрации:
   - авто-мёрдж при переводе задачи в `done` — хук
     `autoCommitAndMergeTask` (`server/gitflow_auto.go:244`):
     конфликт только логируется (`server/gitflow_auto.go:279`), доска не
     трогается;
   - инструмент ассистента `TaskMerge` (`server/actions.go:231`) → общая
     механика `mergeTaskBranch` (`server/gitflow.go:383`), конфликт приходит
     как `MergeConflictError` в результат инструмента;
   - `reconcileMRs` (`server/gitflow_mr.go:411`, в `boardFlusher` раз в 60 с)
     сверяет только статусы MR и мёрджи не делает.
2. **Повторяющиеся `A:` в логе — зациклившийся ассистент, а не фоновая
   рассылка.** `TaskMerge` возвращает один и тот же `MergeConflictError`
   (бинарик `my-rust-app`); состояние доски и чата не меняется → каждый новый
   вызов модели даёт ту же реплику. Дубли `U:`/`S:` — повторная отправка
   клиента/двойной клик, дублей в хранилище чата не обнаружено
   (`handlePostChat` `server/server.go:585` и `runChatAssistant`
   `server/chatassist.go:32` ведут к единственной записи ответа: guard
   `finalReported` + ручной append).
3. **Конфликт не отображается на доске.** `board.Epic`/`board.Task`
   (`board/entity.go:167,204`) несут только `git_branch`; `gitView`/`gitLinkView`
   (`server/gitflow_mr.go:28-48`) — ветку и MR без признака конфликта. Поле
   «есть MR-статус» не покрывает случай «мерж невозможен».

## Текущее состояние

- Резолв конфликтов «main ↔ релизная ветка эпика» уже встроен (Ф-4):
  `handleEpicRebase`/`handleEpicResolve` (`server/gitflow_resolve.go`),
  инструмент `ResolveGitConflicts`, конфликтный worktree `.conflict-<п>-<эпик>`.
- Конфликт «ветка задачи ↔ ветка эпика» на `done` решается только логом
  (`autoCommitAndMergeTask`) — оркестрация/доска сигнала не получают.
- Статусный переход `done` происходит ДО авто-мёрджа: задача «выполнена», хотя
  её правки в релиз эпика не попали. Хук `TaskDoneHook` не ломает переходы
  статусов (осознанный дизайн) — конфликт нужно не откатывать, а помечать.

## Поведение

1. Задача/эпик на доске несут признак «конфликт мёрджа» со списком файлов там,
   где мёрдж ветки не удался (авто-путь done и инструмент `TaskMerge`).
2. При успешном вливании задачи в релиз эпика признак конфликта у задачи
   снимается. При успешном релизе/резолве эпика — снимается у эпика.
3. Web UI показывает конфликт у задачи/эпика: бейдж «Конфликт мёрджа», список
   файлов и подсказку «резолв через ResolveGitConflicts / ручной rebase».
4. `TaskMerge` при конфликте возвращает стабильный, информативный результат со
   списком файлов и указанием пути резолва — модель не «ходит по кругу», а
   видит конкретную причину и точку входа.
5. Повторный `TaskMerge` при том же конфликте не меняет состояние — признак
   конфликта идемпотентен.

## Решения реализации

### Ф-1 — Признак конфликта в модели доски (board) + запись на сервере

- `board.Task` и `board.Epic`: опциональное поле
  `MergeConflictFiles []string` (`json:"merge_conflict_files,omitempty"`).
  Непустой список = «ветка не влилась, ждёт резолва». Для эпика заполняется
  при конфликте авто-синхрона релизной ветки с main (`autoResolveMainSync`,
  ветка `hard`); для задачи — при конфликте мёрджа done→релиз.
- Хелперы `SaveTask`/`SaveEpic` уже умеют перезаписывать запись целиком —
  отдельные геттеры/сеттеры не нужны; проставляем поле там, где доступен
  `*board.Store`.
- Точки записи конфликта:
  - `autoCommitAndMergeTask` (`server/gitflow_auto.go`): ветка
    `MergeConflictError` → `SaveTask` с `MergeConflictFiles = ce.Files`;
    успех → очистка поля; уведомление в чат `RoleStatus` («конфликт мёрджа
    задачи <id> в файлах […] — нужен резолв»).
  - `Session.TaskMerge` (`server/actions.go`): при `MergeConflictError` →
    `SaveTask` с полем конфликта, возврат ошибки с файлами.
  - `mergeTaskBranch` успех (из авто-пути и ручного merge REST
    `handleMergeTask`) → очистка поля задачи.
  - `autoResolveMainSync` hard-конфликт и `handleEpicRebase`/`handleEpicResolve`
    → проставление/очистка у эпика (только при наличии доступа к хранилищу).

### Ф-2 — Уведомления и снапшот доски

- `chatAssistantPrompt` (или отдельное `boardRev`-сообщение) — признак
  конфликта уже виден ассистенту через компоненты доски: «В работе» и модалки
  содержат объекты задач/эпиков целиком (поле проходит как есть, без правок
  `gitView`). Добавить в промпт строку-индикатор «задача X — конфликт мёрджа»
  для задач с `MergeConflictFiles != nil`, чтобы модель не звала `TaskMerge`
  повторно, а шла на резолв.
- `gitView` не меняется: `boardSnapshot` уже несёт полные `Epic`/`Task`
  (`boardView`, `server/session.go:657`).

### Ф-3 — Web UI

- `web/src/Types/Types.ts`: `MergeConflictFiles: string[]` в типах `Task`/`Epic`.
- `GitBlock`/модалки `TaskModal`/`EpicModal`: если поле непусто — показать
  бейдж/баннер «Конфликт мёрджа: файлы […]» и короткую подсказку про
  `ResolveGitConflicts`/ручной rebase. Кнопки «Создать MR»/«Залить в main» не
  прятать (они остаются страховкой), но конфликт виден первым делом.
- `npm run build` в `web/`.

### Ф-4 — Стабильный результат TaskMerge

- `Session.TaskMerge`: ошибку конфликта возвращать в виде
  `MergeConflictError`-совместимой строки, содержащей список файлов и путь
  резолва («конфликт в [f1, f2] — ветка не тронута; используйте
  ResolveGitConflicts или ручной rebase»). Результат детерминирован: повторный
  вызов возвращает то же (состояние жетсля не меняется).
- Промпт `agents/chatassist/agent.go`: явная инструкция «при status=error с
  конфликтом мёрджа не повторяй TaskMerge — сообщи пользователю файлы и
  предложи резолв/спроси ручное действие».

### Ф-5 — Верификация

- Hermetic- и real-git тесты записи конфликта (`autoCommitAndMergeTask` со
  `MergeConflictError` пишет поле; успешный мёрдж очищает; идемпотентность
  повторного `TaskMerge`).
- Тесты снапшота доски (поле проходит в REST и WS).
- Сборка/vet/тесты по перечню AGENTS.md + `npm run build`.

## Не входит в задачу

- **Резолв конфликтов фазой KanbanRunner** («в рамках оркестрации»): перевод
  «конфликтной» задачи в отдельный статус и авто-планирование резолва лидами —
  крупная доработка оркестратора, выносится отдельным планом. Здесь — только
  видимость и стабильная обратная связь.
- **Авто-dedup идентичных сообщений ассистента в чате**: повторные реплики
  уйдут сами исчезновением причины (конфликт перестанет быть «немым»). Финальный
  дедупликатор писать не будем.
- **Снятие «всех» конфликтов эпика автоматически**: при hard-конфликтах
  авто-синхрона ветка эпика не продвигается (осознанное поведение Ф-4), признак
  лишь дублирует это на доске.

задаче отношения не имеют.
