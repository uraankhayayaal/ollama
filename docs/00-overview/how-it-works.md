# Как проходит задача

Сквозной путь: от промпта пользователя до merge в `main`. Два входа —
CLI и Web UI, дальше сходятся.

## Общая схема

```
Промпт пользователя
      │
      ├─ CLI: go run . kanban <проект> "<промпт>"
      └─ Web UI: сообщение в чат → session.Start(...)
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Архитектор                                                │
│    Собирает стек проекта (DetectStack), планку проекта,      │
│    при необходимости — индекс RAG. Публикует эпики:          │
│    submit_architecture_backlog                               │
└─────────────────────────────────────────────────────────────┘
      │  доска: status=new, requires_review=true
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Ревизия черновиков (если включена)                        │
│    phaseArchitectReview: архитектор в режиме AsReviewer()    │
│    снимает requires_review, выравнивает LeadSyncedRev        │
└─────────────────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Лиды (backend / frontend / devops / qa)                   │
│    Декомпозируют эпик на атомарные задачи,                  │
│    задают scope (какие файлы/папки), контракты,             │
│    зависимости, assigned_role                                │
└─────────────────────────────────────────────────────────────┘
      │  задачи: status=analysis → ready
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Исполнение                                               │
│    Каждая готовая задача уходит специалисту. Параллельно —  │
│    независимые задачи одной волны. Файловые мутации —        │
│    под пер-проектной блокировкой (tools/filelock.go)         │
└─────────────────────────────────────────────────────────────┘
      │  задача: in_progress → done
      │  git: коммит worktree → авто-MR → merge в релиз
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. Приёмка (детерминированно, без LLM)                       │
│    install → build → format → analyze → LSP → run            │
│    Провал → багрепорт; баг-фаза: эксперт → решения          │
│    → эпик на исправление → снова лиды → снова специалисты    │
└─────────────────────────────────────────────────────────────┘
      │  все задачи done + приёмка ок
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. Релиз эпика                                              │
│    syncEpicWithMain (фон, таймаут 5 мин)                     │
│    merge в main или merge_conflict_files на доске            │
└─────────────────────────────────────────────────────────────┘
```

## Фазы Kanban-раннера

`agents/planner/kanban.go` — цикл до полного решения задачи:

| Фаза | Функция | Что делает |
|---|---|---|
| Архитектура | `phaseArchitect:658` | Эпики создаются, если их нет |
| Ревизия | `phaseArchitectReview:700` | Черновики (`requires_review=true`) уходят архитектору на ревизию |
| Лиды | `phaseLeads:766` | Эпики без задач декомпозируются |
| Готовность | `phaseReady:1090` | Задачи `analysis` → `ready` |
| Исполнение | `phaseExecute:1167` | Готовые задачи раздаются специалистам |
| Баги | `phaseBugs:1254` | Багрепорты: эксперт → решение → новый эпик |
| Завершение | `phaseComplete:1314` | Эпик выпускается, доска очищается |

Ограничения цикла: `maxKanbanRounds = 100` (`kanban.go:29`), опрос доски в
режиме ожидания — `standbyPoll = 5s` (`kanban.go:87`).

## Что делает каждый участник

| Роль | Создаёт | Меняет статус | Инструменты работы с кодом |
|---|---|---|---|
| Архитектор | Эпики, `Opportunity` | Эпик: `new` → `analysis` → `ready` … | `List`, `ReadFiles`, `Lsp*`, `CodeSearch`, `RagIndexStatus`, `DetectStack` |
| Лид направления | Задачи, контракты | Задача: `analysis` → `ready` | `List`, `ReadFiles`, `ReadMap`, `WriteFiles`, `AppendFile`, `Lsp*` |
| Специалист | Код, багрепорты (QA) | Задача: `ready` → `in_progress` → `done` | `WriteFiles`, `ReadFiles`, `ReadMap`, `DeleteFiles`, `Run`, `List`, `AppendFile`, `SearchReplace`, `PatchGoFunction`, `PatchFunction`, `LspCheck`, `ReadAppLogs`, `CodeSearch` |
| Ревьюер | Комментарии в MR, вердикт | — | `ReviewMr`, `ApproveMr`, `NextChunk` |
| Чат-ассистент | Эпики, багрепорты | Эпик, баг | чтение + `CodeSearch` + `WebSearch` + `Board*` + серверные мосты |
| Приёмка | Отчёт, вердикт | — | Детерминированный пайплайн, LLM нет |

## Цикл исправления по багу

```
QA-инженер / приёмка находит проблему
      │  BoardCreateBugReport, status=new
      ▼
QA Lead: триаж → confirmed | slop
      │  confirmed
      ▼
Архитектор-эксперт (AsBugExpert) → BoardReviewBugReport
      │  fix → создаётся эпик на исправление → цикл лидов
      │  feature | wont_fix → закрывается
      ▼
Специалист чинит → задача done → приёмка заново
```

## Границы цикла

Цикл не бесконечен: `maxKanbanRounds = 100`. При исчерпании сессия
останавливается с понятным статусом. То же с `ACCEPT_MAX_ROUNDS` в
исполнителе плана (`plan`) — количество циклов «приёмка → исправления →
приёмка».

## Что может остановить задачу

| Ситуация | Поведение |
|---|---|
| Сборка упала в приёмке | `reject` → багрепорт → эпик на исправление |
| LSP-ошибка в scope шага | Шаг падает, scope откатывается, план останавливается (`agents/planner/lspgate.go:153-164`) |
| Модель вернула пустой ответ с `finish_reason=length` | Шаг `failed`, план падает — а не «успешно без кода» |
| Конфликт merge в задаче | `merge_conflict_files` + откат в `in_progress` |
| Конфликт merge в эпике | `merge_conflict_files` на эпике, автосинхронизация main в фоне |
| Неоднозначность в постановке | `AskUser` (только Web UI): вопрос ждёт ответа 15 минут |
