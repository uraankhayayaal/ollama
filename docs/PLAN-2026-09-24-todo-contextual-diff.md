## Цель

Убрать устаревшую плавающую кнопку «Дифф» проекта. Она показывает изменения
рабочей копии основного клона, тогда как код задач и эпиков теперь живёт в
отдельных ветках и worktree. Просмотр диффа должен начинаться из самой задачи
или эпика и показывать изменения именно её ветки относительно основной ветки
(`git_base`, обычно `main`). Для отображения и просмотра файлов переиспользовать
существующую компоненту `Diffboard`, адаптировав её под контекстный режим.

## Проблема (диагноз)

Для git-проектов дифф строится как `git add -N -A && git diff <base>` в
**рабочем каталоге основного клона** `temp/<проект>` (ветка `ai/<проект>`),
где `<base>` = `git_base` (main) с момента открытия. Но с введением git-workflow
реальная работа идёт **не в этом клоне**:

- специалисты задач в `in_progress` пишут в **постоянные worktree** веток
  `ai/task/<id>` (`.wt-task-<проект>-<taskID>`, `server/gitflow_auto.go`);
  `OutputDir` специалиста = worktree задачи;
- изменения задач попадают в **релизные ветки эпиков** `ai/epic/<id>` через
  авто-мёрдж done→релиз и авто-коммит;
- основной клон остаётся чистым на `ai/<проект>`.

**Следствие.** Дифф проекта показывает пустой результат либо только
legacy-правки общего клона — реальные изменения веток эпиков/задач он не видит.
Дополнительно был латентный баг кэша: `gitProjectDiff` мог вернуть
закешированные данные без пересоздания на новый запрос списка.

## Поведение

1. Удалить плавающую кнопку «Дифф» проекта. Кнопка «Логи» остаётся на месте.
2. В `GitBlock` модалки эпика показывать «Дифф» для ветки эпика; в `GitBlock`
   модалки задачи — «Дифф» для ветки задачи. Не показывать кнопку, если нужная
   ветка ещё не создана или проект не git-типа.
3. Нажатие открывает общий `Diffboard` в контексте выбранного ref и показывает
   изменения этой ветки относительно основной ветки проекта (`git_base`). Для
   задачи включать незакоммиченные изменения её worktree, если worktree есть.
4. Использовать имеющиеся в `Diffboard` фильтрацию файлов и side-by-side
   просмотр. В заголовке явно показать имя/тип сущности, source branch и
   основную ветку сравнения.
5. Закрытие Diffboard возвращает к той же открытой модалке. Открытие другого
   diff сбрасывает раскрытые файлы, фильтры, патчи и ошибки предыдущего ref.
6. Контекстный режим — только просмотр. Кнопки «Принять»/«Отклонить» текущего
   проектного diff не показываются для веток задач и эпиков; проектные действия
   не применяются к выбранному ref.
7. Если у ветки пока нет изменений, показать понятное пустое состояние. Ошибки
   отсутствующей ветки/worktree объясняют причину, не скрывают дифф другой
   ветки и не превращаются в пустой успешный результат.

## Решения реализации

### Серверный API

Расширить существующий `GET /api/projects/{id}/diff` параметрами `ref` и `vs`,
сохранив прежнее поведение при их отсутствии. Для контекстного запроса передавать
`ref=ai/epic/<id>` или `ref=ai/task/<id>`, `vs=<git_base>`.

```
GET /api/projects/{id}/diff                            — legacy: проектная ветка ai/<проект> vs main
GET /api/projects/{id}/diff?ref=ai/epic/<eid>[&vs=main]
GET /api/projects/{id}/diff?ref=ai/task/<tid>[&vs=main|ai/epic/<eid>]
GET /api/projects/{id}/diff?file=<path>&ref=...&vs=... — ленивый патч файла с тем же ref/vs
```

- **Ветка задачи с зарегистрированным worktree** (`BranchRef.Worktree`): команды
  выполняются в worktree, включаются незакоммиченные правки —
  `git add -N -A` + `git diff <MB>`, где `MB = merge-base(vs, HEAD)` (`rev-parse --git-dir`
  проверяет, что worktree ещё жив, иначе — ошибка, а не пустой diff). Семантика
  совпадает с тем, что на done закоммитит `commitTaskWorktree`.
- **Эпик и задача без worktree**: трёхточечный diff коммитов `vs...ref`
  (three-dot, вклад от merge-base) в основном клоне, рабочий каталог не
  участвует — не тянет «обратный» шум от движения main после точки отхода.
- **Проверка ref по реестру веток проекта** (side-реестр `workspace.GitBranches`,
  `EpicBranch`/`TaskBranch`): произвольные пути клиента не принимаются;
  неизвестная ref → 4xx с объяснением, не скрывается и не выдаётся за пустой diff.
- **`vs` по умолчанию** = `git_base` (main): дифф показывает всё, что придёт в
  main при «Залить в main»/MR эпика.
- **Кэш**: отдельный ключ `(project, ref, vs)` (`diffCacheKey`); список файлов
  пересоздаётся на каждый запрос списка, ленивые патчи берутся из последнего
  результата с тем же ключом. Инвалидация при accept/reject/release/merge,
  создании/снятии worktree и создании веток (`invalidateDiffs(project)`).
- **Текущий API без ref** остаётся совместимым для иных клиентов; Web UI больше
  не предлагает глобальный просмотр проектной рабочей копии.

## Не входит в задачу (взято из плана от 09-23)

- **Селектор веток в глобальном Diffboard** и поле `refs` в ответе — заменено
  контекстной точкой входа из модалок.
- **Режим «Все изменения»** (суммарный дифф всех релизных веток эпиков против
  main) — отдельная задача.
- **Действия по выбранной ветке** (accept→MR / reject / «Залить в main» из
  диффа ветки) — не первая волна; сейчас дифф только для просмотра.
- **Отдельные примитивы `gitops.DiffIn`/`DiffTree`** — логика branchDiff встроена
  в `server/diff.go`, вынос в gitops не потребовался.
