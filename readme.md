# Начало работы:
1. Запустить контейнеры `docker compose up` (поднимает Ollama, Qdrant и Redis — Redis нужен для чекпоинтов команды `plan`)
1. Загрузить модель `docker compose exec -it ollama ollama pull qwen3-coder:30b`
1. Загрузить модель `docker compose exec -it ollama ollama pull qwen2.5-coder:7b`

# Запуск команд

Агент выбирается через первый аргумент командной строки.

1. **Генератор кода** — создаёт проект в папке `temp/<имя_проекта>/`. Имя проекта обязательный аргумент, промпт опционален:
   ```bash
   go run . generate storageService "Напиши микросервис для хранения файлов"
   ```
   Если промпт не указан, используется задание по умолчанию: `go run . generate storageService`

   Возможности генератора:
   - **Инструменты** `WriteFile`/`WriteFiles` (запись файлов), `ReadFiles` (чтение), `DeleteFiles` (удаление), `List` (дерево файлов), `AppendFile` (точечное дополнение) и `Run` (запуск `go build`/`go vet`/`go test` в OutputDir).
   - **Принудительный вызов инструмента**: в первом раунде модель обязана вызвать `WriteFiles` (а не ответить текстом). Если она всё же отвечает текстом, раннер подсказывает ей и повторяет запрос; для Yandex на первом шаге дополнительно форсируется `tool_choice` на этот инструмент.
   - **Самопроверка кода**: после записи агент сам запускает сборку и проверки, а если есть ошибки — исправляет код до «зелёного» состояния.
   - **Self-review (цикл repair)**: написанный код прогоняется через агента кодревью в локальном режиме (без сети), найденные замечания передаются модели для исправления в несколько раундов (до схождения или бюджета `CODEGEN_MAX_REPAIR_ROUNDS`), после чего SUMMARY записывается в файл.
   - В конце пишет `readme.md` с инструкцией запуска.
1. **Рефакторинг существующего проекта** — работает с уже созданным проектом по имени. Проект должен существовать в `temp/`:
   ```bash
   go run . refactor storageService "Добавить эндпоинт /healthcheck"
   ```
   Агент изучает текущий код (List → ReadFiles), вносит целенаправленные правки и проверяет сборку. Цикл self-repair работает аналогично генератору.

   Примеры:
   ```bash
   # Добавить новую фичу в существующий проект
   go run . refactor storageService "Добавить REST API для управления пользователями"

   # Проверить код и исправить ошибки
   go run . refactor storageService "Проверить код на ошибки, провести рефакторинг и запустить автотесты"

   # Доработка: добавить тесты
   go run . refactor storageService "Добавить unit-тесты для всех функций в пакете internal/"
   ```
1. **Планировщик (`plan`)** — разбивает задачу на этапы и выполняет их отдельными агентами с чистым контекстом (экономия токенов по сравнению с одним длинным диалогом):
   ```bash
   go run . plan storageService "Создай микросервис хранения файлов и отревьюй код"
   ```
   Как это работает:
   - Планировщик возвращает план в JSON: шаги с типом агента (`codegenerator` / `refactor` / `codereviewer`), зависимостями и **scope** — областью работы шага (конкретные файлы/директории). Агенты работают только в рамках своего scope: ревьювер не смотрит на код, не затронутый шагом, и не заваливает план незапрошенными фиксами.
   - **Последовательность делегации**: все шаги разработки идут агенту `refactor` (для нового проекта его создаёт `codegenerator`), затем, ПОСЛЕ выполнения всех шагов, весь изменённый код одним шагом передаётся `codereviewer`. Замечания ревью превращаются в новые шаги `refactor` (цикл «ревью → исправление → ревью», бюджет `REVIEW_FIX_ROUNDS`), и только когда замечаний не осталось — финальная приёмка `acceptor` (сборка, стилизатор, анализатор). Замечания приёмки также возвращаются разработчику (цикл `ACCEPT_MAX_ROUNDS`).
   - **Декомпозиция задач**: перед планированием проекту строится компактная **карта проекта** (структура, размеры файлов, языки — без содержимого), которая подсказывает планировщику, как разбить задачу. Крупная работа разбивается на несколько небольших шагов по 5–10 файлов (по одному пакету за шаг), чтобы каждый шаг умещался в контекст модели.
    - **Фронтенд и бэкенд**: когда запрос затрагивает клиент и/или сервер, планировщик строит монорепозиторий с подкаталогами `frontend/` и `server/`. Шаги разработки получают **роль** (`role: "frontend" | "backend"`) и работают только внутри своей директории (фронтендер не трогает серверный код и наоборот), чтобы параллельные шаги не конфликтовали за файлы. Приёмка монорепозитория выполняется по подпроектам: отдельная сборка/запуск фронтенда и бэкенда, отчёт содержит блоки по каждому подпроекту (`main.go: accept` печатает их по одному, файлы замечаний имеют префикс `frontend/…`, `server/…`). Статический фронтенд (Vite/React и т.п. без точки входа для запуска) принимается по сборке.
   - Шаги группируются в **волны параллельности** (`ComputeWaves`): независимые шаги одной волны могут выполняться параллельно (сейчас — последовательно, структура готова к распараллеливанию).
   - **Защита от переполнения контекста**: дифф ревью ограничен `REVIEW_MAX_DIFF_SIZE`, чтение файлов — `CODEGEN_READ_MAX_FILE`/`CODEGEN_READ_MAX_TOTAL`, бинарные файлы в дифф не попадают.
   - Выполнение идёт с **контрольными точками** (чекпоинтами) в Redis — можно возобновлять работу с места остановки.
   - **Честность при сбоях**: если модель не создала код (пустой ответ с `finish_reason="length"`), шаг считается упавшим (`failed`) и план останавливается с ошибкой, а не «успешно выполняется» без кода. Исправь лимит токенов (`YANDEX_MAX_TOKENS`, по умолчанию 8000, первый раунд WriteFiles — 16000) и повтори через `--resume`.

   Чекпоинты и resume (`plan --resume`):
   ```bash
   # чекпоинты включаются автоматически, если в .env задан REDIS_ADDR
   go run . plan storageService "Создай микросервис и отревьюй код"

   # если прогон прервался — продолжаем, не перепланируя задачу и не
   # переделывая выполненные шаги (планировщик при resume не вызывается)
   go run . plan storageService --resume
   ```
   Включить контрольные точки можно и явно переменной `PLAN_CHECKPOINT=1`,
   возобновить — флагом `--resume` или `PLAN_RESUME=1`. После успешного
   завершения плана чекпоинт можно сбросить: `redis-cli del checkpoint:<имя_проекта>`.

   ### Декомпозиция задач и лимиты контекста

   Чтобы планы не упирались в лимит контекста модели (ошибки вида
   `maximum context length is ... tokens`), планировщик работает так:

   1. **Карта проекта** — перед составлением плана проекту строится компактная
      сводка: дерево файлов с размерами и языки по расширениям (без содержимого).
      Она передаётся планировщику в системный промпт, поэтому модель видит,
      что уже есть в проекте, и не тратит контекст на чтение всех файлов.
   2. **Декомпозиция** — планировщик разбивает задачу на небольшие шаги:
      5–10 файлов на scope, один пакет за шаг; крупная работа — несколькими
      отдельными шагами, а не одним гигантским «сделай всё». У каждого шага
      явный `scope`.
   3. **Волны** — независимые шаги группируются в волны, которые можно
      выполнять параллельно (структура готова к распараллеливанию).
   4. **Лимиты контекста** — даже при неточном scope срабатывают жёсткие
      ограничения: дифф ревью не превышает `REVIEW_MAX_DIFF_SIZE`, чтение
      файлов ограничено `CODEGEN_READ_MAX_FILE` / `CODEGEN_READ_MAX_TOTAL`,
      бинарные файлы в дифф не попадают.

   Когда что подкручивать:
   - Упал с ошибкой `maximum context length`: **сначала** уменьши лимиты
     (`REVIEW_MAX_DIFF_SIZE=100000`, `CODEGEN_READ_MAX_TOTAL=300000`) — это
     дешевле, чем пересобирать план; **потом** перезапусти `plan --resume`.
   - Замечания ревью «не увидели» часть кода (в диффе заметка о превышении
     лимита) — увеличь `REVIEW_MAX_DIFF_SIZE` и при необходимости
     `REVIEW_CHUNK_SIZE`.
   - Проект большой (сотни файлов) — карта проекта сама ограничена 200
     файлами, планировщик сделает много мелких шагов; это нормально.

1. **Кодревью** MR — ссылку на Merge Request/Pull Request передаём напрямую. Второй необязательный аргумент — цель ревью (например «безопасность», «производительность»):
   ```bash
   go run . review <URL_MR>
   # пример:
   go run . review https://gitlab.com/it-yakutia/botsad.ru/-/merge_requests/2
   # с фокусом на безопасность:
   go run . review https://github.com/user/repo/pull/10 "безопасность"
   ```
   Репозиторий можно ревьюить и без сети, передав локальную директорию: `go run . review local:///путь/к/коду`.

Вспомогательные флаги:
- `LLM_DEBUG=1` — подробный лог запросов/ответов моделей: `LLM_DEBUG=1 go run . generate`
- `YANDEX_MAX_TOKENS=<число>` — лимит токенов ответа Yandex (по умолчанию 8000; на первом раунде WriteFiles автоматически поднимается до 16000)
- `REVIEW_TIMEOUT=<длительность>` — таймаут всего цикла агента (например `15m`), по умолчанию `5m`
- `REVIEW_MAX_COMMENTS=<число>` — лимит замечаний за ревью (по умолчанию 10)
- `REVIEW_CRITICAL_ONLY=<true|false>` — публиковать только критические замечания (баги, падения, уязвимости, гонки, утечки ресурсов); стиль/«можно лучше»/«стоит проверить» отсекаются и не пачкают MR (по умолчанию true)
- `REVIEW_BLOCK_ON_CRITICAL=<true|false>` — блокировать апрув при критичных замечаниях (по умолчанию true)
- `REVIEW_SKIP_GENERATED=<true|false>` — отсекать сгенерированные/бинарные файлы (по умолчанию true)
- `REVIEW_CHUNK_SIZE=<число>` — дифф длиннее этого значения (в символах) ревьюится по частям, чтобы не переполнять контекст модели (по умолчанию 14000, 0 — без разбиения)
- `REVIEW_MAX_DIFF_SIZE=<байт>` — жёсткий лимит суммарного размера диффа (по умолчанию 300000). Защита на больших проектах: файлы сверх бюджета в дифф не попадают (перечисляются заметкой), бинарные пропускаются. При 0 лимит принимает значение по умолчанию
- `REVIEW_MAX_ROUNDS=<число>` — максимум циклов «модель→инструмент» за ревью (по умолчанию 12; для ревью больших диффов по частям может потребоваться больше)
- `CODEGEN_LANG=<язык>` — целевой язык программирования (по умолчанию `Go`)
- `CODEGEN_MODULE=<модуль>` — имя модуля Go для `go.mod` (пусто — модель придумывает сама)
- `CODEGEN_MAX_FILES=<число>` — максимум записываемых файлов за запуск (0 — без лимита)
- `CODEGEN_NO_OVERWRITE=<true|false>` — запрещать перезапись существующих файлов (по умолчанию false)
- `CODEGEN_SUMMARY_FILE=<имя>` — имя файла-отчёта после генерации (по умолчанию `SUMMARY.md`, пусто — отключить)
- `CODEGEN_READ_MAX_FILE=<байт>` — максимум содержимого одного файла при чтении инструментом `ReadFiles` (по умолчанию 100000; избыток обрезается с пометкой)
- `CODEGEN_READ_MAX_TOTAL=<байт>` — суммарный лимит чтения за один вызов `ReadFiles` (по умолчанию 800000; файлы сверх лимита пропускаются с пометкой)

Настройки чекпоинтов планировщика (`plan`):
- `REDIS_ADDR=<host:port>` — адрес Redis (по умолчанию `localhost:6379`). Если задан явно, контрольные точки включаются автоматически
- `PLAN_CHECKPOINT=1` — явно включить контрольные точки (крайне рекомендуется для больших планов)
- `PLAN_RESUME=1` / флаг `--resume` — продолжить план с места остановки (без вызова планировщика); Redis должен быть доступен
- `REDIS_PASSWORD=<пароль>` — пароль Redis (пусто — без пароля)
- `REDIS_DB=<число>` — номер базы Redis (по умолчанию 0)
- `PLAN_CHECKPOINT_TTL=<длительность>` — время жизни чекпоинта (например `24h`), 0 — без истечения (по умолчанию)

Автоматическая защита от галлюцинаций: перед публикацией каждое замечание проверяется по актуальному диффу — комментарии к файлам или номерам строк, которых нет в диффе, отсекаются и не публикуются (при этом не блокируют апрув и не считаются ошибками). Дубликаты замечаний к одной и той же строке публикуются один раз.

Если модель (например, YandexGPT) вместо вызова инструментов пишет ревью текстом, замечания автоматически распарсиваются из ответа и публикуются в MR/PR, с применением той же проверки по диффу.

Провайдер (ollama/yandex) и ключи задаются в файле `.env` (переменная `LLM_PROVIDER`).

## Запуск локально на Apple Silicon (MacBook)

Для локального запуска через Ollama/LM Studio подготовлены два готовых
конфига — переключайся между «дом/Yandex» и «работа/локально» простым
копированием нужного файла в `.env`:

- **`.env.macbook.air`** — MacBook Air **M1 / 16 ГБ** (слабое железо):
  8B модель в кванте **Q4_K_M**, уменьшенный контекст и мелкие диффы
  (`REVIEW_CHUNK_SIZE=6000`), меньше раундов ревью/repair, таймаут `10m`.
- **`.env.macbook.m3`** — MacBook **M3 / 64 ГБ** (мощное): можно модель
  14B–30B, дефолтные (более щедрые) лимиты, таймаут `15m`.

Общие советы под локальный 8B на слабом железе:
- Бери квант **Q4_K_M** (ок. 5 ГБ) — Q5/Q6/Q8 не дают ощутимого качества,
  но быстрее забивают память 16 ГБ и уводят в своп.
- Ограничь контекст в самой модели/сервере на **8192 токенов**: это делается
  в Ollama (`OLLAMA_CONTEXT_LENGTH=8192` / `num_ctx`) или в настройках LM Studio.
  Сам провайдер `ollama` в этом проекте контекст не пробрасывает — только
  уровень сервера.
- На 16 ГБ не ставь контекст выше 16K и не держи параллельно тяжёлые приложения.

Для работы на слабом железе полезно уменьшать: `REVIEW_CHUNK_SIZE`,
`REVIEW_MAX_COMMENTS`, `CODEGEN_MAX_REPAIR_ROUNDS` — так диффы и история
влезают в малый контекст, а генерация идёт быстрее.

В Go для работы с Qdrant используется официальный клиент https://github.com/qdrant/go-client:
```bash
go get github.com/qdrant/go-client
```
Для RAG-систем всегда используйте gRPC порт (6334) вместо HTTP — это снижает задержки (latency) при поиске векторов в разы.
```go
package main

import (
	"context"
	"log"
	"time"

	"github.com/qdrant/go-client"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	// Подключаемся по gRPC
	client, err := qdrant.NewClient(&qdrant.Config{
		Host: "localhost",
		Port: 6334,
	})
	if err != nil {
		log.Fatalf("Ошибка подключения к Qdrant: %v", err)
	}
	defer client.Close()

	collectionName := "knowledge_base"

	// Создаем коллекцию (например, под эмбеддинги размерностью 1024)
	err = client.CreateCollection(ctx, &qdrant.CreateCollection{
		CollectionName: collectionName,
		VectorsConfig: qdrant.NewVectorsConfig(&qdrant.VectorParams{
			Size:     1024,                   // Укажите размерность вашей модели эмбеддингов
			Distance: qdrant.Distance_Cosine, // Косинусное сходство — стандарт для RAG
		}),
	})
	if err != nil {
		log.Printf("Коллекция уже существует или ошибка: %v", err)
	}
}

```
