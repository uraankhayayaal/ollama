# Начало работы:
1. Запустить контейнеры `docker compose up` (поднимает Ollama, Qdrant и Redis — Redis нужен для чекпоинтов команды `plan`)
1. Загрузить модель `docker compose exec -it ollama ollama pull qwen3-coder:30b`
1. Загрузить модель `docker compose exec -it ollama ollama pull qwen2.5-coder:7b`

# Запуск команд

Агент выбирается через первый аргумент командной строки.

1. **Backend разработчик** — создаёт серверную часть проекта (подкаталог `server/`) или дорабатывает существующую: API, бизнес-логика, БД. Проект создаётся в папке `temp/<имя_проекта>/`. Имя проекта обязательный аргумент, промпт опционален:
   ```bash
   go run . backend storageService "Напиши микросервис для хранения файлов"
   ```
   Если промпт не указан, используется задание по умолчанию: `go run . backend storageService`
   Алиас по обратной совместимости: `go run . generate storageService "..."`.

   Возможности агента-разработчика:
   - **Инструменты** `WriteFile`/`WriteFiles` (запись файлов), `ReadFiles` (чтение), `DeleteFiles` (удаление), `List` (дерево файлов), `AppendFile` (точечное дополнение) и `Run` (запуск `go build`/`go vet`/`go test` в OutputDir).
   - **Точечные правки существующего кода**: `SearchReplace` (универсальные блоки `<<<<<<< SEARCH ... ======= ... >>>>>>> REPLACE` — дословное совпадение искомого фрагмента, при промахе файл не изменяется) и `PatchGoFunction` (семантическая замена одной Go-функции через `go/ast`, с форматированием через `go/format` и опциональным добавлением импортов). Механизм изолирует правку субагента, чтобы он не переписывал/удалял функционал, реализованный другими задачами плана.
   - **Изучение кода до правок**: агент не обязан вызывать инструмент в первом раунде — сначала изучает существующую структуру (List → ReadFiles), затем создаёт недостающие файлы или дорабатывает код.
   - **Самопроверка кода**: после записи агент сам запускает сборку и проверки, а если есть ошибки — исправляет код до «зелёного» состояния.
   - В конце пишет `readme.md` с инструкцией запуска.
1. **Frontend разработчик** — создаёт или дорабатывает клиентскую часть (подкаталог `frontend/`): UI-компоненты, страницы, стили, клиентская логика:
   ```bash
   go run . frontend storageService "Напиши веб-интерфейс для просмотра файлов"
   ```
   Работает аналогично backend-разработчику, но только внутри `frontend/` (не трогает серверный код).
   Оба разработчика умеют дорабатывать уже существующий проект: изучают текущий код (List → ReadFiles), вносят целенаправленные правки и проверяют сборку. Примеры:
   ```bash
   # Добавить новую фичу (серверная часть)
   go run . backend storageService "Добавить REST API для управления пользователями"

   # Проверить код и исправить ошибки
   go run . backend storageService "Проверить код на ошибки и запустить автотесты"

   # Доработка: добавить тесты
   go run . backend storageService "Добавить unit-тесты для всех функций в пакете internal/"
   ```
1. **Планировщик (`plan`)** — разбивает задачу на этапы и выполняет их отдельными агентами с чистым контекстом (экономия токенов по сравнению с одним длинным диалогом):
   ```bash
   go run . plan storageService "Создай микросервис хранения файлов и отревьюй код"
   ```
Как это работает:
    - Планировщик возвращает план в JSON: шаги с типом агента (`backend` / `frontend` / `devops` / `qa` / …), зависимостями и **scope** — областью работы шага (конкретные файлы/директории). Агенты работают только в рамках своего scope: например, разработчик не трогает код вне своей части подпроекта.
    - **Последовательность делегации**: все шаги разработки идут агентам-разработчикам `backend` (подкаталог `server/`) / `frontend` (подкаталог `frontend/`), затем, ПОСЛЕ выполнения всех шагов, добавляется финальный шаг `qa` — единый агент приёмки: собирает проект, запускает автотесты и проверяет логи на ошибки. Если приёмка не пройдена — отчёт (логи) возвращается планировщику, тот составляет шаги исправления разработчикам, и приёмка повторяется (цикл `ACCEPT_MAX_ROUNDS`). Эпик/план завершается, когда выполнены все задачи и приёмка пройдена.
   - **Декомпозиция задач**: перед планированием проекту строится компактная **карта проекта** (структура, размеры файлов, языки — без содержимого), которая подсказывает планировщику, как разбить задачу. Крупная работа разбивается на несколько небольших шагов по 5–10 файлов (по одному пакету за шаг), чтобы каждый шаг умещался в контекст модели.
    - **Фронтенд и бэкенд**: когда запрос затрагивает клиент и/или сервер, планировщик строит монорепозиторий с подкаталогами `frontend/` и `server/`. Шаги разработки назначаются отдельным агентам (backend — только `server/`, frontend — только `frontend/`) и работают только внутри своей директории (фронтендер не трогает серверный код и наоборот), чтобы параллельные шаги не конфликтовали за файлы. Приёмка монорепозитория выполняется по подпроектам: отдельная сборка/запуск фронтенда и бэкенда, отчёт содержит блоки по каждому подпроекту (`main.go: accept` печатает их по одному, файлы замечаний имеют префикс `frontend/…`, `server/…`). Статический фронтенд (Vite/React и т.п. без точки входа для запуска) принимается по сборке.
   - Шаги группируются в **волны параллельности** (`ComputeWaves`): независимые шаги одной волны могут выполняться параллельно (сейчас — последовательно, структура готова к распараллеливанию).
   - **Защита от переполнения контекста**: дифф ревью ограничен `REVIEW_MAX_DIFF_SIZE`, чтение файлов — `CODEGEN_READ_MAX_FILE`/`CODEGEN_READ_MAX_TOTAL`, бинарные файлы в дифф не попадают.
   - Выполнение идёт с **контрольными точками** (чекпоинтами) в Redis — можно возобновлять работу с места остановки.
   - **Честность при сбоях**: если модель не создала код (пустой ответ с `finish_reason="length"`), шаг считается упавшим (`failed`) и план останавливается с ошибкой, а не «успешно выполняется» без кода. Исправь лимит токенов (`YANDEX_MAX_TOKENS`, по умолчанию 8000, первый раунд WriteFiles — 16000) и повтори через `--resume`.
   - **Защитный откат (rollback)**: перед выполнением каждого шага делается снимок файлов проекта; если шаг упал с реальной ошибкой (не «исчерпан лимит раундов» — там откат поломал бы resume), директория возвращается к состоянию снимка: созданные упавшим субагентом файлы удаляются, а изменённые/удалённые им файлы (в т.ч. чужой код) — восстанавливаются. Следующий шаг и параллельные агенты всегда стартуют с консистентного состояния. Отключается переменной `CODEGEN_ROLLBACK_ON_FAIL=0` (по умолчанию включён).

   Чекпоинты и resume (`plan --resume`):
   ```bash
   # чекпоинты включаются автоматически, если в .env задан REDIS_ADDR
   go run . plan storageService "Создай микросервис и отревьюй код"

   # если прогон прервался — продолжаем, не перепланируя задачу и не
   # переделывая выполненные шаги (планировщик при resume не вызывается)
   go run . plan storageService --resume
   ```
   Включить контрольные точки можно и явно переменной `PLAN_CHECKPOINT=1`,
   возобновить — флагом `--resume` или `PLAN_RESUME=1`. После успешного
   завершения плана чекпоинт можно сбросить: `redis-cli del checkpoint:<имя_проекта>`.

   ### Декомпозиция задач и лимиты контекста

   Чтобы планы не упирались в лимит контекста модели (ошибки вида
   `maximum context length is ... tokens`), планировщик работает так:

   1. **Карта проекта** — перед составлением плана проекту строится компактная
      сводка: дерево файлов с размерами и языки по расширениям (без содержимого).
      Она передаётся планировщику в системный промпт, поэтому модель видит,
      что уже есть в проекте, и не тратит контекст на чтение всех файлов.
   2. **Декомпозиция** — планировщик разбивает задачу на небольшие шаги:
      5–10 файлов на scope, один пакет за шаг; крупная работа — несколькими
      отдельными шагами, а не одним гигантским «сделай всё». У каждого шага
      явный `scope`.
   3. **Волны** — независимые шаги группируются в волны, которые можно
      выполнять параллельно (структура готова к распараллеливанию).
   4. **Лимиты контекста** — даже при неточном scope срабатывают жёсткие
      ограничения: дифф ревью не превышает `REVIEW_MAX_DIFF_SIZE`, чтение
      файлов ограничено `CODEGEN_READ_MAX_FILE` / `CODEGEN_READ_MAX_TOTAL`,
      бинарные файлы в дифф не попадают.

   Когда что подкручивать:
   - Упал с ошибкой `maximum context length`: **сначала** уменьши лимиты
     (`REVIEW_MAX_DIFF_SIZE=100000`, `CODEGEN_READ_MAX_TOTAL=300000`) — это
     дешевле, чем пересобирать план; **потом** перезапусти `plan --resume`.
   - Замечания ревью «не увидели» часть кода (в диффе заметка о превышении
     лимита) — увеличь `REVIEW_MAX_DIFF_SIZE` и при необходимости
     `REVIEW_CHUNK_SIZE`.
   - Проект большой (сотни файлов) — карта проекта сама ограничена 200
     файлами, планировщик сделает много мелких шагов; это нормально.

1. **Кодревью** MR — ссылку на Merge Request/Pull Request передаём напрямую. Второй необязательный аргумент — цель ревью (например «безопасность», «производительность»):
   ```bash
   go run . review <URL_MR>
   # пример:
   go run . review https://gitlab.com/it-yakutia/botsad.ru/-/merge_requests/2
   # с фокусом на безопасность:
   go run . review https://github.com/user/repo/pull/10 "безопасность"
   ```
   Репозиторий можно ревьюить и без сети, передав локальную директорию: `go run . review local:///путь/к/коду`.

Вспомогательные флаги:
- `LLM_DEBUG=1` — подробный лог запросов/ответов моделей: `LLM_DEBUG=1 go run . generate`
- `YANDEX_MAX_TOKENS=<число>` — лимит токенов ответа Yandex (по умолчанию 8000; на первом раунде WriteFiles автоматически поднимается до 16000)
- `OLLAMA_MODEL_LARGE=<модель>` — большая модель для «тяжёлых» агентов (Лиды, Архитектор, Ревьюер). Если задана, `OLLAMA_MODEL` используется для рядовых разработчиков, а эта — для агентов, требующих высокого качества рассуждения (мультипровайдер `LayeredProvider`)
- `OLLAMA_THINK=<0|1>` — управление цепочкой рассуждения (thinking) для reasoning-моделей (qwen3 и др.): `0`/`false`/`off` — явно отключить (рекомендуется для инструментных циклов — рассуждение удваивает время и токены), `1` — принудительно включить; по умолчанию не задаётся (модель работает как настроена)
- `OLLAMA_KV_CACHE_TYPE=<q8_0|f16|q4_0>` — формат KV-кэша модели: `q8_0` сильно уменьшает объём кеша в RAM/VRAM ценой небольшой потери точности (рекомендуется для длинных сессий агентов), `f16` — точность, `q4_0` — максимум экономии
- `OLLAMA_KEEP_ALIVE=<длительность>` — сколько держать модель в памяти после запроса (например `10m`, `-1` — без выгрузки). Сессии агентов делают десятки обращений подряд — постоянная выгрузка/загрузка модели замедляет работу
- `REVIEW_TIMEOUT=<длительность>` — таймаут всего цикла агента (например `15m`), по умолчанию `5m`
- `REVIEW_MAX_COMMENTS=<число>` — лимит замечаний за ревью (по умолчанию 10)
- `REVIEW_CRITICAL_ONLY=<true|false>` — публиковать только критические замечания (баги, падения, уязвимости, гонки, утечки ресурсов); стиль/«можно лучше»/«стоит проверить» отсекаются и не пачкают MR (по умолчанию true)
- `REVIEW_BLOCK_ON_CRITICAL=<true|false>` — блокировать апрув при критичных замечаниях (по умолчанию true)
- `REVIEW_SKIP_GENERATED=<true|false>` — отсекать сгенерированные/бинарные файлы (по умолчанию true)
- `REVIEW_CHUNK_SIZE=<число>` — дифф длиннее этого значения (в символах) ревьюится по частям, чтобы не переполнять контекст модели (по умолчанию 14000, 0 — без разбиения)
- `REVIEW_MAX_DIFF_SIZE=<байт>` — жёсткий лимит суммарного размера диффа (по умолчанию 300000). Защита на больших проектах: файлы сверх бюджета в дифф не попадают (перечисляются заметкой), бинарные пропускаются. При 0 лимит принимает значение по умолчанию
- `REVIEW_MAX_ROUNDS=<число>` — максимум циклов «модель→инструмент» за ревью (по умолчанию 12; для ревью больших диффов по частям может потребоваться больше)
- `CODEGEN_LANG=<язык>` — целевой язык программирования (по умолчанию `Go`)
- `CODEGEN_MODULE=<модуль>` — имя модуля Go для `go.mod` (пусто — модель придумывает сама)
- `CODEGEN_MAX_FILES=<число>` — максимум записываемых файлов за запуск (0 — без лимита)
- `CODEGEN_NO_OVERWRITE=<true|false>` — запрещать перезапись существующих файлов (по умолчанию false)
- `CODEGEN_SUMMARY_FILE=<имя>` — имя файла-отчёта после генерации (по умолчанию `SUMMARY.md`, пусто — отключить)
- `CODEGEN_READ_MAX_FILE=<байт>` — максимум содержимого одного файла при чтении инструментом `ReadFiles` (по умолчанию 100000; избыток обрезается с пометкой)
- `CODEGEN_READ_MAX_TOTAL=<байт>` — суммарный лимит чтения за один вызов `ReadFiles` (по умолчанию 800000; файлы сверх лимита пропускаются с пометкой)
- `PARALLEL_TOOL_CALLS=<0|1>` — параллельное выполнение независимых (read-only) инструментов одного раунда (по умолчанию включено). Когда модель запрашивает несколько вызовов сразу (parallel tool calling), чтения (`List`/`ReadFiles`/`ReadMap` и чтение Kanban-доски) выполняются одновременно — раунд «изучить проект» ускоряется в разы. Пишущие/мутирующие инструменты (`WriteFiles`, `SearchReplace`, `PatchGoFunction`, `Run`, публикация ревью и др.) по-прежнему выполняются строго последовательно в порядке вызова. `0` — отключить (последовательное исполнение, как раньше)
- `PARALLEL_TOOL_MAX=<число>` — максимальная ширина параллельной волны read-only инструментов (по умолчанию 8; `0` — без ограничения)

Инструмент `LspCheck` (точечная диагностика кода «глазами IDE»: точные строки ошибок по стеку проекта — gopls/tsc/pyright/ruff):
- По умолчанию (Ф-4) диагностики берутся нативно — из стрима `publishDiagnostics` языкового сервера стека (тот же процесс, что навигация Ф-3); если сервер недоступен — автоматический fallback на CLI-чекер (gopls check / tsc / pyright):
- `LSP_NATIVE=<0|1>` — выключить/включить нативный режим (по умолчанию включён; `0`/`false`/`off`/`no` — только CLI-чекеры)
- `LSP_DIAG_WAIT=<длительность|секунды>` — пауза ожидания публикации диагностик после открытия файлов (по умолчанию 3s; например `1500ms` или `2`)
- `LSP_MAX_DIAGS=<число>` — максимум диагностик в одном ответе (по умолчанию 30; сначала error, затем warning)
- `LSP_MAX_OUTPUT=<байт>` — символьный лимит суммарного ответа (по умолчанию 4000; лишние диагностики отсекаются с пометкой `truncated`)
- Бинарники ищутся не только в PATH процесса (у сервера/демона он урезан), но и в типовых каталогах установки: `~/go/bin`, `GOBIN`/`GOPATH/bin`, префиксы npm/nvm, Homebrew (`/opt/homebrew/bin`, `/usr/local/bin`) — см. пакет `tools/binpath`. Дополнительные каталоги можно задать:
- `LSP_BIN_PATH=<каталоги>` — список каталогов поиска чекеров/серверов, добавляется к поиску с наивысшим приоритетом (разделитель как у PATH)
- Если нужный чекер/сервер не установлен — инструмент возвращает `skipped` с подсказкой использовать `Run`; шаг не падает.

Точечные ЛСП-замечания по scope шага (Ф-5) — приёмка и волны плана используют те же нативные диагностики (без CLI-чекера): ошибки дают точные файл:строка:колонка, из которых строится scope фикс-шагов:
- `LSP_STEP_GATE=<0|1>` — включить/выключить scope-гейт шага плана: после каждого кодирующего шага нативные диагностики прогоняются строго по области работы (scope); найденные error-замечания — шаг падает, область откатывается, план останавливается (по умолчанию включён; `0`/`false`/`off`/`no` — выключить). Сервер не установлен или в scope нет исходников — гейт молчит (деградация)
- `ACCEPT_LSP=<0|1>` — включить/выключить этап ЛСП-диагностики при приёмке (по умолчанию включён; `0`/`false`/`off`/`no` — выключить). Замечания попадают в отчёт приёмки как analyze-ошибки (error → reject) и в scope планировщика исправлений; сервер не установлен — этап пропускается без сбоя

Языковые серверы ставятся **на хост** (Dockerfile агента нет; в `compose.yaml` только ollama/open-webui/qdrant/redis): `go install golang.org/x/tools/gopls@latest`, `npm i -g typescript-language-server`, `npm i -g pyright`.
Навигация по коду «глазами IDE» (Ф-3, инструменты `LspDefinition`/`LspReferences`/`LspHover`) — выдаются разработчикам/QA и лидам: переход к определению символа, поиск всех ссылок и справка (hover) без чтения десятков файлов. Языковой сервер поднимается как долгоживущий процесс по стеку проекта (`gopls` / `typescript-language-server` / `pyright-langserver`) и кэшируется на проект.
- `LSP_TIMEOUT=<длительность|секунды>` — таймаут одного LSP-запроса (по умолчанию 15s; например `20s` или `60`)
- `LSP_MAX_LOCATIONS=<число>` — максимум позиций в ответе навигации (по умолчанию 50; избыток отсекается с пометкой `truncated`)
- `LSP_SERVER=<команда>` — явно задать языковой сервер (например `gopls` или `typescript-language-server --stdio`), минуя автопоиск в PATH
- Если сервер не установлен — инструмент возвращает `skipped` с подсказкой `ReadMap`/`ReadFiles`; шаг не падает.

Авто-самоисправление (Ф-2): после раунда, в котором агент-разработчик менял файлы, раннер сам прогоняет `LspCheck` по затронутым файлам и при ошибках подмешивает скрытую подсказку с точными строками — модель правит код, не тратя раунды на перечитывание логов сборки. Повторные диагностики между итерациями дедуплицируются (Ф-4): один и тот же текст не показывается модели дважды.
- `LSP_AUTO_FIX=<0|1>` — включить/выключить авто-самоисправление (по умолчанию включено; `0`/`false`/`off`/`no` — выключить)
- `LSP_MAX_FIX_ROUNDS=<число>` — максимум подряд итераций авто-лечения до сброса эпизода (по умолчанию 3). Чистый раунд (без диагностик) сбрасывает счётчик и память об отправленных строках

Частичная переиндексация RAG (Ф-5): после раунда, в котором агент-разработчик менял файлы, раннер (в том же хуке, что и авто-самоисправление) заново индексирует затронутые файлы в векторную память — последующие `CodeSearch`/контекст плана видят свежий код. Удалённые файлы чистятся из индекса; промптов модели переиндексация не подмешивает.
- `RAG_AUTO_REINDEX=<0|1>` — включить/выключить авто-переиндексацию после мутаций (по умолчанию выключено: индекс собирается явно командой `go run . index <проект>`; `1`/`true`/`on`/`yes` — включить). Без подключённого Qdrant переиндексация молча пропускается (degrade)

- `LSP_IDLE_TTL=<длительность|минуты>` — таймаут простоя клиента LSP: неиспользуемые клиенты закрываются через указанное время (по умолчанию 10m; например `30m` или `1` для 1 минуты; `0` — отключить эвикцию)

Настройки чекпоинтов планировщика (`plan`):
- `REDIS_ADDR=<host:port>` — адрес Redis (по умолчанию `localhost:56379`). Если задан явно, контрольные точки включаются автоматически
- `PLAN_CHECKPOINT=1` — явно включить контрольные точки (крайне рекомендуется для больших планов)
- `PLAN_RESUME=1` / флаг `--resume` — продолжить план с места остановки (без вызова планировщика); Redis должен быть доступен
- `CODEGEN_ROLLBACK_ON_FAIL=<0|1>` — отключить/включить защитный откат шагов, упавших с ошибкой (по умолчанию включён; при `0` файлы упавшего субагента сохраняются для отладки/resume)
- `REDIS_PASSWORD=<пароль>` — пароль Redis (пусто — без пароля)
- `REDIS_DB=<число>` — номер базы Redis (по умолчанию 0)
- `PLAN_CHECKPOINT_TTL=<длительность>` — время жизни чекпоинта (например `24h`), 0 — без истечения (по умолчанию)

Логи (пакет `logging`) — у каждого проекта свой файл:
- `LOG_DIR=<каталог>` — каталог лог-файлов (по умолчанию `logs` относительно cwd)
- Проект пишет в `logs/<проект>.log`. Имя файла выводится из имени проекта (`logging.ProjectLogName`): всё, кроме букв/цифр/`-_.`, заменяется на `_`, поэтому `../` в имени не выводит запись за пределы каталога
- `go run . serve` — один процесс ведёт много проектов, поэтому служебные сообщения процесса идут в `logs/server.log`, а сообщения сессии и оркестрации (`KanbanRunner`, `Executor`) — в `logs/<проект>.log` своего проекта. Панель «Логи» Web UI показывает только файл этого проекта плюс все логи из `<корень_проекта>/logs/`
- CLI-команды `backend`/`frontend`/`plan`/`kanban`/`accept`/`devops`/`qa`/`*lead` пишут в `logs/<имя_проекта>.log`; `review` → `logs/review.log`, `listen` → `logs/mrlistener.log`
- До вызова `logging.Setup` (тесты, утилиты) файлы не создаются — вывод только в консоль
- Real-time: хвост лог-файла транслируется в панель «Логи» по WebSocket (`type="log"`); брокер пересканирует каталог и подхватывает файлы, созданные позже подписки, корректно переживает ротацию и удаление

Автоматическая защита от галлюцинаций: перед публикацией каждое замечание проверяется по актуальному диффу — комментарии к файлам или номерам строк, которых нет в диффе, отсекаются и не публикуются (при этом не блокируют апрув и не считаются ошибками). Дубликаты замечаний к одной и той же строке публикуются один раз.

Если модель (например, YandexGPT) вместо вызова инструментов пишет ревью текстом, замечания автоматически распарсиваются из ответа и публикуются в MR/PR, с применением той же проверки по диффу.

Провайдер (ollama/yandex) и ключи задаются в файле `.env` (переменная `LLM_PROVIDER`).

Поддержка git submodule в Web UI: при открытии git-проекта приложение
инициализирует сабмодули, регистрирует каждый как дочерний git-проект и
показывает изменения его файлов в общей Diffboard. Для task worktree вложенный
репозиторий получает отдельную ветку; при приёмке сначала публикуются и
получают MR сабмодули, затем родитель с обновлёнными gitlink.

- `GITOPS_SUBMODULES=0` — не инициализировать сабмодули (по умолчанию включено).
- `GITOPS_SUBMODULE_DEPTH=<число>` — ограничить историю сабмодулей указанной
  положительной глубиной; пустое значение оставляет полную историю.
- Токены GitHub/GitLab выбираются отдельно для remote каждого репозитория:
  `GITHUB_TOKEN` и `GITLAB_TOKEN`. Для SSH remote используются настроенные SSH-ключи.
- Глубоко вложенные сабмодули и параллельные задачи, меняющие один gitlink,
  требуют ручной проверки; поддерживаемый workflow рассчитан на прямые
  сабмодули родительского проекта.

## Запуск локально на Apple Silicon (MacBook)

Для локального запуска через Ollama/LM Studio подготовлены два готовых
конфига — переключайся между «дом/Yandex» и «работа/локально» простым
копированием нужного файла в `.env`:

- **`.env.macbook.air`** — MacBook Air **M1 / 16 ГБ** (слабое железо):
  8B модель в кванте **Q4_K_M**, уменьшенный контекст и мелкие диффы
  (`REVIEW_CHUNK_SIZE=6000`), меньше раундов ревью/repair, таймаут `10m`.
- **`.env.macbook.m3`** — MacBook **M3 / 64 ГБ** (мощное): можно модель
  14B–30B, дефолтные (более щедрые) лимиты, таймаут `15m`.

Общие советы под локальный 8B на слабом железе:
- Бери квант **Q4_K_M** (ок. 5 ГБ) — Q5/Q6/Q8 не дают ощутимого качества,
  но быстрее забивают память 16 ГБ и уводят в своп.
- Ограничь контекст в самой модели/сервере на **8192 токенов**: это делается
  в Ollama (`OLLAMA_CONTEXT_LENGTH=8192` / `num_ctx`) или в настройках LM Studio.
  Сам провайдер `ollama` в этом проекте контекст не пробрасывает — только
  уровень сервера.
- На 16 ГБ не ставь контекст выше 16K и не держи параллельно тяжёлые приложения.

Для работы на слабом железе полезно уменьшать: `REVIEW_CHUNK_SIZE`,
`REVIEW_MAX_COMMENTS` — так диффы и история
влезают в малый контекст, а генерация идёт быстрее.

В Go для работы с Qdrant используется официальный клиент https://github.com/qdrant/go-client:
```bash
go get github.com/qdrant/go-client
```
Для RAG-систем всегда используйте gRPC порт (56334) вместо HTTP — это снижает задержки (latency) при поиске векторов в разы.
```go
package main

import (
	"context"
	"log"
	"time"

	"github.com/qdrant/go-client"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	// Подключаемся по gRPC
	client, err := qdrant.NewClient(&qdrant.Config{
		Host: "localhost",
		Port: 6334,
	})
	if err != nil {
		log.Fatalf("Ошибка подключения к Qdrant: %v", err)
	}
	defer client.Close()

	collectionName := "knowledge_base"

	// Создаем коллекцию (например, под эмбеддинги размерностью 1024)
	err = client.CreateCollection(ctx, &qdrant.CreateCollection{
		CollectionName: collectionName,
		VectorsConfig: qdrant.NewVectorsConfig(&qdrant.VectorParams{
			Size:     1024,                   // Укажите размерность вашей модели эмбеддингов
			Distance: qdrant.Distance_Cosine, // Косинусное сходство — стандарт для RAG
		}),
	})
	if err != nil {
		log.Printf("Коллекция уже существует или ошибка: %v", err)
	}
}

```
